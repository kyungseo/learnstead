# 01. 한 세션이 막히는 세 가지 이유 — 컨텍스트·시간·편향

> 이 문서는 [`README.md`](README.md)의 1장입니다. 다음 → [`02-layers-of-splitting.md`](02-layers-of-splitting.md)

## 이 장에서 답하는 질문

- 코딩 에이전트 세션 하나로 충분하던 일이 언제부터 안 되는가
- "나눈다"는 말이 코딩 에이전트에서 정확히 무엇을 뜻하는가
- 작업을 분담하기 전에 무엇을 측정해야 효과를 비교할 수 있는가

## 1. 기본값은 한 세션이다

코딩 에이전트는 한 세션 안에서 파일을 읽고, 명령을 돌리고, 결과를 보고 다음 행동을 정하는 루프를 돕니다([Agent 구조](../../guides/agent-skills/00-how-an-agent-works.md)). 먼저 이 실행 흐름 하나로 작업을 완료할 수 있는지 확인합니다. **별도 에이전트나 세션을 추가하려면 해결할 문제를 구체적으로 정해야 합니다.** 이 원칙은 [코드로 여러 호출을 엮는 가이드](../../guides/agent-orchestration/01-why-more-than-one.md)와 같습니다. 그쪽은 내 코드가 모델을 여러 번 부르는 이야기이고, 이 가이드는 Claude Code·Codex 같은 실행 도구(runtime)의 subagent·worktree·팀 기능으로 작업을 맡기고 조정하는 방법을 다룹니다. `[원리]`

## 2. 작업 분담을 검토할 세 가지 이유

이 가이드에서는 컨텍스트·시간·검토 관점의 세 문제를 살펴봅니다. 모든 실패가 이 셋에 속하는 것은 아닙니다. 요구사항이 불분명하거나 필요한 권한·자료가 없는 문제는 세션을 늘려도 해결되지 않습니다.

| 문제 | 증상 | 원인으로 살펴볼 것 | 검토할 방법 |
| --- | --- | --- | --- |
| **컨텍스트** | 조사하느라 읽은 파일이 대화를 채워 정작 구현할 때 앞의 지시를 잊는다 | 읽은 자료와 작업 기록이 같은 세션의 입력에 쌓인다([05 예산과 compaction](../../guides/context-engineering/05-budget-and-compaction.md)) | 읽기를 **위임하고** 요약만 받는다 (subagent) |
| **시간** | 서로 독립적인 과제를 순서대로 처리하느라 완료가 늦어진다 | 과제를 순차로 수행하는 구성 | 과제를 **병렬로** 돌린다 (subagent 여러 개 · worktree 세션) |
| **편향** | 방금 쓴 코드를 같은 세션이 검토하면 "문제 없음"이 나올 수 있다 | 검토자가 작성자의 가정을 그대로 들고 있다 | 검토 기준을 지목해 묻고, 필요하면 **다른 컨텍스트에서** 검토한다 (이 가이드의 실측에서는 기준을 지목하자 같은 세션도 잡았다) |

이 세 문제는 [Local LLM 앱 연결 가이드](../../guides/local-llm-app-integration/06-tool-calling-workflow-agent.md)가 말한 "누가 제어 흐름을 쥐는가"와 다른 축입니다. 그 가이드는 코드가 정한 절차(workflow)와 모델이 다음 행동을 정하는 agent를 구분했고, 여기서는 agent가 이미 있다는 전제에서 **agent를 몇 개, 어떤 관계로 두는가를** 다룹니다. `[해석]`

## 3. 무엇을 별도로 맡기거나 실행하는가

작업 분담을 설계할 때는 입력 자료와 기록, 편집할 폴더, 담당 역할을 각각 정합니다. 이 셋은 해결하는 문제가 다릅니다.

- **별도 컨텍스트에서 작업한다** — subagent가 전달받은 자료로 작업하고, 메인은 그 결과를 받습니다. 메인 화면에 별도 창이 뜨는지는 도구마다 다르고, 전체 시간은 줄지 않을 수 있습니다. subagent 위임의 중요한 효과이며, [context-engineering 05](../../guides/context-engineering/05-budget-and-compaction.md)가 "큰 읽기는 서브에이전트로"라고 한 것이 이것입니다.
- **별도 작업 폴더에서 편집한다** — 같은 저장소를 다른 폴더에 체크아웃(checkout)하고 각 폴더에서 작업합니다. 충돌은 사라지지 않고 **합칠 때로 미뤄집니다**. [Git 가이드 07](../../guides/git-for-vibe-coders/07-worktrees.md)의 worktree가 이것입니다.
- **작성과 검토의 담당을 구분한다** — 예를 들어 한 세션이 작성한 코드를 다른 세션이 요구사항과 대조합니다. 추가 시간과 토큰을 써서 작성 과정의 가정을 다시 살펴보려는 구성입니다. 다른 컨텍스트라는 이유만으로 검토 품질이 높아지는 것은 아닙니다.

이 방법들은 함께 사용할 수 있습니다. 예를 들어 worktree에서 실행하는 subagent는 작업 기록과 편집 폴더를 모두 별도로 둡니다. 입력 부담을 줄이려는지, 편집 충돌을 피하려는지, 다른 관점의 검토를 받으려는지 먼저 정하고 필요한 방법을 선택하세요.

## 4. 작업을 분담하기 전에 측정할 것

작업 분담의 효과를 알려면 한 세션이 직접 처리한 결과와 비교해야 합니다. 이 가이드와 실습은 다음 네 항목을 기준선으로 씁니다. 벽시계 시간은 명령을 시작해 끝날 때까지 실제로 흐른 시간입니다.

| 숫자 | 어디서 읽나 | 무엇을 말해 주나 |
| --- | --- | --- |
| **메인 컨텍스트 크기** | 메인 세션의 마지막 API 호출에 실린 입력 토큰. Claude Code는 `stream-json`의 마지막 assistant 메시지 `usage`(입력+캐시), Codex는 rollout `token_count`의 `last_token_usage`. 채점기 열 `main_ctx_last` | 직접 처리보다 마지막 요청이 작았는가. 작업 중 최대 크기나 압축 횟수까지 뜻하지는 않음 |
| **누적 입력 토큰** | 세션이 보낸 입력의 합. Claude Code `result.usage`(메인만)·`modelUsage`(subagent 포함), Codex `turn.completed`와 자식 rollout | 반복 입력량이 얼마나 늘었는가. 캐시·모델별 단가가 달라 청구 금액과 같지는 않음 |
| **벽시계 시간** | 실행 전후 시각 | 병렬이 실제로 빨랐는가 |
| **결과 품질** | 채점기의 결함 위치 일치·미리 정한 결함 목록(골든셋) 밖의 지적 수 + 지적 원문·요구 기능 확인 | 올바른 결함을 설명했는가, 요구한 변경이 최종 결과에 남았는가. 위치 일치와 테스트 통과만으로 완료를 판정하지 않음 |

한 세션이 직접 처리한 측정값을 먼저 기록하는 것이 이 가이드에서 가장 중요한 습관입니다. [코드 레벨 가이드](../../guides/agent-orchestration/05-when-not-to.md)도 역할과 단계를 추가한 효과를 기존 방식과 비교하도록 안내합니다. 실습 [01](../../labs/delegate-and-verify/01-baseline.md)이 이 기준선을 만듭니다. `[실행 검증 · 실습 01]`

## 이 장을 끝내면

- 한 세션의 문제 중 작업 분담으로 개선할 수 있는 것과 먼저 해결해야 할 것을 구분할 수 있습니다.
- 입력 자료와 작업 기록, 편집 폴더, 담당 역할을 별도로 정하는 이유를 설명할 수 있습니다.
- 작업 분담 전에 기준선 네 항목을 기록하는 이유를 설명할 수 있습니다.
