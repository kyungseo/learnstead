# 04. 병렬은 언제 실제로 빠른가 — worktree와 파일 소유권

> 이전 ← [`03-subagent-anatomy.md`](03-subagent-anatomy.md) · 다음 → [`05-plan-execute-review.md`](05-plan-execute-review.md)

## 이 장에서 답하는 질문

- subagent 여러 개를 동시에 띄우면 전체 시간이 실제로 줄어드는가
- 두 subagent가 같은 파일을 고치면 무슨 일이 생기고, worktree는 무엇을 해결하고 무엇을 미루는가
- Codex CLI처럼 subagent worktree가 없는 도구에서는 어떻게 하는가

## 1. worktree로 작업 폴더를 따로 두기

worktree는 같은 저장소를 별도 폴더에 체크아웃해 작업하는 Git 기능입니다. 각 에이전트가 자기 폴더에서 편집할 수 있지만, 완료된 변경은 나중에 통합해야 합니다. [Git 가이드 07](../../guides/git-for-vibe-coders/07-worktrees.md)이 worktree의 개념·생성·정리와 "AI 세션 하나에 worktree 하나와 branch 하나"를 실행 검증까지 마쳤습니다. 이 장은 그 위에서 두 가지만 더합니다. 코딩 에이전트가 **subagent 단위로** worktree를 자동으로 만들 때의 규칙, 그리고 병렬이 끝난 뒤 **합치는 비용입니다**. `[원리]`

## 2. 병렬의 두 층 — 스레드와 계산

[코드 레벨 가이드의 실습 02](../../labs/when-splitting-fails/02-orchestrator-workers.md)는 로컬 모델 워커 셋을 스레드로 동시에 띄웠는데 순차보다 빠르지 않았습니다. 워커별 완료 시간에 차이가 있었지만, 그 기록만으로 서버가 계산을 하나씩 처리했다고 단정할 수는 없습니다. 코딩 에이전트의 subagent도 각자 API를 호출하지만, 서버가 요청을 처리하는 방식과 계정 한도에 영향을 받습니다. 로컬 서버의 결과를 그대로 적용할 수는 없으며 다음 병목도 확인해야 합니다.

| 병목 | 어디서 | 신호 |
| --- | --- | --- |
| 도구 실행 | 같은 checkout에서 테스트·빌드를 동시에 돌리면 파일·포트가 겹친다 | 한 subagent의 테스트가 다른 subagent의 미완성 편집 때문에 실패 |
| 메인의 대기 | 최종 취합에 필요한 모든 결과를 기다리는 구성 | 가장 늦게 끝난 작업을 기다린 뒤에야 결과 취합을 시작할 수 있음 |
| 요청 한도 | 계정의 분당 요청·토큰 한도 | 429 재시도로 벽시계가 늘어남 |

따라서 **동시에 실행했는지와 전체 시간이 줄었는지는 별개입니다.** 실행 구간의 겹침으로 동시성을 확인하고, 순차 대조로 시간 절감 효과를 확인합니다. `[해석]`

## 3. 실측 — 독립 과제 셋, 동시 vs 순차

서로 다른 파일을 고치는 과제 세 개(`parse.py`·`store.py`·`cli.py`, 각각 테스트 추가)를 `implementer` subagent 셋에게 동시에 맡긴 경우와 하나씩 순서대로 맡긴 경우입니다. 3회 중앙값. `[실행 검증 · 실습 03]`

| 도구 | 구성 | 벽시계 | 메인 컨텍스트(끝) | 메인 누적 입력 | 위임 누적 입력 | 테스트 |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Code (Opus 5) | 동시 3 | 150초 | 35,155 | 73,985 | 373,573 | 통과 3/3 |
| Claude Code (Opus 5) | 순차 | 256초 | 35,418 | 234,678 | 260,755 | 통과 3/3 |
| Codex | 동시 3 | 223초 | 24,646 | 282,832 | 398,951 | 통과 2/3 |
| Codex | 순차 | 344초 | 28,651 | 462,757 | 455,401 | 통과 3/3 |

동시 3이 순차의 0.6~0.65배 시간이었습니다. 이번에는 실제로 겹쳤습니다. Claude Code의 subagent transcript 시각을 보면 세 subagent가 9~13초 간격으로 시작해 구간이 겹쳤고, 순차 실행에서는 앞의 것이 끝난 뒤 다음이 시작했습니다. 시간 절감 폭에는 [2절](#2-병렬의-두-층--스레드와-계산)의 대기와 조정 비용이 영향을 줄 수 있습니다. 메인은 가장 느린 subagent(테스트 추가가 큰 과제 C)를 기다리고, 그 사이 완료 알림을 처리하는 턴을 씁니다. Claude Code의 메인 누적 입력은 순차가 약 3배였고, Codex는 약 1.6배였습니다. 순차 실행이 앞 결과를 다음 위임에 다시 싣는 점은 차이를 설명할 한 요인이지만, 호출 횟수와 캐시 영향까지 분리해 측정한 것은 아닙니다.

Codex 동시 3에서 테스트가 실패한 1회는 원인을 따로 확인했습니다. subagent C가 규격 기준으로 `--json` 출력 테스트를 썼는데, 심어 둔 `parse_amount`의 부호 결함 때문에 합계가 양수로 나와 실패했습니다. 기록상 실패 원인은 fixture에 심어 둔 결함입니다. 그래도 병렬 조건이 세 번 모두 검증을 통과한 것은 아니므로, 시간을 줄였다는 결과와 품질 확인 결과를 함께 남깁니다. `[해석]`

## 4. 같은 파일 — 격리 없이, 그리고 worktree로

같은 함수(`report.py`의 `render`)에 서로 다른 인자를 추가하는 과제 X·Y를 두 subagent에게 동시에 맡깁니다. 격리가 없으면 둘 다 같은 파일을 읽고 각자의 편집을 씁니다. `[실행 검증 · 실습 03]`

| 도구 | 격리 | 최종 파일에 두 기능이 | 테스트 | 메인이 한 일 | 벽시계 |
| --- | --- | --- | --- | --- | --- |
| Claude Code (Opus 5) | 없음(같은 checkout) | 3/3 모두 있음 | 통과 3/3 | 두 subagent가 편집 직전 파일을 다시 읽고 상대 변경 위에 자기 것을 덧붙였다고 보고 | 170초 |
| Claude Code (Opus 5) | `isolation: worktree` | **1/3** (2회는 메인 트리가 baseline 그대로) | 통과(변경 없음 포함) | 2회는 "각자 worktree에 커밋되지 않은 채 남았다"고 보고하고 끝냄. 1회는 두 worktree의 변경을 메인으로 옮겨 16개 테스트 통과 | 211초 |
| Codex | 없음(같은 checkout) | 3/3 모두 있음 | 통과 3/3 | 취합 없이 최종 파일 확인 | 194초 |
| Codex | `git worktree add` 둘 + `codex exec` 둘 | 각 worktree에 하나씩 | 기존 runner는 merge 시도 후 메인만 검사 | merge 시 `report.py` content conflict 3/3 | 72초(편집 실행만) |

격리 없이 같은 함수를 고친 두 subagent가 **여섯 번 모두 서로를 덮어쓰지 않았습니다.** 일부 실행 보고에는 편집 직전 다시 읽거나 작은 범위를 치환해 상대 변경을 보존했다는 설명이 있었습니다. 이것만으로 여섯 실행의 원인을 모두 입증하거나 동시 쓰기가 안전하다고 결론 낼 수는 없습니다. 이것은 "덮어쓰기가 없다"는 보장이 아니라 이 규모(함수 하나, 인자 하나씩)에서의 관측입니다. `[해석]`

worktree는 반대 방향으로 실패했습니다. 두 subagent는 각자 잘 끝냈지만 결과가 `.claude/worktrees/` 아래 두 branch에 남았고, 메인은 3회 중 2회 그것을 합치지 않은 채 "합쳐지지 않았다"고 보고하고 끝났습니다. 격리는 덮어쓰기를 막는 대신 **합치는 일을 메인(또는 사람)에게 남깁니다.** Codex의 worktree 둘은 그 일을 `git merge`로 미뤘고 3회 모두 같은 함수에서 충돌했습니다. Git 가이드 07이 "worktree는 충돌을 없애지 않습니다"라고 적은 그대로입니다. 같은 파일을 병렬로 고칠 계획이라면 격리와 함께 정할 것은 "누가 합치는가"입니다. `[해석]`

Codex의 72초는 두 편집 프로세스가 끝날 때까지이며, worktree 생성·커밋·merge·최종 검사를 포함하지 않습니다. 기존 기록에는 통합 완료 시간이 없으므로 이 값으로 격리 유무의 총 작업 시간을 비교하지 않습니다. 실습 runner는 후속 실행부터 편집·통합 시도·전체 시간을 따로 기록합니다. merge 충돌 상태는 전체 시간이 기록돼도 통합 완료로 세지 않습니다.

같은 폴더에서 변경이 보존된 관측과 별개로, 병렬 쓰기를 운영할 때는 **별도 branch·worktree, 겹치지 않는 쓰기 범위, 최종 통합 담당자**를 먼저 정합니다. worktree는 작업 폴더를 분리하는 장치이며, 외부 서비스·공유 자원까지 분리하는 sandbox를 뜻하지 않습니다. `[해석]`

## 5. subagent worktree의 규칙 — Claude Code

| 규칙 | 내용 | 함정 |
| --- | --- | --- |
| 위치·branch | `.claude/worktrees/<이름>/`, branch `worktree-<이름>` | `.gitignore`에 `.claude/worktrees/` 추가 |
| **base** | 기본은 **원격 default branch**(`worktree.baseRef: "fresh"`) | 내 feature branch의 커밋 위에서 돌리려면 `"head"`로 바꿔야 한다(현재 HEAD의 커밋 상태와 미푸시 커밋을 가져옴). **미커밋 변경은 어느 쪽이든 넘어가지 않는다.** 먼저 커밋해야 subagent가 본다 |
| 격리 강제 | 메인 checkout 편집·`git -C`·`GIT_DIR` 우회를 도구 호출 단계에서 거부 | subagent가 "메인을 고치라"는 지시를 받아도 못 한다 |
| 정리 | 변경 없으면 자동 삭제, 있으면 남기고 잠금. 주기적 sweep | 남은 worktree를 메인이 합쳐야 결과가 된다 |
| 환경 | 새 checkout이라 `.env` 같은 무시 파일이 없다 | `.worktreeinclude`에 나열 |

agent teams는 teammate를 worktree로 격리하지 않습니다. 사람이 에이전트별 담당 파일 범위를 정해야 합니다. Codex CLI는 subagent worktree가 없고, 데스크톱 앱의 worktree는 대화 단위입니다. CLI에서 병렬 편집이 필요하면 `git worktree add`로 폴더를 만들고 `codex exec --cd`를 폴더마다 띄웁니다. `[문서 확인 · 2026-09-06]`

## 6. 담당 파일 범위와 통합 담당자를 함께 정하기

worktree를 쓰든 안 쓰든, 병렬 과제에서는 **각 에이전트가 수정할 파일 범위를 겹치지 않게 정하는 것이** 먼저입니다. 이 문서에서 말하는 파일 소유권은 이러한 작업별 수정 범위를 뜻합니다. 작업 폴더를 나눠도 쓰기 범위가 겹치면 통합 충돌이 남고, 같은 폴더에서는 상대 변경을 덮어쓸 위험이 있습니다. [바이브 코딩 가이드 04](../../guides/vibe-coding-practice/04-one-at-a-time.md)의 "한 요청 = 한 가지 변화"가 병렬에서는 "한 subagent = 한 파일 집합"이 됩니다. 수정 범위를 구분하기 어렵다면 순차로 처리합니다. `[해석]`

## 이 장을 끝내면

- 병렬이 실제로 시간을 줄였는지 순차 대조로 판정할 수 있습니다.
- subagent worktree가 해결하는 것(덮어쓰기)과 미루는 것(merge)을 구분할 수 있습니다.
- Claude Code의 base branch 기본값과 Codex CLI의 대안을 알고 병렬 과제마다 담당 파일 범위를 정할 수 있습니다.
