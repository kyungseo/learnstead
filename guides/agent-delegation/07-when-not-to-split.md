# 07. 작업을 맡길지 결정하기 — 목적·품질·통합 비용

> 이전 ← [`06-failure-map.md`](06-failure-map.md) · 다음 → [`08-glossary.md`](08-glossary.md)

## 이 장에서 답하는 질문

- 어느 작업을 직접 하고 어느 작업을 맡길 것인가
- 작은 실험 결과를 내 프로젝트에 어떻게 적용할 것인가
- 유지·보완 후 재측정·되돌림을 무엇으로 판단할 것인가

## 1. 다섯 질문

한 세션으로 충분하면 그대로 진행합니다. 별도 에이전트에게 맡길 이유가 있으면 다음 순서로 범위와 확인 방법을 정합니다. 아래는 도구의 강제 규칙이 아니라 이 가이드의 판단 절차입니다. `[해석]`

| 순서 | 질문 | 다음 행동 |
| --- | --- | --- |
| 1 | 지금 무엇을 개선하려는가? | 컨텍스트 부담·완료 시간·검토 관점 등 목표를 정합니다. 요구사항이나 자료가 부족하다면 먼저 보완합니다. |
| 2 | 독립적으로 맡길 범위와 완료 조건을 적을 수 있는가? | 어렵다면 직접 처리하거나 과제를 더 작게 나눕니다. 가능하면 대상·제약·보고 형식을 적습니다. |
| 3 | 각 에이전트에게 어떤 자료와 작업 폴더를 제공할 것인가? | 필요한 이력만 전달합니다. 병렬 쓰기는 별도 branch·worktree와 겹치지 않는 쓰기 범위를 정합니다. |
| 4 | 누가 결과를 확인하고 통합하는가? | 담당자를 정하고 원문·변경·검사 결과를 확인합니다. 검토라면 규격과 제안의 범위를 구분합니다. |
| 5 | 직접 처리한 기준선보다 나아졌는가? | 목표 지표뿐 아니라 결과 품질과 통합까지 비교해 유지·보완·되돌림을 결정합니다. |

읽기 위임의 손익이 갈리는 토큰 수는 과제·지시문·결과 길이·모델에 따라 다릅니다. 이 실습의 파일 5개 결과를 “수천이면 직접, 수만이면 위임”이라는 고정 기준으로 쓰지 않습니다. 팀·스크립트는 [02장](02-layers-of-splitting.md)의 조정 요구가 생겼을 때 별도로 검토합니다.

## 2. 먼저 보완해야 할 신호

| 신호 | 필요한 보완 |
| --- | --- |
| “여러 개면 더 잘할 것 같아서” | 개선할 문제를 먼저 정합니다. |
| 읽을 것이 파일 몇 개이고 결과도 길다 | 작은 과제 하나로 직접 읽을 때와 위임할 때의 시간·입력량을 비교합니다. |
| 과제가 같은 파일·같은 함수에 몰려 있다 | 쓰기 범위를 다시 나눕니다. 나누기 어렵다면 순차로 처리합니다. |
| 검토 기준을 설명하기 어렵다 | 요구사항과 검토 목적을 먼저 정합니다. |
| 기준선이나 결과 기록이 없다 | 아직 성능·품질 개선을 주장하지 않고 비교 자료부터 남깁니다. |
| 미커밋 변경 위에서 subagent worktree를 만들려 한다 | worktree의 시작 커밋과 필요한 변경의 전달 방법을 확인합니다([04 §5](04-parallel-and-worktrees.md)). |

## 3. 실측 종합

다음은 2026-09-06~07 작성 환경의 기록입니다. 두 도구에서 각 3회 실행했으며, 시간·토큰은 중앙값입니다. 자동 점수는 **결함 위치 일치**이고, 지적의 정확성은 별도 확인이 필요합니다. 작은 과제의 관측이므로 그대로 다른 저장소에 일반화하지 않습니다. 자세한 수집 방식은 실습 [VALIDATION](../../labs/delegate-and-verify/VALIDATION.md)에 있습니다.

| 비교 | 관측 | 이 결과로 판단할 수 있는 범위 |
| --- | --- | --- |
| 직접 검토 vs 위임 (03) | 메인 마지막 컨텍스트 Claude −3%·Codex −7%, 위임 입력 각각 2.9만·13만, 위치 일치 동일 | 이번 작은 읽기에서는 컨텍스트 절감이 작고 전체 입력량은 늘었음 |
| 이력 의존 vs 자기완결 위임 (03) | Claude 수정 1/3 vs 3/3. Codex는 둘 다 3/3, 자기완결 조건의 메인 입력·시간 약 40% 감소 | 명확한 요청이 유리했지만 차이 전부를 이력 복제 비용으로 설명하지는 못함 |
| 병렬 vs 순차 (04) | Claude 150초 vs 256초, Codex 223초 vs 344초. Codex 병렬은 테스트 2/3 통과 | 기록한 실행 시간은 줄었음. 품질·최종 완료도 함께 확인해야 함 |
| 같은 파일, 격리 없음 vs worktree (04) | 공유 폴더는 여섯 실행 모두 변경 보존. Claude worktree는 통합 1/3, Codex는 merge 충돌 3/3 | 공유 폴더 쓰기의 안전성을 입증한 것은 아님. 격리와 통합 계획이 모두 필요 |
| 같은 세션 vs 새 컨텍스트 검토 (05) | 모두 규격 위반 발견 3/3. 같은 세션의 시간이 짧았고 Codex 입력 토큰은 새 세션이 적었음 | 위반 발견 차이는 미관측. 토큰·시간·청구 금액은 구분 |
| 결함만 vs 모든 개선점 (05) | 위치 일치 동일, 넓은 요청에서 골든셋 밖 지적 16~28건 | 요청 범위에 따라 지적량이 달라졌음. 오탐률은 측정하지 않음 |

## 4. 유지·보완·되돌림

목적에 해당하는 항목만 확인합니다. 하나의 수치로 모든 구성을 판정하지 않습니다.

- **컨텍스트 부담을 줄이려 했다면:** 메인이 직접 처리할 때보다 입력 크기가 줄었는지 보고, 누적 입력량이 늘어난 대가도 확인합니다. 마지막 크기만 쟀다면 작업 중 최대 크기는 모른다고 남깁니다.
- **시간을 줄이려 했다면:** 실행이 겹쳤는지와 전체 시간이 줄었는지를 따로 확인합니다. 편집·통합·검사의 끝 지점이 같은 비교인지 봅니다.
- **검토 관점을 넓히려 했다면:** 기준에 맞는 문제를 발견했는지 원문으로 확인합니다. 새 컨텍스트를 썼다는 사실이나 지적 수 자체를 효과로 세지 않습니다.
- **공통:** 요구한 기능이 최종 결과에 남았는지, 검사가 무엇을 확인했는지, 미완료 작업을 누가 맡는지 확인합니다.

목표 지표가 개선되고 품질·통합 조건도 충족하면 **유지**, 효과가 불분명하거나 실험 조건이 다르면 **보완 후 재측정**, 부담만 늘거나 현재 작업을 안전하게 마무리할 수 없으면 **되돌림**으로 기록합니다. 작은 요청은 직접 처리하고, 필요성이 분명해진 부분부터 맡기면 됩니다.

## 이 장을 끝내면

- 다섯 질문으로 맡길 범위와 확인 방법을 정할 수 있습니다.
- 측정값·관측·일반적인 권고를 구분할 수 있습니다.
- 목적별로 유지·보완 후 재측정·되돌림을 판단할 수 있습니다.
