# ORCHESTRATION-CARD — 내 오케스트레이션 카드

**어떤 작업을 분담할지(Split), 각 역할에 어떤 자료를 전달할지(Isolate), 언제 실행을 멈출지(Stop)를** 한 장에 기록하는 양식입니다. 구성을 바꿀 때마다 복사해 씁니다.

← [가이드 README](README.md) · 다음 → [01 왜 하나로는 안 되는가](01-why-more-than-one.md)

---

## 기록 원칙

- **기준선(단일 호출) 숫자를 먼저 적습니다.** 이게 없으면 나아졌는지 알 수 없습니다.
- 프롬프트 전문 대신 **한 줄 요약과** 토큰 수를 적습니다.
- 구성을 바꿀 때는 **한 번에 하나만** 바꾸고 같은 질문 묶음으로 다시 잽니다.

## 복사해서 쓰는 template

```md
# 오케스트레이션 카드 — <구성 이름>

## 기준선 (단일 호출)

- 호출 1회 · 입력 __ 토큰 · 출력 __ 토큰 · __ 초
- 질문 묶음 __개 중 정답 __개

## Split — 어떤 작업을 왜 분담하는가

- 현재 방식의 한계: (컨텍스트 초과 / 동시 처리 필요 / 권한·역할 분리)
- 고른 패턴: (파이프라인 / 라우터 / 워커 / 평가 루프 / 여러 패턴 조합)
- 단계와 각 단계의 역할:

## Isolate — 각 역할에 어떤 자료를 전달하는가

| 단계 | 보는 것 | 입력 토큰 |
| --- | --- | --- |
|  |  |  |

- 입력 경계를 코드·전달 자료로 확인했는가: 예 / 아니오
- 합계 입력 토큰: ___ (기준선 대비 ↑/↓)
- 결과를 취합하는 단계에서 워커가 읽은 원문을 다시 보는가: 예 / 아니오

## Stop — 언제 멈추는가

- 호출 수 상한 / 시간 상한 / 토큰 중단 기준:
- 토큰 기준: 호출 전 추정 / 응답 후 집계, 진행 중 호출 초과 가능 여부:
- 상한 도달 시 반환하는 것:
- 폴백 경로: (단일 호출로 되돌아가기 / 부분 결과 / 오류)
- 사람이 개입하는 지점:

## Prove — 나아졌는가

- 정확도: 기준선 __ → 현재 __
- 입력 토큰: 기준선 __ → 현재 __
- 시간: 기준선 __ → 현재 __
- 단계별 로그가 있는가: 예 / 아니오
- **결론: 유지 / 수정 후 재측정 / 되돌림**

## 한계와 다음 조치

- 아직 확인 안 한 것:
- 다음에 바꿔 볼 한 가지:
```

## 가장 짧은 예시

실습 구성을 적은 예시입니다. `[실행 검증 · 2026-08-30]`

| 항목 | 기록 |
| --- | --- |
| 기준선 | 단일 1회 · 입력 508 · 출력 19 · 0.6초 · 정답 |
| Split | 컨텍스트를 좁히려고 → 파이프라인(분류·답변·다듬기) |
| Isolate | 분류 67 / 답변 234(문서 1편) / 다듬기 64 = **365** (기준선 대비 ↓) |
| Stop | 정상 경로 3단계 · 분류 파싱 실패 시 단일 호출로 폴백 |
| Prove | 정확도 동일, 토큰 −28%, 시간 +0.5초 → **유지** |
| 비교 | 라우터는 8문항 중 4개 오분류(정확도 0.50) → **되돌림**. 폴백을 붙여도 평균 비용이 단일보다 큼 |
