# 여러 AI를 엮어 일하게 하기 — Agent와 오케스트레이션

![사람이 순서·분기·검토를 나타내는 카드로 로봇들의 작업 흐름을 구성하는 손그림](assets/agent-orchestration-hero.webp)

> "AI를 여러 개 붙이면 더 똑똑해진다"는 말을 같은 질문·같은 모델·같은 문서 3편으로 직접 검증한 결과 위에 선 가이드입니다. 단일 호출·파이프라인·라우터·오케스트레이터-워커·평가 루프 다섯 방식을 돌려 호출 수·토큰·시간·정답을 나란히 비교했더니 **셋만 깨끗한 정답을 냈고, 라우터는 나누는 판단 자체가 틀렸으며, 워커는 없는 말을 섞었습니다.** 정답을 유지하면서 토큰이 준 구성은 파이프라인이었습니다. 라우터도 토큰은 적었지만 답이 틀렸습니다. 나누기는 최적화이고, 최적화는 측정한 뒤에 합니다.

## 먼저 보는 큰 그림

이 가이드는 **내 코드가** 모델을 여러 번 부르는 이야기입니다. 코딩 에이전트 runtime이 제공하는 subagent·worktree·검토 루프로 나누는 이야기는 짝이 되는 가이드가 맡습니다.

| 앞선 가이드 | 이 가이드에서 맡는 자리 |
| --- | --- |
| [Local LLM 앱 연결 06](../../guides/local-llm-app-integration/06-tool-calling-workflow-agent.md) — tool calling·workflow·agent, 누가 제어 흐름을 쥐는가 | 거기서 만든 "도구 쓰는 agent 하나"를 여러 개로 늘릴 때 무엇이 좋아지고 나빠지는가 |
| [RAG 가이드 05](../../guides/local-rag/05-chunking-and-retrieval-quality.md) — 잡음이 답을 흐린다 | 같은 문제를 "덜 넣기"로 푸는 다른 길: 컨텍스트 격리 |
| [Context Engineering 05](../../guides/context-engineering/05-budget-and-compaction.md) — 큰 읽기는 서브에이전트로 | 그 원리를 코드 레벨에서 토큰 수로 확인 |
| [나눠 맡기는 법](../../guides/agent-delegation/README.md) — 코딩 에이전트 안의 subagent·병렬·검토 | 같은 다섯 질문·같은 실패 지도를 도구 안에서 다시 잼. 두 가이드는 한 시리즈 |

이 실습에서 비교할 다섯 방식입니다. 전체 패턴 목록은 아니며, 워커는 코드가 미리 정한 문서별 작업을 실행합니다. `[코드 확인 · 2026-09-07]`

```text
① 단일           [질문] ──────────────▶ [LLM(문서 전부)] ──▶ 답
② 파이프라인     [질문] ─▶ 분류 ─▶ 답변 ─▶ 다듬기 ─▶ 답            순서를 내 코드가 고정
③ 라우터         [질문] ─▶ 분류 ─┬─▶ 휴가 담당 ─▶ 답               담당만 자기 문서를 봄
                                 ├─▶ 장비 담당
                                 └─▶ 총무 담당
④ 오케스트레이터 [요청] ─▶ 오케스트레이터 ─┬─▶ 워커A ─┐            워커가 병렬(runtime이 허락하면), 각자 좁은 컨텍스트
   -워커                                  ├─▶ 워커B ─┼─▶ 취합 ─▶ 답
                                          └─▶ 워커C ─┘
⑤ 평가-개선      [요청] ─▶ 작성 ─▶ 평가 ─(불합격)─▶ 재작성 ─▶ …    통과하거나 상한까지
```

## 학습 달성 목표(Learning Objective)

이 가이드를 끝내면:

- 네 가지 오케스트레이션 패턴(파이프라인·라우터·오케스트레이터-워커·평가 루프)을 그림과 코드로 구분할 수 있습니다.
- 각 호출이 받는 정보와 전체 토큰 비용을 구분해 확인할 수 있습니다.
- 같은 과제를 여러 패턴으로 돌려 호출 수·토큰·정확도를 비교하고 근거를 대며 고를 수 있습니다.
- 다섯 가지 실패 모드를 알아보고 각각에 로그·상한·폴백을 붙일 수 있습니다.
- "이건 멀티가 아니라 단일로 충분하다"를 판단할 수 있습니다. 이 가이드에서 가장 자주 쓰게 될 판단입니다.

## 누구를 위한 가이드인가

- Local LLM을 프로그램에서 부르고 구조화 출력·tool calling을 써 본 사람. 앱 연결 가이드 06~08이 전제입니다.
- "여러 agent로 나누면 좋아진다"는 말을 들었고, 정말 그런지 자기 과제에서 확인하고 싶은 사람.
- 이미 나눠 놓았는데 토큰이 늘거나 답이 이상해진 사람. [04](04-failure-modes.md)와 [05](05-when-not-to.md)부터 읽어도 됩니다.

필요한 배경은 Python으로 API를 부르는 정도입니다. 프레임워크는 쓰지 않습니다.

## 가이드 작성 중 직접 확인한 검증 기록

작성 환경: Apple M4 Pro·24GB Mac, Ollama 0.33.0, `gemma3:4b`(temperature 0), 2026-08-30. 상세는 [`VALIDATION.md`](VALIDATION.md)와 실습 [검증 기록](../../labs/when-splitting-fails/VALIDATION.md).

- 같은 질문에 단일 508 / 파이프라인 365 / 라우터 268 / 워커 782 / 루프 1,043 입력 토큰. 호출 수와 토큰은 따로 움직였습니다.
- 라우터가 8문항 중 4개를 잘못 보냈습니다. 기준 질문조차 `reason`에 "연차 관련 문의"라고 적고 회의실 담당에게. 3회 반복해도 같았습니다. (실습 01 §3)
- 병렬로 돌린 워커가 순차보다 빠르지 않았습니다. 워커 시간이 2.0/3.5/5.2초로 계단을 이뤘고 순차는 3.9초. 서버가 하나씩 처리하고 있었습니다. (실습 02 §3)
- 취합 단계가 워커의 답을 뒤집었습니다. "15분 이내에 입실하지 않으면 자동 취소"가 "15분 내 입실해야 자동 취소"로. (실습 02 §2)
- 평가-개선 루프가 수렴하지 않았습니다. 평가자가 매 라운드 다른 말로 지적해 상한 3회에 걸렸고 토큰은 8.5배. "같은 지적이면 멈추기"는 발동하지 않았고 토큰 예산만 발동했습니다. (실습 03 §3·§4)

## 검증 표기

| 표기 | 뜻 |
| --- | --- |
| `원리` | 특정 제품 version보다 오래 유지되는 구조·수학·물리 설명 |
| `실행 검증 · YYYY-MM-DD` | 기록한 환경에서 명령과 성공 조건을 실제로 확인함 |
| `부분 검증 · YYYY-MM-DD` | 명시한 단계만 실제로 확인함 |
| `문서 확인 · YYYY-MM-DD` | 공식 문서나 발표를 확인했지만 직접 실행하지는 않음 |
| `자료 확인 · YYYY-MM-DD` | 공개 자료를 확인했지만 1차 출처나 직접 실행으로 확정하지 못함 |
| `미검증` | 아직 직접 확인하지 못함 |
| `해석` | 근거를 바탕으로 저자가 정리한 판단 |

각 표기의 근거는 [출처](SOURCES.md)와 [검증 기록](VALIDATION.md)에 연결합니다. 프레임워크와 패턴 이름은 빠르게 바뀌므로 확인일이 오래됐다면 공식 문서를 다시 확인하세요.
