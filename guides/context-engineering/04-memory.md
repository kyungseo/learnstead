# 04. memory — 세션을 넘어 남는 것

> 이전 ← [`03-always-vs-conditional.md`](03-always-vs-conditional.md) · 다음 → [`05-budget-and-compaction.md`](05-budget-and-compaction.md)

## 이 장에서 답하는 질문

- 지시문과 memory는 무엇이 다른가
- Claude Code와 Codex의 local memory는 무엇을 어디에 저장하고 언제 읽는가
- 무엇을 memory에 두지 말아야 하는가

## 1. 지시문 vs memory

두 도구의 문서를 기준으로 구분하면 다음과 같다 [문서 확인 · 2026-09-02].

| | 지시문 (`CLAUDE.md`·`AGENTS.md`) | local memory |
| --- | --- | --- |
| 누가 쓰나 | 사람 | 모델 |
| 내용 | 규칙·관례·명령 | 배운 것·교정·선호·코드에서 못 읽는 프로젝트 맥락 |
| 범위 | 프로젝트·사용자·조직 | 저장소별(worktree 공유), 장비 로컬 |
| 로드 | 매 세션 전체 또는 제품의 문서 한도까지 | 색인을 먼저 보고 주제 파일은 필요할 때 |

둘 다 **컨텍스트이지 강제 수단은 아닙니다.** 차이는 저자와 수명입니다. 지시문은 팀이 합의해 git에 넣는 것이고, memory는 에이전트가 작업에서 배운 것을 사용자 장비에 남깁니다.

Claude Code의 auto memory는 기본 제공됩니다. Codex의 local memory는 2026-09-02 현재 기본값이 꺼진 opt-in 기능이며 `~/.codex/memories`에 저장되고 `/memories`에서 관리합니다 [문서 확인]. 기능의 기본값과 세부 동작은 바뀔 수 있으므로 현재 설정을 확인합니다.

## 2. Claude Code auto memory의 구조 [문서 확인]

```text
~/.claude/projects/<프로젝트>/memory/
├── MEMORY.md            ← 색인. 한 줄에 하나. 매 세션 앞 200줄/25 KB만 로드
├── user_role.md         ← 주제 파일. 시작 시 로드하지 않고 필요할 때 읽음
├── feedback_testing.md
└── …
```

- 네 종류: `user`(역할·선호), `feedback`(교정·확인된 접근), `project`(코드·git에서 못 읽는 진행 상황·결정), `reference`(외부 위치).
- 문서가 제시하는 원칙상, 모델은 **코드에서 읽어 낼 수 있는 것**(구조·경로·버그 수정)과 **지시문이 이미 말하는 것은** 저장 대상에서 제외합니다.
- `MEMORY.md`가 한계에 가까우면 도구가 줄이라고 알리고, 넘으면 쓰기는 되지만 다음 로드에서 잘립니다.
- 서브에이전트는 메인 세션의 memory를 받지 않는다(fork 제외). 서브에이전트 자체의 memory는 별도.
- `/memory`로 확인하고 편집·삭제할 수 있으며, 설정 `autoMemoryEnabled: false` 또는 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`로 끕니다.

Codex local memory도 색인과 세부 기록을 분리합니다. 다만 기능이 꺼져 있으면 아무것도 기록하거나 주입하지 않습니다. 켜기 전에 저장되는 내용과 팀 정책을 먼저 확인합니다.

이 가이드를 만든 세션의 장비에도 이 디렉터리가 있었고 `MEMORY.md`에 사용자 선호 한 줄이 있었습니다 [실행 검증 · 존재 확인]. 즉 "매 세션 시작 시 모델이 이미 나에 대해 아는 것"이 여기에 있습니다.

## 3. 무엇을 두지 말아야 하나

memory는 편리하지만 세 가지 위험이 있습니다.

| 위험 | 이유 | 대응 |
| --- | --- | --- |
| **지시문과 memory의 중복·충돌** | 같은 규칙이 두 곳에 있고 한쪽만 바뀌면 모델이 임의로 고른다 | 규칙은 지시문에만. memory는 "왜"와 선호 |
| **운영 규칙의 memory 유출** | 팀 규칙이 한 사람 장비의 memory에만 있으면 다른 사람·다른 도구는 모른다. 그리고 지시문만으로 동작이 유도되는지 검증할 수 없게 된다 | 저장소가 소유해야 할 것은 지시문·Skill로. memory는 개인 것만 |
| **낡은 사실** | memory는 쓴 시점의 사실. 파일·함수 이름이 바뀌면 틀린 지시가 된다 | `modified` 시각을 보고, 추천 전에 존재 여부를 확인. 주기적으로 `/memory` 감사 |

Anthropic 글의 "structured note-taking"(에이전트가 `NOTES.md` 같은 외부 파일에 진행 상황을 적고 컨텍스트 리셋 뒤 이어 감)도 같은 원리입니다 [자료 확인]. 기억을 컨텍스트 밖 파일에 두고 필요할 때 읽습니다. auto memory는 그것을 도구가 대신해 주는 것이며, **무엇이 남는지는 사람이 감사해야 합니다.**

## 4. 사람이 쓰는 memory — 작업 문서

지시문도 auto memory도 아닌 세 번째 자리가 있습니다. 진행 중인 작업의 상태·결정·다음 할 일을 저장소 안 문서로 두는 것입니다. 이 가이드를 만든 저장소는 상태 대시보드 한 파일과 작업 단위 파일을 그렇게 씁니다. 특징:

- **저장소가 소유합니다.** 사람도 도구도 읽으며 git 이력이 남습니다.
- 진입 지시문은 "세션 시작 시 그 파일의 현재 절만 읽어라"라고 **가리킵니다.** 항상 로드하지는 않습니다.
- 압축·세션 종료를 넘어 살아남는 유일한 층이다(5장).

세 층을 나란히 두면:

| | 지시문 | local memory | 작업 문서 |
| --- | --- | --- | --- |
| 저자 | 사람 | 모델 | 사람 + 모델 |
| 소유 | 저장소 | 장비 | 저장소 |
| 내용 | 규칙 | 선호·교정 | 상태·결정·다음 |
| 로드 | 항상 | 색인만 항상 | 지시문이 가리킬 때 |

## 이 장을 끝내면

- 지시문·local memory·작업 문서를 저자·소유·로드로 구분합니다.
- auto memory의 로드 한계(200줄/25 KB)와 감사 방법을 설명할 수 있습니다.
- 팀 규칙을 memory에 두지 않는 이유를 말할 수 있습니다.
