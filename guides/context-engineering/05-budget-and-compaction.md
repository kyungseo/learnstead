## 이 장에서 답하는 질문

- 작업 중 컨텍스트는 무엇으로 채워지고 얼마나 드는가
- 압축(compaction)이 일어나면 각 층은 어떻게 되는가
- 큰 읽기·큰 출력을 어떻게 컨텍스트 밖으로 밀어내는가

## 1. 채우는 것은 지시문이 아니라 작업이다

실습의 한 실행(작은 함수 추가)에서 Claude Code가 쓴 토큰 [실행 검증 · 실습 05, 3회 평균]:

| 조건 | 턴 | 캐시 쓰기(시작 컨텍스트) | 캐시 읽기(누적) |
| --- | --- | --- | --- |
| 지시문 없음 | 6 | 13,891 | 120,497 |
| 짧은 지시문(10줄) | 4 | 13,766 | 83,727 |
| 긴 지시문(176줄) | 5 | 19,555 | 121,753 |

긴 지시문은 시작 컨텍스트를 약 6,000 토큰 늘렸습니다(12.5 KB 파일). 이 비교에서는 **턴 수와 누적 캐시 읽기에도 차이가 있었습니다.** 지시문이 없으면 모델이 관례를 찾아 파일을 더 읽었고, 그 읽기가 매 턴 다시 캐시에서 읽혔습니다. 다만 지시문 길이·턴 수·캐시 사용의 영향을 따로 분리한 실험은 아닙니다. 컨텍스트 예산을 정할 때는 지시문 길이뿐 아니라 **불필요한 탐색과 반복 입력도** 함께 확인합니다.

## 2. 무엇이 쌓이나 [문서 확인 · Claude Code 예시]

| 항목 | 대표 토큰 | 줄이는 방법 |
| --- | --- | --- |
| 파일 읽기 한 번 | 1,000~2,500 | 필요한 범위만(offset·limit), 검색으로 위치 먼저 |
| 명령 출력(테스트 등) | 1,200 | 요약 옵션, 실패만 출력 |
| 경로 조건 규칙 | 300~400 (읽는 파일이 매칭될 때) | 규칙을 짧게 |
| hook의 추가 컨텍스트 | 100~120 (매 이벤트) | 필요한 이벤트만 |
| MCP 도구 결과 | 상한 25,000 (경고 10,000) | 도구가 페이지네이션·요약 |
| 서브에이전트 | 결과 요약만 (예: 6,100 읽고 420 반환) | 큰 읽기를 위임 |
| 호출된 skill 본문 | 본문 크기 | 500줄 미만, 참조는 별도 파일 |

Anthropic 글의 표현으로는 **just-in-time retrieval**입니다. 전부 미리 넣지 않고 가벼운 식별자(경로·제목)만 둔 뒤 필요할 때 도구로 가져옵니다 [자료 확인]. 코딩 에이전트의 Read·Grep·MCP가 그 도구이고, [RAG](../local-rag/README.md)는 같은 원리를 문서 검색에 적용한 것입니다.

## 3. compaction — 무엇이 남는가

![압축 후 각 층의 운명 — 재주입(루트 지시문·memory·계획), 재읽기 시(경로 규칙·하위 지시문), 부분(읽은 파일 5개·skill 상한), 불확실(대화로만 준 지시·hook 컨텍스트)](diagrams/05-compaction-survival.svg)


컨텍스트가 한계에 가까워지면 도구가 대화를 요약으로 바꿉니다. Claude Code를 기준으로 각 층이 어떻게 처리되는지 살펴보겠습니다 [문서 확인 · 2.1.251].

| 층 | 압축 후 |
| --- | --- |
| system prompt | 그대로 (이력이 아님) |
| **루트 `CLAUDE.md`, `paths` 없는 규칙** | **디스크에서 다시 읽어 재주입** |
| auto memory | 디스크에서 재주입 |
| plan 모드의 계획 | 디스크에서 재주입 |
| `paths` 규칙, 하위 `CLAUDE.md` | 요약됨. 해당 파일을 다시 읽을 때 재로드 |
| 읽거나 고친 파일 | 최근 수정 5개까지 다시 읽음. 5,000 토큰 넘으면 경로만 |
| 호출된 skill 본문 | 재주입, skill당 5,000·합 25,000 토큰, 오래된 것부터 탈락 |
| hook이 넣은 컨텍스트 | 요약과 함께 사라짐 |
| **대화에서만 준 지시** | **요약에 남을 수도, 안 남을 수도** |

마지막 줄이 실무에서 가장 자주 문제가 됩니다. "이번 세션에서는 X 하지 마"라고 대화로만 말한 것은 압축 뒤 사라질 수 있습니다. 문서의 처방: **살아남아야 할 지시는 `CLAUDE.md`에 넣습니다.** 세션 중 지시문 파일을 고쳐도 되며, 압축 시 디스크에서 다시 읽습니다.

이 표는 Claude Code의 동작입니다. Codex의 compaction 세부 동작은 이 가이드에서 실행 검증하지 않았으므로 같은 방식이라고 가정하지 않는다 [미검증]. Codex local memory는 별도 opt-in 기능이며 compaction과 같은 개념이 아닙니다.

## 4. 압축을 다루는 손잡이 [문서 확인]

- `/compact <초점>` — 무엇을 남길지 지정해 미리 압축.
- `/autocompact <토큰>` — 자동 압축 시점을 앞당김.
- `/clear` — 관련 없는 작업으로 넘어갈 때 비웁니다. 오래된 대화는 다음 작업에 필요한 파일을 밀어냅니다.
- 큰 조사는 **서브에이전트로** — 읽기는 그쪽 컨텍스트에, 내 컨텍스트에는 요약만.
- `/context` — 현재 무엇이 얼마나 차지하는지, 어떤 지시문·memory가 로드됐는지.

## 5. 설계로 돌아오면

| 컨텍스트에 넣는 방식 | 압축 생존 | 비용 | 적합 |
| --- | --- | --- | --- |
| 루트 지시문 | 재주입 | 매 세션 | 짧은 규칙 |
| 경로 규칙·하위 지시문 | 재읽기 시 | 매칭 시 | 파일 종류별 규칙 |
| skill | 상한 안에서 재주입 | 호출 시 | 절차 |
| auto memory | 색인 재주입 | 매 세션 | 선호·교정 |
| 작업 문서(저장소) | 파일로 보존됨. 필요할 때 다시 읽기 | 읽을 때 | 상태·결정 |
| 대화 지시 | 불확실 | 대화 입력에 포함될 때 | 일회성 |

"압축 뒤에도 남아야 하는가"가 층을 고르는 마지막 기준입니다.

## 이 장을 끝내면

- 지시문 크기·탐색 턴·누적 입력량을 함께 비교하고, 각각의 영향을 분리해 측정하지 않은 한계를 설명할 수 있습니다.
- 압축 후 각 층의 운명을 표로 말할 수 있습니다.
- 대화로만 준 지시를 지시문 파일로 옮겨야 하는 이유를 설명할 수 있습니다.
