# 01. 저장 버튼을 눌렀는데, 어디에 저장됐을까?

<!-- learnstead:nav:start -->
[← 이전: 자료 소개](README.md) · [목차](README.md) · [다음: 02. 내 앱에는 어떤 DB가 필요할까?](02-choose-a-database.md)
<!-- learnstead:nav:end -->

스터디 모임에 참가할 사람이 이름을 입력하고 신청 버튼을 누르는 앱을 예로 들어보겠습니다. 이 가이드에서 데이터의 저장과 관리를 설명할 때 사용할 가상의 앱입니다. 지금 앱을 준비하거나 실행할 필요는 없습니다.

신청 버튼을 누르자 화면의 신청자 목록에 이름이 나타났다고 해 보겠습니다. 그러면 신청 정보가 저장된 걸까요?

화면에 이름이 보이더라도 새로고침하면 사라질 수 있고, 내 컴퓨터에서는 보이지만 다른 사람에게는 보이지 않을 수도 있습니다. 무엇이 다른지 이해하려면, 화면에 보이는 내용과 데이터가 실제로 보관되는 곳을 구분해야 합니다.

이 장에서는 **앱이 데이터를 어디에 보관하는지** 알아봅니다. DB에 명령을 보내는 언어인 SQL을 몰라도 읽을 수 있습니다. 이미 앱을 만들었다면 아래 예와 자신의 앱을 대조해 보세요.

## 화면, 프로그램, 저장소를 나누어 보기

신청자 목록에 같은 이름이 보이더라도, 프로그램이 그 이름을 처리한 방법은 다를 수 있습니다.

- 입력한 이름을 실행 중인 프로그램에만 잠시 보관하고 목록에 표시했을 수 있습니다. 프로그램이 종료되면 그 이름을 잃을 수 있습니다.
- 이름을 파일이나 DB에 기록한 뒤, 저장된 내용을 읽어서 목록에 표시했을 수 있습니다. 기록이 유지된다면 앱을 다시 열어도 불러올 수 있습니다.

그래서 화면에 이름이 나타났다는 사실만으로는 어디에 저장했는지, 다시 열었을 때도 남는지 알 수 없습니다. 여기서 **저장소는 데이터를 보관하는 곳을** 뜻합니다. DB(database, 데이터베이스)는 데이터를 정해진 구조로 저장하고 찾아 쓸 수 있게 모아 둔 것이고, DBMS는 그 저장과 조회를 처리하는 프로그램입니다. 일상에서는 둘을 묶어 ‘DB’라고도 부릅니다.

웹앱에서는 내 브라우저가 다른 컴퓨터의 프로그램에 저장이나 조회를 요청하기도 합니다. 이 요청을 처리하는 쪽을 서버라고 합니다. 아래 그림의 API는 프로그램끼리 이런 요청을 주고받는 접점이며, 04장에서 자세히 살펴봅니다.

![화면의 요청이 API와 DB로 이어지며 브라우저 저장소는 별도 경로임을 보여 주는 그림](diagrams/data-flow.svg)

| 위치 | 신청 내역을 담는 예 | 어디까지 기대할 수 있나 |
| --- | --- | --- |
| 프로그램 메모리 | 실행 중인 프로그램이 임시로 기억하는 신청 목록 | 프로그램이 종료되면 잃을 수 있음 |
| 브라우저 저장소 | 브라우저가 기기에 보관하는 데이터 (`localStorage`, IndexedDB) | 같은 브라우저 환경에 남을 수 있지만 다른 기기에 자동 공유되지 않음 |
| 로컬 파일 | JSON, CSV, SQLite 파일 | 파일이 유지되는 장치에 남음. 삭제·교체·저장장치 장애는 별도 문제 |
| 서버의 DB | PostgreSQL 등 | 여러 기기가 같은 서비스를 통해 접근 가능. 권한과 백업이 필요 |

브라우저 저장도 쓸모가 있습니다. 테마 설정이나 임시 작성 내용처럼 특정 기기에만 있어도 되는 데이터에 적합할 수 있습니다. 반대로 여러 사람이 함께 보는 신청 명단이라면 공통으로 접근할 저장소가 필요합니다. 인터넷 없이 쓰는 개인 기록장은 로컬 DB가 더 단순할 수 있습니다.

‘저장된다’는 말에는 기간과 조건이 빠져 있습니다. **앱을 다시 실행해도 남는다는 것과 영원히 사라지지 않는다는 것은 다릅니다.** 서버 DB도 잘못된 삭제, 계정 해지, 저장장치 장애로 잃을 수 있습니다. 데이터를 유지하는 방법과 잃은 뒤 복구하는 방법을 따로 생각합니다.

## 가장 짧게 확인하는 방법

이미 만든 앱이 있다면 개발용 사본이나 연습 환경에서 다음을 확인해 보세요. 이름을 입력하는 앱이라면 `연습 사용자 A` 같은 가상 값을 사용합니다. 다른 종류의 앱이라면 연습용 할 일이나 메모처럼 그 앱이 저장하는 항목을 하나 만듭니다. 실제 서비스나 실제 개인정보로 시험하지 않습니다.

아직 앱이 없다면 아래 항목을 읽으며 무엇을 확인하는지만 이해하고 다음 장으로 넘어가도 됩니다.

1. 새로고침 뒤 값이 남는지 봅니다.
2. 앱을 종료하고 다시 실행한 뒤 조회합니다.
3. 다른 브라우저에서 같은 계정으로 조회합니다. 계정 기능이 없다면 다른 브라우저가 별도 사용자라는 점을 기록합니다.
4. AI에게 저장 코드와 읽는 코드, 저장소 위치를 찾아 설명하게 합니다.

새로고침 후 값이 남아도 DB를 쓴다고 단정할 수는 없습니다. 브라우저 자체에도 데이터를 보관하는 기능이 있기 때문입니다. 다른 브라우저에서 값이 보이지 않는다면 저장 위치뿐 아니라 로그인 계정과 접근 권한도 확인해야 합니다. 사용자마다 볼 수 있는 데이터가 다르게 정해져 있을 수 있습니다. 화면에서 관찰한 결과와 AI가 찾아낸 저장 코드를 함께 확인해 보세요.

직접 실행해 보고 싶다면 [DB 안전 실습](../../labs/database-safety/README.md)의 SQLite 시작 경로에서 파일에 쓰고 다시 읽어 볼 수 있습니다. SQLite는 DB를 파일로 보관할 수 있는 DBMS입니다. 해당 실습의 준비 사항을 먼저 확인하세요. 클라우드 계정은 필요하지 않습니다.

## 배포하면 파일 위치도 달라진다

내 컴퓨터에서 SQLite 파일에 저장한 앱을 그대로 배포해도 같은 보관 조건이 보장되지는 않습니다. 배포 플랫폼의 실행 공간이 임시이거나 실행 인스턴스마다 분리될 수 있습니다. 예를 들어 Vercel은 로컬 SQLite 파일과 서버리스 파일시스템의 제약을 설명합니다. 서버에서 SQLite를 쓸 수 있는 환경도 있으므로, 제품 이름뿐 아니라 배포 환경의 파일 저장 조건도 확인해야 합니다. `문서 확인 · 2026-09-13` — [Vercel의 SQLite 안내](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel).

## AI에게 지시할 프롬프트

> 이 앱의 신청 정보가 저장되는 곳을 찾아 설명해 줘. 화면 상태, 브라우저 저장소, 서버 메모리, DB를 구분하고, 실제로 쓰고 읽는 코드 위치를 알려 줘. 새로고침, 서버 재시작, 다른 기기 접속에서 무엇이 유지되는지 설명해 줘. 비밀값이나 실제 사용자 데이터는 출력하지 마.

AI가 “PostgreSQL을 사용합니다”라고 답했다면, 신청 정보가 어떻게 저장되고 다시 표시되는지도 설명해 달라고 하세요. 예를 들어 ‘신청 버튼을 누름 → 서버가 신청을 DB에 기록함 → 목록을 열 때 DB에서 읽어 옴’처럼 한 데이터의 이동 과정을 따라갈 수 있어야 합니다.

다음 장에서는 ‘DB를 붙여 줘’라고 요청하기 전에 무엇을 선택해야 하는지 살펴봅니다.
