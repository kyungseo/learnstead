# 02. 내 앱에는 어떤 DB가 필요할까?

[이전: 01. 저장 버튼을 눌렀는데, 어디에 저장됐을까?](01-where-data-lives.md) · [목차](README.md) · [다음: 03. 데이터를 어떤 모양으로 나눌까?](03-model-your-data.md)

AI가 “Supabase를 쓰겠습니다”라고 답했을 때 지금 결정된 것이 무엇인지 알아봅시다. DB 엔진만 고른 것일 수도 있고, 인증·API·파일 저장까지 제공하는 서비스에 앱을 연결하겠다는 뜻일 수도 있습니다.

이 장을 읽으면 **저장 형태와 운영 방법을 나눠 선택할** 수 있습니다. 처음에는 아래의 세 질문만 답하면 됩니다. 데이터가 없는 소개 페이지라면 DB 없이 시작하는 것도 올바른 선택입니다.

## 먼저 세 가지를 정하기

- 누가 함께 쓰나요? 나 혼자, 같은 기기의 가족, 인터넷으로 접속하는 여러 사용자 중 어디에 해당하나요?
- 데이터를 어떻게 묶고 찾나요? 신청자별·모임별 목록과 중복 제한이 필요한가요, 서로 모양이 다른 기록을 주로 다루나요?
- 누가 보관을 책임지나요? 로컬 파일을 직접 관리하나요, 서버를 운영하나요, 관리형 서비스를 쓰나요?

이 가이드의 스터디 앱은 여러 사용자가 같은 모임에 신청하고, 자신의 신청만 취소합니다. 사용자·모임·신청의 관계를 표현하기 좋은 관계형 DB를 기준으로 설명합니다. 이것은 예제에 맞춘 선택이며 모든 앱에 대한 우열 판단은 아닙니다.

## 이름을 같은 층에서 비교하기

| 구분 | 예 | 선택하면서 함께 확인할 것 |
| --- | --- | --- |
| DBMS | SQLite, PostgreSQL, MySQL, MongoDB | 데이터 모델, 쿼리, 일관성, 운영 방식 |
| 관리형 DB 서비스 | Cloud Firestore | 서비스가 제공하는 DB 기능, 접근 규칙, 사용량 비용 |
| 앱 개발 플랫폼 | Supabase, Firebase | DB 외에 인증·파일·API를 어디까지 맡기는지 |
| 앱 제작 도구 | AI 코딩 도구, 시각적 앱 빌더 | 실제 연결된 DB와 생성된 코드, 데이터 내보내기 경로 |

Supabase에서 사용하는 관계형 DB는 PostgreSQL입니다. Firebase에는 여러 제품이 있고 이 글의 문서 DB 비교 대상은 Cloud Firestore입니다. 따라서 ‘PostgreSQL 대신 Supabase’라는 말에는 자체 운영 PostgreSQL 대신 Supabase가 제공하는 PostgreSQL 환경을 선택한다는 뜻이 숨어 있을 수 있습니다.

## 대표적인 다섯 선택지

| DB | 데이터를 보는 기본 모양 | 어울리는 출발 상황 | 놓치기 쉬운 질문 |
| --- | --- | --- | --- |
| SQLite | 테이블, 보통 파일에 저장 | 개인 도구, 작은 앱, 로컬 학습 | 파일이 어디에 남고 동시 쓰기가 얼마나 생기나? |
| PostgreSQL | 테이블과 관계 | 신청·재고·업무 기록처럼 관계와 규칙이 중요한 앱 | 연결·권한·백업을 누가 운영하나? |
| MySQL | 테이블과 관계 | 기존 서비스·팀이 MySQL을 운영하는 상황 | 사용 버전과 저장 엔진, SQL 차이는 무엇인가? |
| MongoDB | 문서와 컬렉션 | 한 덩어리로 읽는 구조가 있고 필드가 다양한 데이터 | 어떤 값을 포함하고 어떤 값을 참조할 것인가? |
| Cloud Firestore | 문서와 컬렉션 | 관리형 서비스와 클라이언트 SDK를 활용하는 앱 | 접근 규칙과 조회 패턴별 비용을 확인했나? |

SQLite는 연습 전용 제품이 아닙니다. 서버의 앱 뒤에서도 사용할 수 있습니다. 다만 한 DB 파일에는 한 순간에 하나의 쓰기 작업만 진행되므로 쓰기 경쟁과 배포 구조를 따져야 합니다. 여러 컴퓨터가 네트워크 공유 폴더의 파일을 직접 열게 만드는 방식은 피하는 편이 좋습니다. `문서 확인 · 2026-09-13` — [SQLite 사용 범위](https://www.sqlite.org/whentouse.html).

MySQL의 InnoDB는 트랜잭션과 외래키를 지원합니다. 관계형 DB라는 공통점이 SQL 문법·기본 설정까지 같다는 뜻은 아닙니다. `문서 확인 · 2026-09-13` — [MySQL InnoDB 소개](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html).

MongoDB의 유연한 구조도 모델링을 없애 주지는 않습니다. 검증 규칙으로 필드의 형식과 값도 제한할 수 있습니다. Firestore의 문서 역시 조회하고 갱신할 단위를 생각하며 설계합니다. `문서 확인 · 2026-09-13` — [MongoDB 스키마 검증](https://www.mongodb.com/docs/manual/core/schema-validation/), [Firestore 데이터 모델](https://firebase.google.com/docs/firestore/data-model).

## 이 시리즈의 학습 경로

먼저 SQLite로 저장과 규칙 위반을 짧게 관찰합니다. 그다음 [신청 앱 튜토리얼](../../tutorials/study-signup-db/README.md)에서 로컬 Supabase/PostgreSQL로 사용자별 접근을 배웁니다. MySQL·MongoDB·Firestore는 비교 설명이며 이 시리즈에서 실행했다고 주장하지 않습니다. 클라우드 가입, 유료 요금제, 실제 개인정보 없이 학습하는 경로를 기준으로 삼았습니다.

## AI에게 부탁할 말

> 앱은 여러 사람이 모임에 신청하는 용도야. 모임별 목록, 한 사람의 중복 신청 금지, 본인 신청만 취소하는 기능이 필요해. DB 엔진과 운영 서비스를 구분해서 제안해 줘. 내가 관리해야 할 항목, 데이터 내보내기 방법, 비용이 늘어나는 조건까지 비교하고 가장 단순한 경로 하나를 추천해 줘.

사람이 확인할 결과는 비교표의 승자가 아니라 **내가 맡을 운영 책임입니다**. 관리형 서비스가 백업 기능을 제공해도 우리 요금제에 포함되는지, 무엇을 복원할 수 있는지까지 확인해야 합니다.
