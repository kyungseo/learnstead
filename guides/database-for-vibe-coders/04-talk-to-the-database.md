<a id="04-앱은-db에-어떻게-부탁할까"></a>

신청 버튼을 누르면 무엇이 DB까지 전달될까요? AI가 API·SDK·SQL·ORM을 섞어 말해도 각각 맡은 일을 구분하면 요청의 경로를 읽을 수 있습니다.

이 장에서는 **한 번의 등록과 조회가 어디에서 처리되는지 설명합니다**. 모든 SQL을 외우는 대신 조회 조건과 변경 대상을 확인하는 것이 목표입니다.

## 버튼 뒤의 네 단어

신청 버튼을 눌렀을 때 앱은 ‘이 사용자를 이 모임에 등록해 달라’는 요청을 보냅니다. 요청을 받은 서버는 신청 정보를 DB에 기록합니다. 이 과정에서 다음 도구들이 쓰일 수 있습니다.

- **API**: 프로그램이 다른 프로그램에 요청을 보내고 결과를 받는 접점입니다. 신청 정보를 보내면 등록 결과를 돌려주는 기능을 예로 들 수 있습니다.
- **SDK**: API를 코드에서 쉽게 사용하도록 묶어 둔 도구입니다. 개발자가 요청을 보내는 코드를 매번 처음부터 작성하지 않도록 돕습니다.
- **SQL**: 관계형 DB에 ‘신청을 추가해라’, ‘모임 목록을 찾아라’처럼 저장과 조회를 요청하는 언어입니다.
- **ORM**: 프로그램 안에서 다루는 데이터와 DB의 기록을 연결하는 도구입니다. 개발자가 SQL을 직접 쓰는 일을 줄일 수 있지만, 최종적으로는 DB에 요청을 보냅니다.

네 가지가 반드시 차례대로 쓰이는 것은 아닙니다. 앱 구성에 따라 일부만 사용할 수도 있습니다.

일반적인 경로는 ‘브라우저 → 앱 서버 API → DB’입니다. Supabase처럼 브라우저가 SDK로 관리형 API를 호출하는 구성도 있습니다. 이때 브라우저가 DB 관리자 비밀을 들고 있는 것이 아니라, API와 DB의 접근 규칙이 각 요청을 제한해야 합니다. 어느 구성인지는 코드와 연결 설정에서 확인합니다.

## 등록·조회·수정·삭제 읽기

이 네 작업을 영어 첫 글자로 CRUD라고 부릅니다.

| 하고 싶은 일 | SQL의 대표 표현 | 사람이 확인할 것 |
| --- | --- | --- |
| 모임 목록 보기 | `SELECT` | 필요한 열과 허용된 행만 반환하는가? |
| 신청 추가 | `INSERT` | 요청자와 모임, 중복 처리 기준이 맞는가? |
| 신청 메모 바꾸기 | `UPDATE` | 누구의 어떤 신청을 바꾸는가? |
| 신청 삭제 | `DELETE` | 다른 기록이나 복구에 어떤 영향이 있는가? |

다음은 개념을 읽기 위한 SQL입니다. 초기화나 설치 명령이 아니며, 실제 스키마를 확인하지 않은 DB에 붙여 넣지 않습니다. 실행 경로는 [튜토리얼](../../tutorials/study-signup-db/README.md)에 있습니다.

```sql
SELECT id, title, capacity
FROM events
WHERE capacity > 0
ORDER BY id
LIMIT 10;
```

‘events에서 정원이 양수인 모임의 세 항목만, ID 순서로 최대 10개’라는 뜻입니다. `WHERE`는 조건, `ORDER BY`는 정렬, `LIMIT`는 반환 개수입니다. 조건이 빠진 수정·삭제는 의도보다 많은 기록에 영향을 줄 수 있습니다. 실제 변경 전에 같은 조건의 조회로 대상 ID와 개수를 확인합니다.

## 떨어진 정보를 같이 읽기

모임별 신청 건수를 보는 개념 예입니다. 튜토리얼 앱에는 신청 상태 열이 없으며, 해당 모임에 남아 있는 신청 기록을 모두 셉니다.

```sql
SELECT e.id, e.title, COUNT(r.id) AS registrations
FROM events AS e
LEFT JOIN registrations AS r ON r.event_id = e.id
GROUP BY e.id, e.title
ORDER BY e.id;
```

`JOIN`은 연결 조건에 맞춰 정보를 함께 읽습니다. `LEFT JOIN`을 사용하면 신청이 없는 모임도 남습니다. `COUNT(r.id)`는 연결된 신청 ID 개수를 셉니다. `COUNT(*)`로 바꾸면 신청이 없는 모임도 결합 결과의 한 행으로 세어질 수 있습니다. 숫자가 그럴듯해 보여도 0명·1명·여러 명인 모임을 따로 확인해야 하는 이유입니다.

이 조회를 모든 사용자에게 공개할 수 있는지는 별도 문제입니다. 사용자별 접근 규칙이 신청 행을 제한하면 결과가 전체 신청 수와 다를 수 있습니다. 공개 집계가 필요하다면 개인 신청 정보는 감추면서 집계만 제공하는 방법을 따로 설계합니다.

## 입력값을 SQL 문장으로 붙이지 않기

검색어와 신청 메모는 데이터입니다. 입력값을 문자열로 이어 SQL 문장에 넣으면 입력이 SQL 명령 일부로 해석되는 SQL injection 위험이 생깁니다. 코드에서는 매개변수화된 쿼리로 명령과 값을 분리합니다. 구체적인 매개변수 표기는 사용하는 라이브러리에 따라 다릅니다. ORM을 사용하더라도 직접 SQL을 조합하는 부분은 확인해야 합니다. `문서 확인 · 2026-09-13` — [OWASP SQL injection 예방](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

이는 AI가 문서 속 지시를 따르는 prompt injection과 다른 문제입니다. 사용자 입력을 DB에 전달하는 코드의 문제이므로 “이상한 지시를 무시해”라는 프롬프트만으로 해결하지 않습니다.

<a id="ai에게-부탁할-말"></a>

## AI에게 지시할 프롬프트

> 신청 버튼부터 DB까지 호출 경로를 설명해 줘. 조회는 어떤 조건과 권한으로 제한되고, 수정은 어떤 ID를 대상으로 하는지 보여 줘. 입력값을 SQL 문자열에 붙이는 부분이 있는지도 확인해 줘. 변경 쿼리는 먼저 같은 조건의 읽기 전용 조회와 예상 대상 수를 제시해 줘.

직접 볼 결과는 ‘정상 동작’ 한 문장보다 구체적입니다. 입력 ID, 조회 조건, 반환한 행 수, 변경된 행 수가 의도와 맞는지 확인합니다. 단, 로그에 비밀키나 실제 개인정보를 남기지는 않습니다.
