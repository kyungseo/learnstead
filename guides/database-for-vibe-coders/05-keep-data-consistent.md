# 05. 틀린 데이터가 들어오면 누가 막을까?

[이전: 04. 앱은 DB에 어떻게 부탁할까?](04-talk-to-the-database.md) · [목차](README.md) · [다음: 06. 로그인하면 내 데이터만 보일까?](06-permissions-and-keys.md)

신청 버튼을 한 번 누른 것처럼 보여도 네트워크 재시도나 두 번 클릭으로 요청은 두 번 도착할 수 있습니다. 동시에 두 사람이 마지막 한 자리에 신청할 수도 있습니다. 데이터 규칙은 화면에서 시작해 DB까지 이어져야 합니다.

이 장에서는 **중복, 부분 성공, 동시 요청을 다른 문제로 구분합니다**. 오류를 일부러 만드는 실행은 [DB 안전 실습](../../labs/database-safety/README.md)의 가상 환경에서 진행합니다.

## 화면의 안내와 DB의 거절

화면이 빈 이름을 막으면 사용자에게 빠르게 안내할 수 있습니다. API가 입력을 검사하면 잘못된 요청을 구분할 수 있습니다. DB의 제약조건은 다른 코드 경로로 들어온 데이터도 같은 규칙을 지키게 합니다. 한 곳의 검사가 나머지를 모두 대체하지는 않습니다.

| 규칙 | DB에서 표현하는 예 | 실패가 뜻하는 것 |
| --- | --- | --- |
| 모임 제목이 필요함 | `NOT NULL`과 필요 시 빈 문자열 검사 | 누락된 입력을 저장하지 않음 |
| 정원은 양수 | `CHECK (capacity > 0)` | 잘못된 수치 거절 |
| 같은 모임에 한 번만 신청 | `UNIQUE (event_id, user_id)` | 중복 조합 거절 |
| 실제 모임에 신청 | 외래키 | 없는 대상 참조 거절 |

이 표는 설계 예입니다. 실제 스키마가 어떤 검사를 구현했는지는 코드와 실패 결과로 확인합니다. `NOT NULL`만으로 빈 문자열까지 막지는 않는다는 차이도 읽어야 합니다. `문서 확인 · 2026-09-13` — [PostgreSQL 제약조건](https://www.postgresql.org/docs/current/ddl-constraints.html).

## 함께 성공하거나 함께 취소하기

정원 카운터를 줄이고 신청을 기록하는 두 작업을 생각해 봅시다. 첫 작업만 성공하면 신청자는 없는데 자리는 줄어듭니다. 트랜잭션(transaction)은 함께 처리할 DB 작업의 경계를 정합니다. `COMMIT`은 확정, `ROLLBACK`은 확정 전 변경 취소입니다. 실패 시 일부만 남지 않는 성질을 원자성이라고 합니다. `문서 확인 · 2026-09-13` — [PostgreSQL 트랜잭션](https://www.postgresql.org/docs/current/tutorial-transactions.html).

트랜잭션이 이메일까지 되돌려 주지는 않습니다. DB 변경 후 외부로 발송한 메일이나 결제 요청에는 별도의 실패·재시도 설계가 필요합니다. 이 시리즈의 실습은 DB 내부의 변경을 다룹니다.

## 트랜잭션만 쓰면 정원을 지킬까?

자리가 하나 남았을 때 A와 B가 각각 ‘남은 자리 1개’를 읽고 둘 다 신청할 수 있습니다. 작업을 트랜잭션으로 묶더라도 둘이 읽고 변경하는 순서와 보호 방식에 따라 경쟁이 생깁니다.

이를 막으려면 같은 모임의 변경을 순서대로 처리하는 잠금, 조건을 포함한 원자적 갱신, 충돌을 발견하는 격리 수준과 재시도 같은 방법을 선택해야 합니다. 초급 독자가 구현을 외울 필요는 없습니다. **거의 동시에 신청했을 때 최종 신청 수가 정원을 넘지 않는지** 확인하는 것이 중요합니다. 서로 다른 사용자 둘로 보내야 중복 신청 제한만 시험하고 끝나지 않습니다.

> 🔧 한 단계 더: 격리 수준은 동시에 진행되는 트랜잭션이 서로의 변경을 어떻게 보게 할지 정하는 규칙입니다. 가장 강한 설정을 켜기만 하면 끝나는 것이 아니라 충돌로 취소된 작업을 어떻게 안내하고 재시도할지도 필요합니다.

## 재시도를 같은 신청으로 알아보기

멱등성(idempotency)은 같은 의도의 요청이 반복되어도 추가 부작용이 생기지 않도록 하는 성질입니다. 신청 예에서는 사용자와 모임 조합의 고유 제약이 중복 기록을 막는 데 도움이 됩니다. 그러나 두 번째 요청에 오류를 보여 줄지, 이미 완료된 신청을 돌려줄지는 API가 정해야 합니다.

일반적인 결제나 주문은 같은 사람이 여러 번 합법적으로 주문할 수 있으므로 사용자 ID만으로 중복을 막을 수 없습니다. ‘같은 시도’를 구분하는 요청 식별자가 필요한 이유입니다. 이 예제의 단순한 중복 규칙을 다른 업무에 그대로 옮기지 않습니다.

## AI에게 부탁할 말

> 같은 사용자의 중복 요청과 서로 다른 두 사용자의 마지막 자리 경쟁을 나눠 시험해 줘. 어떤 제약조건과 트랜잭션이 각각을 막는지 설명하고, 중간에 실패했을 때 남는 데이터도 보여 줘. 테스트가 통과해도 검증하지 않은 동시성 조건은 별도로 적어 줘.

확인할 것은 오류 메시지 유무만이 아닙니다. 정상 신청은 들어가고, 중복은 늘어나지 않으며, 중간 실패 후 값은 원상태이고, 정원 초과 기록은 없어야 합니다. 오류를 전부 무시해서 화면만 조용해진 상태는 성공이 아닙니다.
