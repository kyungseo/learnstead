# 06. 로그인하면 내 데이터만 보일까?

스터디 앱에 연습 사용자 A와 B가 각각 신청했다고 해 보겠습니다. A로 로그인하니 ‘내 신청’ 화면에는 A의 신청만 보입니다. 그러면 B의 신청 정보는 안전하게 보호되고 있을까요?

앱이 모든 신청을 받아 온 뒤 화면에서 A의 것만 골라 보여 주고 있을 수도 있습니다. 또는 서버가 어떤 신청을 읽을 수 있는지 검사하지 않아, A가 요청에 넣는 신청 ID를 B의 것으로 바꾸면 B의 정보까지 받을 수도 있습니다. 다른 사람의 신청을 화면에서 숨기는 것과, 그 정보에 접근하지 못하게 막는 것은 다릅니다.

이 장에서는 **로그인과 데이터 접근 권한이 어떻게 다른지** 알아봅니다. 아래 확인 항목을 실제로 시험할 때는 자신이 만든 연습 환경과 A·B 계정만 사용합니다. 타인의 실제 데이터에 접근하는 시험은 하지 않습니다.

## 신원 확인 다음에는 행동 범위를 정하기

인증(authentication)은 요청자가 누구인지 확인합니다. 인가 또는 권한 검사(authorization)는 그 사람이 무엇을 읽고 바꿀 수 있는지 판단합니다. 로그인은 첫 질문에 답할 뿐 두 번째 질문의 정답은 아닙니다.

스터디 예제에서 사용자는 모임을 보고 자신의 신청을 만들 수 있지만 다른 사용자의 신청을 취소하면 안 됩니다. 서버는 화면이 보낸 `user_id`를 그대로 신뢰하기보다 검증한 로그인 정보와 맞춰야 합니다. ‘관리자 버튼 숨김’도 관리자 권한 검사가 아닙니다.

## 행마다 적용하는 규칙

RLS(Row Level Security)는 테이블의 행에 접근 규칙을 적용하는 기능입니다. ‘이 행의 사용자 ID가 현재 로그인한 사용자와 같은가?’ 같은 기준을 둘 수 있습니다. Supabase에서는 노출한 테이블의 RLS와 정책, 역할별 권한을 함께 확인합니다. RLS를 켰다는 사실만으로 원하는 접근이 완성됐다고 판단하지 않습니다. `문서 확인 · 2026-09-13` — [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

설계를 읽을 때는 조회·등록·수정·삭제를 각각 적습니다. 수정의 경우 남의 행을 선택하지 못하는지뿐 아니라 자신의 행을 남의 소유로 바꿀 수 없는지도 확인합니다. 권한 있는 DB 관리 도구에서 조회한 결과는 일반 사용자의 권한 시험을 대신하지 못합니다.

## 브라우저에서 보여도 되는 키와 비밀키

Supabase의 publishable key는 공개 환경에 사용할 수 있는 키입니다. 높은 권한을 가진 secret key와 기존 service-role 계열 키는 브라우저에 넣으면 안 됩니다. 키 종류와 사용자 로그인 토큰의 역할도 다릅니다. 로컬 도구에서 사용하는 기존 `anon` 키 같은 표기는 버전과 설정에 따라 다를 수 있으므로 이름만 보고 권한을 추측하지 않습니다. `문서 확인 · 2026-09-13` — [Supabase API 키](https://supabase.com/docs/guides/getting-started/api-keys).

환경 변수는 프로그램을 실행하거나 빌드할 때 DB 주소나 키 같은 설정값을 전달하는 방법입니다. 빌드 과정에서 브라우저용 코드에 포함되는 환경 변수는 사용자가 읽을 수 있습니다. `.env`라는 파일명이나 `SECRET`이라는 변수 이름이 비밀을 보장하지 않습니다. 서버 전용 비밀인지, 공개용 설정인지, 최종적으로 어느 코드에 들어가는지 확인합니다.

비밀이 노출됐다면 코드에서 지우는 것만으로 끝내지 않습니다. 해당 키를 폐기·교체하고 영향 범위를 확인해야 합니다. 문서·로그·Git 이력에 원래 값을 다시 복사하지 않습니다.

## 허용과 거절을 함께 확인하기

| 요청자 | 작업 | 예제에서 기대하는 결과 |
| --- | --- | --- |
| 사용자 A | A의 신청 조회·취소 | 허용 |
| 사용자 A | B의 신청 조회·취소 | 거절 또는 보이지 않음 |
| 사용자 B | B의 신청 조회·취소 | 허용 |
| 비로그인 | 모임·신청 조회, 신청 만들기 | 거절 |
| 사용자 A | 소유자를 B로 바꿔 등록·수정 | 거절 |

제품에 따라 거절이 오류, 빈 목록, 변경 0건 등으로 나타날 수 있습니다. HTTP 응답 코드만 보고 성공·실패를 단정하지 말고 반환된 내용과 DB의 변경 여부를 함께 봅니다. 이 시리즈의 앱은 모임 목록도 로그인 후 조회하도록 정했습니다. 공개 목록을 제공하고 싶다면 그 정책을 따로 설계하고 다시 시험합니다.

Firestore를 사용한다면 같은 목적을 Security Rules 등 해당 제품의 권한 체계로 구현합니다. 서버용 라이브러리는 클라이언트 규칙과 다른 권한 경로를 사용하므로 브라우저 규칙만 점검하고 서버가 안전하다고 결론내리지 않습니다. `문서 확인 · 2026-09-13` — [Firestore Security Rules 시작](https://firebase.google.com/docs/firestore/security/get-started).

## AI에게 지시할 프롬프트

> A, B, 비로그인 상태로 조회·등록·수정·삭제의 허용과 거절을 확인해 줘. 관리자 키를 사용하는 테스트와 실제 사용자 토큰 테스트를 구분해 줘. 화면 필터를 우회한 요청도 연습 환경에서 시험하고, 비밀값 없이 결과와 남은 데이터만 보고해 줘.

[실습](../../labs/database-safety/README.md)에서는 의도적으로 구성한 실패와 수정 결과를 비교합니다. 실패 예제는 학습을 위해 만든 것으로, 실제 AI가 일으킨 사고를 재현한 것은 아닙니다.
