# 07. AI에게 DB 변경을 어떻게 맡길까?

[이전: 06. 로그인하면 내 데이터만 보일까?](06-permissions-and-keys.md) · [목차](README.md) · [다음: 08. 데이터가 늘거나 사라지면 어떻게 할까?](08-operate-and-recover.md)

“신청 상태에 대기 중을 추가해 줘”라는 작은 요청도 이미 저장된 신청의 의미를 바꿀 수 있습니다. 비어 있는 새 DB에서 성공한 변경이 기존 데이터가 있는 DB에서도 성공하는지 확인해야 합니다.

이 장에서는 **변경 계획·적용·검증·복구를 구분해 AI에게 맡기는 방법을** 배웁니다. 코드를 고치기 전에 현재 연결 대상부터 확인합니다.

## 새 구조를 선언하는 것과 기존 구조를 바꾸는 것

스키마가 현재의 구조라면 migration은 그 구조를 단계적으로 바꾸는 변경 기록입니다. 새 컬럼 추가, 기존 값 변환, 제약조건 추가 같은 작업이 들어갑니다. AI가 모델 파일만 수정했다면 실제 DB에도 반영되는지, 이미 운영 중인 DB에는 어떤 변경 순서가 필요한지 확인해야 합니다.

Supabase는 migration 파일로 DB 변경을 관리하는 경로를 제공합니다. 로컬 변경, 원격 프로젝트 적용, 기존 변경 이력의 관계를 이해한 뒤 해당 명령을 실행합니다. `문서 확인 · 2026-09-13` — [Supabase migration](https://supabase.com/docs/guides/deployment/database-migrations).

개발용 reset은 데이터를 지우고 처음부터 다시 만드는 작업일 수 있습니다. 새 DB 재현에 도움이 되더라도 기존 데이터를 살리는 migration 검증은 아닙니다. `reset`, `DROP`, `TRUNCATE` 같은 표현을 보면 실행 대상과 삭제 범위를 먼저 읽습니다.

## 먼저 추가하고, 채우고, 확인하기

예를 들어 기존 신청에 `status`를 새로 넣는다고 합시다. 모든 옛 신청을 자동으로 승인 상태로 채워도 되는지는 업무 결정입니다. AI가 기술적으로 가능한 기본값을 골랐다고 업무 의미까지 맞는 것은 아닙니다.

1. 기존 데이터 중 어떤 상태로 옮길 수 있는지 확인합니다.
2. 새 구조와 옛 앱이 함께 동작할 수 있는 기간이 필요한지 정합니다.
3. 가상 기존 데이터를 가진 개발 DB에서 변경을 적용합니다.
4. 이전 기록의 값과 개수, 정상 신청, 권한을 확인합니다.
5. 실제 적용 전 백업과 복구 경로를 준비하고 대상 DB를 다시 확인합니다.

이 순서는 모든 DB 변경의 명령 묶음이 아니라 변경을 판단하는 순서입니다. 컬럼 삭제나 대량 변환에는 추가 검토가 필요합니다. 기존 값을 지운 뒤 같은 이름의 컬럼을 다시 만든다고 옛 값이 돌아오지는 않습니다.

## 개발·운영 연결을 눈으로 구분하기

개발 DB는 가상 데이터를 넣고 실패를 시험하는 곳입니다. 운영 DB는 실제 사용자의 기록이 있는 곳입니다. 앱 주소가 `localhost`여도 환경 설정이 운영 DB를 가리킬 수 있습니다. 화면 주소만으로 구분하지 않습니다.

AI에게 프로젝트 식별자, DB 이름, 연결 대상 종류를 비밀값 없이 표시하게 합니다. 연결 문자열 전체에는 비밀번호가 들어갈 수 있으므로 복사해 공개 문서에 남기지 않습니다. 개발용 앱의 비밀 저장소에 운영 자격증명을 넣지 않는 방식으로 실수를 줄입니다.

## 세 가지 되돌리기

| 되돌릴 대상 | 대표 수단 | 돌아오지 않을 수 있는 것 |
| --- | --- | --- |
| 앱 코드 | Git의 이전 코드 | 이미 바뀐 DB 구조와 데이터 |
| DB 구조 | 검증한 후속 migration | 이미 삭제하거나 변환해 잃은 원래 값 |
| DB 데이터 | 검증한 백업 복원 | 백업 시점 이후 변경, 별도 파일 저장소 |

Git에 migration 파일이 있어도 운영 DB 데이터의 백업은 아닙니다. 앱 코드를 먼저 되돌렸는데 DB 구조는 새 상태라면 서로 맞지 않을 수 있습니다. rollback 계획은 어느 코드와 어느 DB 상태를 함께 사용할지 설명해야 합니다.

## AI에게 부탁할 말

> 지금 연결 대상이 개발용인지 비밀값 없이 확인해 줘. 기존 신청을 보존하면서 상태를 추가하려고 해. 현재 데이터의 의미, 변경 SQL, 옛 데이터 처리 방법, 권한 영향, 검증 방법, 실패 후 복구 경로를 먼저 설명해 줘. 새 DB 재생성과 기존 데이터가 있는 DB의 변경 검증을 구분해 줘.

확인할 결과는 두 경로입니다. 처음 설치한 DB에서 완성 구조가 만들어지고, 이전 데이터가 있는 DB에서도 의도대로 변경되어야 합니다. 한쪽만 통과했다면 그 범위를 기록하고 공개 준비가 끝났다고 하지 않습니다.
