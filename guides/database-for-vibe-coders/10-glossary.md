# 10. 데이터베이스 용어집

[이전: 09. 다른 사람에게 공개해도 될까?](09-ready-to-share.md) · [목차](README.md) · [다음: 신청 앱 튜토리얼](../../tutorials/study-signup-db/README.md)

앞의 글에서 낯선 말이 나왔을 때 찾아보는 페이지입니다. 용어를 모두 외운 뒤 시작할 필요는 없습니다. 자신의 앱을 설명하는 문장에 넣어 보세요.

| 용어 | 이 가이드에서의 뜻 | 신청 앱에서의 예 |
| --- | --- | --- |
| DB / DBMS | 데이터 저장소 / 이를 관리하는 프로그램 | 신청 데이터 / PostgreSQL |
| 테이블 / 행 / 열 | 같은 종류의 기록 모음 / 한 기록 / 항목 | 모임 목록 / 한 모임 / 제목 |
| 문서 / 컬렉션 | 필드와 값을 묶은 기록 / 문서 모음 | 장소 정보를 포함한 모임 문서 |
| 스키마 | 데이터 구조의 약속 | 신청에 어떤 항목과 관계가 있는가 |
| 기본키 | 행을 유일하게 가리키는 키 | 신청 `id` |
| 외래키 | 다른 테이블의 기록과 연결을 유지하는 규칙 | 신청의 `event_id` |
| 제약조건 | DB가 저장할 때 지키는 규칙 | 정원 양수, 중복 신청 금지 |
| NULL | 값이 없거나 알려지지 않음 | 아직 정하지 않은 값; 0과 다름 |
| 쿼리 / SQL | DB에 하는 요청 / 관계형 DB의 요청 언어 | 모임별 신청 목록 조회 |
| CRUD | 등록·조회·수정·삭제 | 신청 생성부터 취소 처리까지 |
| JOIN | 조건으로 연결된 기록을 함께 읽기 | 모임 제목과 신청 기록 함께 보기 |
| 집계 | 여러 기록을 세거나 계산하기 | 모임별 신청 수 |
| API / SDK | 프로그램의 요청 접점 / 사용을 돕는 도구 묶음 | 신청 API, Supabase SDK |
| ORM | 프로그램 객체와 DB 기록을 연결하는 도구 | 코드의 신청 객체를 행으로 저장 |
| 트랜잭션 | 함께 확정하거나 취소할 DB 작업 범위 | 신청 기록과 자리 수 갱신 |
| 원자성 | 작업 일부만 남지 않게 하는 성질 | 중간 실패하면 함께 취소 |
| 동시성 | 여러 작업이 겹쳐 진행되는 조건 | 둘이 마지막 자리에 신청 |
| 잠금 | 충돌하는 변경을 조정하는 수단 | 같은 모임 변경 순서 조정 |
| 멱등성 | 같은 의도의 반복 요청이 추가 부작용을 만들지 않는 성질 | 재전송해도 신청이 하나 |
| 인증 / 인가 | 누구인지 확인 / 허용한 행동인지 판단 | A로 로그인 / A의 신청만 취소 |
| RLS | 행 단위 접근 규칙 | 본인의 신청 행만 접근 |
| migration | DB 구조를 단계적으로 바꾸는 기록 | 상태 항목 추가와 기존 값 처리 |
| seed / fixture | 초기 데이터 / 재현을 위해 고정한 입력 | 실습용 모임과 사용자 |
| 인덱스 | 조회를 돕는 추가 데이터 구조 | 특정 사용자의 신청 찾기 |
| 페이지 나누기 | 목록을 일정량씩 읽기 | 다음 20개 신청 |
| 백업 / 복원 | 되살릴 사본 준비 / 사본에서 다시 사용 가능한 상태 만들기 | 별도 DB에 신청 데이터 복구 |
| RPO / RTO | 허용 데이터 손실 시간 / 목표 복구 시간 | 하루 기록 손실, 두 시간 내 재개 등 |
| 파일 저장소 | 파일 본체를 보관하는 곳 | DB 경로와 별개인 첨부 이미지 |

## AI 답변에서 다시 물어볼 말

“스키마를 마이그레이션했습니다” → 기존 데이터가 있는 DB에도 적용했나요? 무슨 값이 바뀌었나요?

“RLS를 적용했습니다” → A와 B, 비로그인 상태로 무엇이 허용되고 거절됐나요?

“백업했습니다” → 어디에 복원해 봤나요? 첨부 파일과 권한도 포함되나요?

“인덱스를 추가했습니다” → 어떤 조회가 어떻게 달라졌나요? 실제로 측정했나요?

“서버에 저장됩니다” → 개발용인가요, 운영용인가요? 배포·재시작 뒤에도 남나요?

이 질문에 답할 수 있다면 DB의 모든 내부 원리를 알지 못해도 자신의 앱이 데이터를 다루는 방식을 더 정확히 판단할 수 있습니다.
