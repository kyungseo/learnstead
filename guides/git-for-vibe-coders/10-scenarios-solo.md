## S1 — 지금부터 Git으로 관리하기

**상황:** AI와 며칠째 만들고 있는데 Git을 안 쓰고 있었습니다. 지금이라도 시작하고 싶습니다.

```bash
cd 내-프로젝트-폴더
git init
git add .
git commit -m "첫 저장: 지금까지 만든 것"
git log --oneline
```

**★ 성공 판정:** `b975e6c 첫 저장: 지금까지 만든 것` 처럼 한 줄이 나옵니다. `[실행 검증 · 2026-08-23]`

⚠️ **`git add .` 전에 확인:** 비밀번호·API 키가 든 파일이 폴더에 있으면 함께 담깁니다. 먼저 `.gitignore`를 만드세요
([04 §5](04-four-areas.md), [S10](11-scenarios-share.md)).

> 💬 **AI에게:** "이 폴더를 git으로 관리 시작해 줘. 먼저 이 프로젝트에 맞는 .gitignore를 만들어서 비밀번호·API 키·라이브러리
> 폴더가 제외되게 하고, 그다음 지금 상태를 '첫 저장'으로 커밋해 줘."

## S2 — AI에게 시키기 전 세이브 포인트

**상황:** AI에게 "전체적으로 개선해 줘" 같은 큰 작업을 시키려 합니다. **이 가이드에서 가장 중요한 습관입니다.**

```bash
git add .
git commit -m "AI에게 디자인 개편 시키기 전"
```

짧은 명령 두 줄이면 됩니다. 이 commit이 없으면 [S3](#s3--ai가-망쳐놨다)에서 돌아갈 기준 상태가 없어 **Git만으로 원래
상태를 복원하기 어렵습니다.**

| 이럴 때 반드시 | 이유 |
| --- | --- |
| 파일 여러 개를 건드리는 요청 | 어느 파일이 문제인지 나중에 못 찾음 |
| "구조를 바꿔 줘", "리팩터링" | 되돌릴 지점이 필요 |
| 잘 되던 상태에 도달했을 때 | **잘 되는 상태야말로** 저장 가치가 가장 큼 |

> 💬 **AI에게:** "지금 상태를 '(무엇을 하기 전)'이라는 메시지로 커밋하고, 그다음 (하려는 일)을 해 줘."

## S3 — AI가 망쳐놨다

**상황:** AI가 고친 뒤 화면이 깨졌습니다. 되돌리고 싶습니다. **어디까지 갔는지**에 따라 명령이 다릅니다.

### 3-1. 아직 커밋 안 했다 (가장 흔함)

먼저 무엇이 바뀌었는지 봅니다.

```bash
$ git status --short
 M index.html          ← 이것만 되돌리고 싶다
?? app.js              ← 새 파일, 두고 싶다
?? style.css           ← 새 파일, 두고 싶다
```

**한 파일만 되돌리기:**

```bash
$ git restore index.html

$ git status --short
?? app.js              ← 그대로 남음
?? style.css           ← 그대로 남음
```

`[실행 검증 · 2026-08-23]` — `restore`는 **지목한 파일만** 건드립니다. 나머지 작업은 살아남습니다.

**전부 되돌리기(마지막 커밋 상태로):** `git restore .` — 단, tracked file의 커밋 안 된 작업이 **전부 사라집니다.**
`git diff`로 살릴 변경이 없는지 먼저 확인하세요.

### 3-2. 이미 커밋했다

```bash
$ git log --oneline
70b9757 AI: 배경을 검게 (마음에 안 듦)     ← 이 커밋을 취소하고 싶다
9609729 AI: 스타일과 스크립트 추가
842a04e 로그인 버튼 추가

$ git revert --no-edit 70b9757
[main cdb126b] Revert "AI: 배경을 검게 (마음에 안 듦)"
 1 file changed, 1 deletion(-)
```

`[실행 검증 · 2026-08-23]` — 취소하는 **새 commit이** 쌓이고, 그 변경만 파일에서 사라집니다. 원래 commit도 기록에 남습니다.

### 3-3. 몇 커밋 전 상태를 보고 싶다 (되돌리진 않고)

```bash
git switch --detach 842a04e     # 그 시점으로 잠깐 이동
# ... 확인 ...
git switch -                    # 원래대로 복귀
```

⛔ **`git reset --hard`는 쓰지 마세요.** 커밋 안 된 작업이 복구 불가능하게 사라집니다([05 §4](05-commits-and-undo.md)에서 실제로 확인).

> 💬 **AI에게:** "AI가 방금 바꾼 것 중에 index.html만 원래대로 되돌려 줘. 다른 파일은 그대로 둬."
> 또는 — "마지막 커밋을 취소하고 싶어. **reset이 아니라 revert로** 해 줘."

## S4 — 두 가지 안을 비교하기

**상황:** 다크 모드를 A안·B안 두 가지로 만들어 보고 고르고 싶습니다. 폴더를 복사하지 마세요.

```bash
# A안
$ git switch -c try-blue
$ printf 'body { color: blue; }\n' > style.css
$ git commit -am "시안 A: 파랑"

# 본편으로 돌아가 B안
$ git switch main
$ git switch -c try-green
$ printf 'body { color: green; }\n' > style.css
$ git commit -am "시안 B: 초록"

# 오가며 실제로 실행해 보기
$ git switch try-blue
$ cat style.css
body { color: blue; }
$ git switch try-green
$ cat style.css
body { color: green; }
```

`[실행 검증 · 2026-08-23]` — **같은 파일의 내용이 브랜치를 오갈 때마다 바뀝니다.** 앱을 실행해 보고 고르면 됩니다.

**B가 좋았다면:**

```bash
git switch main
git merge try-green      # 채택
git branch -D try-blue   # 폐기
```

> 💬 **AI에게:** "다크 모드를 두 가지 방식으로 만들어 보고 싶어. try-a, try-b 브랜치를 각각 만들어서 한쪽엔 (방법1), 다른
> 쪽엔 (방법2)로 구현해 줘. 브랜치 오가는 명령도 알려 줘."

## S5 — 뭐가 바뀌었는지 보기

**상황:** AI가 "수정했습니다"라고 했는데 정확히 뭘 건드렸는지 모르겠습니다.

`[실행 검증 · 2026-08-23]` — 네 가지 중 상황에 맞는 것을 씁니다.

| 알고 싶은 것 | 명령 | 출력 |
| --- | --- | --- |
| **어떤 파일이** 바뀌었나 | `git status --short` | `M index.html` / `?? style.css` |
| **어떤 줄이** 바뀌었나 (아직 커밋 전) | `git diff` | `+<p>새 문단</p>` 처럼 +/− 로 |
| 얼마나 바뀌었나 (요약) | `git diff --stat` | `index.html \| 1 +` |
| **마지막 커밋이** 무엇을 바꿨나 | `git show --stat HEAD` | 커밋 정보 + 파일 목록 |

실제 출력 예:

```text
$ git diff
diff --git a/index.html b/index.html
--- a/index.html
+++ b/index.html
@@ -1,2 +1,3 @@
 <h1>내 앱</h1>
 <p>소개</p>
+<p>새 문단</p>          ← + 는 추가된 줄. − 는 삭제된 줄
```

**읽는 법:** `+`로 시작하면 추가, `−`로 시작하면 삭제, 아무것도 없으면 문맥(안 바뀜)입니다. 나머지 기호는 무시해도 됩니다. `[원리]`

> 💬 **AI에게:** "지금 작업 폴더에서 뭐가 바뀌었는지 파일별로 요약해 주고, 각각 무슨 의도의 변경인지 설명해 줘."

## S6 — 하던 일을 잠깐 치워 두기

**상황:** 새 기능을 만들다 말았는데 급한 오타 수정 요청이 들어왔습니다. 지금 커밋하기엔 미완성입니다.

```bash
$ git stash push -m "푸터 작업 중"    # 하던 일을 서랍에 넣기
$ git status --short
                                      ← 깨끗해짐 (마지막 커밋 상태)

$ # ... 급한 수정하고 커밋 ...

$ git stash pop                       # 하던 일 되찾기
$ git status --short
 M index.html                         ← 하던 작업이 돌아옴
```

`[실행 검증 · 2026-08-23]`

### ⚠️ 되찾을 때 충돌이 날 수 있습니다

치워 둔 사이에 **같은 파일을** 고쳤다면 이런 화면이 나옵니다. 작성 환경에서 실제로 발생했습니다. `[실행 검증 · 2026-08-23]`

```text
$ git stash pop
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
The stash entry is kept in case you need it again.
```

`index.html`에는 `<<<<<<< Updated upstream` 아래에 그 사이 commit한 내용, `=======` 아래에 stash에 치워 둔 내용,
`>>>>>>> Stashed changes`까지 충돌 구간이 표시됩니다.

**해결:** 파일을 열어 표시 세 줄(`<<<<<<<`, `=======`, `>>>>>>>`)을 지우고 원하는 내용만(또는 둘 다) 남긴 뒤 `git add 파일`.
그다음 `git stash drop`으로 서랍을 비웁니다. 마지막 줄이 알려 주듯 **pop이 실패해도 stash entry는 남으므로** 충돌을
해결한 뒤 다시 적용할 근거가 유지됩니다.

| 명령 | 뜻 |
| --- | --- |
| `git stash list` | 서랍에 뭐가 있나 |
| `git stash pop` | 최근 것을 적용하고, 충돌이 없으면 서랍에서 지움 |
| `git stash apply` | 적용하되 서랍에 남겨 둠 |
| `git stash drop` | 서랍에서 버림 |

> 💬 **AI에게:** "지금 하던 작업을 잠깐 stash로 치워 두고, (급한 일)을 해 줘. 끝나면 다시 꺼내 줘."

기본 `git stash push`는 새로 만든 untracked file을 담지 않습니다. 그 파일까지 치우려면 `git stash push -u`가 필요합니다.
먼저 `git status --short`로 대상 파일을 확인하세요. `[문서 확인 · 2026-08-27]`
