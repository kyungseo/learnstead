# AI와 함께 만들기 — 바이브 코딩에서 Agentic Engineering으로

![자연어로 설명한 아이디어를 계획·확인·복구를 거쳐 앱으로 만들어 가는 바이브 코딩 가이드](assets/vibe-coding-practice-hero.webp)

**AI가 코드를 만들어 주는데, 결과는 왜 이렇게 다를까요?**

바이브 코딩은 코딩을 몰라도 아이디어를 빠르게 구현할 수 있게 해 줍니다. 하지만 어디까지 맡기고 무엇을 직접 확인하느냐에 따라
결과는 달라집니다.

이 가이드는 코드를 읽는 법 대신 **AI에게 일을 맡기면서도 결정권을 놓치지 않는 법을** 다룹니다. 만들 것을 먼저 정하고, 되돌릴
지점을 남기고, 한 번에 하나씩 지시하고, 결과를 직접 확인합니다. 막히면 같은 지시를 반복하지 않고 되돌리거나 접근을 바꿉니다.

## ‘바이브 코딩’이라는 이름에서 시작하는 이유

바이브 코딩(vibe coding)이라는 표현은 2025년 2월 Andrej Karpathy가 재미로 만드는 작은 프로젝트에서 AI가 생성한 코드를 자세히 들여다보지
않고 결과를 보며 계속 작업하는 모습을 설명하면서 널리 알려졌습니다. 1년 뒤 그는 LLM Agent를 활용하는 일이 전문적인 개발
방식으로 자리 잡고 있다며, 더 많은 감독과 엄격한 검토를 전제로 **Agentic Engineering이라는** 표현을 제안했습니다.
`[문서 확인 · 2026-09-01]`

- **바이브 코딩:** 흐름을 따라 빠르게 만들고 실험하는 방식
- **Agentic Engineering:** AI Agent가 구현하더라도 사람이 목표·범위·검증·품질을 책임지는 방식

두 표현의 경계가 공식 표준으로 정해진 것은 아닙니다. 이 가이드도 사람들이 익숙하게 찾는 ‘바이브 코딩’에서 출발하지만, 실제로
익히려는 습관은 Agentic Engineering에 가깝습니다. AI에게 구현을 맡길 수는 있어도 **이것이 맞는지 판단하는 일까지 맡기지는
않습니다.** 다만 이 입문 가이드의 확인 절차가 전문적인 code review나 security 검토를 대신하지는 않습니다. 공개 서비스와
고위험 기능에는 해당 분야의 검토가 별도로 필요합니다. 용어의 유래와 근거는 [출처](SOURCES.md)에 정리했습니다.

## 시작하기 전에 큰 그림부터

바이브 코딩은 코드를 모르는 사람에게도 직접 만들 기회를 주고, 개발자에게는 계획을 더 빠르게 구현할 수단을 줍니다. 반대로
경험이 많아도 계획과 검토 없이 짧은 지시만 반복하면 유지하기 어려운 코드를 만들 수 있습니다. 중요한 것은 누가 AI를 쓰느냐보다
**어떤 구조를 이해하고 어떤 절차로 확인하느냐입니다.** `[해석]`

[00 코드를 둘러싼 큰 그림](00-big-picture.md)에서는 Frontend·Backend·Database의 역할, 개발·배포 플랫폼과 BaaS, 작업을
돕는 harness를 한 번에 정리합니다. 특정 서비스를 따라 하는 사용법이 아니라, 무엇을 도구에 맡기고 무엇을 직접 책임져야 하는지
판단하기 위한 장입니다.

## 이 가이드가 해결하려는 문제

다음 중 하나라도 익숙하다면 이 가이드가 도움이 됩니다.

- 어제까지 되던 기능이 오늘은 왜 안 되는지 모르겠다.
- 고쳐 달라고 한 곳이 아닌 다른 기능까지 달라졌다.
- AI가 완료했다고 했지만 실제로 무엇을 확인해야 할지 모르겠다.
- 같은 오류를 설명해도 비슷한 수정만 반복한다.
- 대화가 길어지자 처음 정한 이름이나 규칙을 지키지 않는다.
- 만든 것을 다른 사람에게 보여 줘도 되는지 불안하다.

이 문제들은 하나의 작업 흐름으로 연결됩니다.

| 단계 | 내가 할 일 | 읽을 곳 |
| --- | --- | --- |
| **큰 그림** | 앱의 세 역할과 도구가 대신하는 범위를 구분한다 | 00 |
| **시작하기 전** | 목표와 성공 조건을 적고 되돌릴 지점을 만든다 | 01 → 02 |
| **만드는 동안** | 현재 상태·원하는 결과·확인 방법·금지 범위를 한 번에 하나씩 지시한다 | 03 → 04 |
| **결과를 받으면** | 직접 동작·잘못된 입력·재시작·기존 기능·변경 파일을 확인한다 | 05 → 실습 |
| **막혔을 때** | 되돌리기·작게 나누기·새 대화·다른 접근 중 하나를 고른다 | 06 → 07 |
| **내보내기 전** | 공개 위험을 확인하고 사람의 판단이 필요한 선에서 멈춘다 | 08 → 09 |

## 먼저 바꿀 세 가지

전체를 읽기 전에, 다음 요청부터 이 세 가지만 적용해도 됩니다.

1. **변경 전에 저장 지점을 만듭니다.**

   > "지금 상태를 ‘완료 표시 기능 작업 전’이라는 메시지로 커밋하고, 커밋 해시를 보여 줘."

2. **한 번에 하나의 변화만 지시합니다.**

   > "할 일을 클릭하면 취소선이 생기게 해 줘. 삭제 기능과 디자인은 이번에는 건드리지 마."

3. **완료 여부를 내가 확인할 방법까지 요구합니다.**

   > "어떤 순서로 클릭하고 무엇이 보이면 성공인지 알려 줘."

이후의 기본 주기는 짧습니다.

**저장 → 하나만 지시 → 직접 확인 → 저장**

한 주기가 짧으면 문제가 생겼을 때 방금 변경만 살펴보거나 되돌릴 수 있습니다. 이 흐름은 [04 한 번에 하나만](04-one-at-a-time.md)과
[05 코드를 몰라도 하는 확인](05-verify-without-reading.md)에서 구체적으로 다룹니다.

## 직접 확인한 실습

[다섯 가지 확인 실습](../../labs/five-checks/README.md)에는 같은 요청을 처리한 것처럼 보이는 할 일 앱 세 판이 있습니다.

- 한 판은 정상적으로 동작합니다.
- 한 판은 완료 표시가 되지만 새로고침하면 목록이 사라집니다.
- 한 판은 완료 표시가 되지만 가운데 항목을 지우면 맨 위 항목이 사라지고, 요청하지 않은 디자인과 파일도 추가돼 있습니다.

세 판은 저자가 의도적으로 만든 고정 fixture입니다. 특정 AI가 실제로 이 코드를 생성했다는 뜻은 아닙니다. macOS의 Chrome과 임시 Git
저장소에서 다섯 가지 확인을 실행했으며, 결과는 [실습 검증 기록](../../labs/five-checks/VALIDATION.md)에 남겼습니다.

## 학습 달성 목표(Learning Objective)

이 가이드를 마치면 다음을 할 수 있습니다.

- 만들기 전에 사용자·동작 순서·성공 조건·이번에 하지 않을 일을 적습니다.
- Frontend·Backend·Database의 역할과 개발·배포 도구가 대신하는 범위를 구분합니다.
- 변경 전후로 되돌릴 수 있는 커밋을 남깁니다.
- 요청을 한 번에 확인할 수 있는 크기로 나눕니다.
- 코드를 읽지 않고도 다섯 가지 확인을 수행합니다.
- 같은 실패가 반복될 때 되돌리거나 접근을 바꿉니다.
- 새 대화에 필요한 현재 상태와 규칙을 인계합니다.
- 공개 전 Secret·실행 환경·입력·남은 흔적·license를 점검합니다.
- 돈·개인정보·인증·법·안전처럼 전문가 확인이 필요한 범위를 구분합니다.

## 선행 자료와 범위

이 가이드는 [AI로 코딩하는 사람을 위한 Git](../git-for-vibe-coders/README.md)의 자매편입니다. Git 가이드가 되돌릴 수 있는
상태를 만드는 법을 다룬다면, 이 가이드는 되돌릴 일을 줄이고 문제를 일찍 발견하는 습관을 다룹니다. Git을 아직 쓰지 않는다면
자매편의 10분 경로를 먼저 따라 해보세요.

다음 내용은 이 가이드에서 다루지 않습니다.

- 프로그래밍 언어·framework·architecture의 상세 학습
- 실제 서비스의 서버·도메인·트래픽·모니터링 운영
- 팀 개발 절차와 전문적인 코드 리뷰
- 특정 AI 코딩·hosting 도구의 화면이나 단계별 사용법
- 저작권·라이선스·법률에 대한 최종 판단
