# 02. 규칙 — 잘못된 데이터가 들어오는가

[← 01 저장](01-persistence.md) · [전체 목차](README.md) · [03 동시 변경 →](03-atomicity.md)

입력칸이 잘못된 값을 막더라도 API로 직접 보낸 요청이 DB에 들어갈 수 있습니다. 이번에는 **화면을 거치지 않는 잘못된 입력을 DB가 거절하는지** 확인합니다.

## 고정된 조건

한 사용자는 한 모임에 한 번만 신청할 수 있고, 신청 내역은 존재하는 모임을 가리켜야 합니다. 기준 데이터는 가상 사용자 A·B와 모임 세 개입니다. 정상 신청 한 건을 만든 뒤 잘못된 입력을 시도합니다.

| 입력 | 기대 결과 | 이유 |
| --- | --- | --- |
| A가 존재하는 모임에 처음 신청 | 한 행 생성 | 정상 경로 |
| A가 같은 모임에 다시 신청 | 새 행 없음 | 두 열을 묶은 고유값 규칙 |
| 존재하지 않는 모임 ID로 신청 | 새 행 없음 | 연결할 모임이 없음 |

오류 문구는 버전이나 호출 경로에 따라 달라질 수 있습니다. **오류 종류와 변경 후 행의 개수·연결 관계로** 판정합니다. 의도한 규칙을 보기 전에 로그인부터 실패했다면 이 시나리오를 검증한 것이 아닙니다.

## 왜 UI 확인만으로는 부족할까?

버튼을 비활성화하면 사용자가 실수하기 어렵습니다. 그러나 다른 클라이언트, 오래된 화면, 재시도, 직접 API 요청에도 같은 규칙이 필요합니다. 제약조건은 그 규칙을 DB에 둡니다.

고유값 제약조건이 “값 두 개를 묶어 비교한다”는 점을 눈여겨보세요. 사용자 ID 하나만 고유하게 만들면 A는 다른 모임에도 신청할 수 없게 됩니다. 모임 ID 하나만 고유하게 만들면 누구든 첫 신청자 한 명만 들어갈 수 있습니다. 우리가 원하는 규칙은 **같은 사용자와 같은 모임의 조합이 중복되지 않는 것**입니다.

## 실행 결과를 읽는 순서

[준비와 공통 실행](README.md)을 완료한 뒤 검증 결과에서 제약조건 항목을 찾습니다. 먼저 정상 행을 만들 수 있었는지 확인하고, 잘못된 입력의 오류와 최종 행 수를 함께 적습니다.

| 관찰 | 내 기록 |
| --- | --- |
| 정상 신청 후 행 수 | |
| 같은 신청 반복의 오류 종류 | |
| 반복 후 행 수 | |
| 없는 모임을 가리키는 행이 남았는가? | |

테스트가 거절을 확인하기 위해 일부러 잘못된 요청을 보냅니다. 로그에 예상된 오류가 있다는 이유로 실습 실패로 분류하지 마세요. 스크립트가 예상한 거절과 DB 상태를 확인해 통과로 판정하는지 봅니다.

## AI의 수정 제안 검토하기

> “중복 오류를 없애기 위해 DB의 unique 규칙을 지우지는 마. 사용자가 같은 신청을 반복하면 이해할 수 있는 안내를 보여 주고, 최종 신청은 한 건만 남아야 해. 다른 모임에는 신청할 수 있어야 해.”

에러를 없애는 것과 잘못된 데이터를 막는 것은 별개의 목표입니다. 규칙을 제거하면 에러는 사라질 수 있지만 중복 행이 생기는 문제가 남습니다.

## 다음 문제와 초기화

이 실습이 통과해도 마지막 자리 경쟁까지 해결됐다고 판단하지 않습니다. 중복 조합과 정원은 서로 다른 규칙입니다. [03 동시 변경](03-atomicity.md)으로 이어집니다.

공통 검증을 다시 실행하면 같은 fixture를 기준으로 반복합니다. 직접 만든 연습 데이터를 모두 비우려면 [튜토리얼 초기화](../../tutorials/study-signup-db/01-prepare.md)를 사용합니다. 실제 서비스에서 제약조건을 추가하기 전에는 기존 데이터가 그 규칙을 어기는지도 먼저 조사해야 합니다.
