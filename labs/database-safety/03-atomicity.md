# 03. 동시 변경 — 마지막 자리를 둘이 차지하는가

[← 02 규칙](02-constraints.md) · [전체 목차](README.md) · [04 접근 →](04-authorization.md)

마지막 한 자리를 A와 B가 동시에 신청합니다. 두 화면 모두 잠시 “자리 있음”을 봤더라도 **완료된 신청은 한 건이어야 합니다.** 또 신청 과정이 실패하면 중간 변경만 남아서는 안 됩니다.

## 시나리오 A — 마지막 자리

고정된 모임의 정원은 1명이고, 처음 신청 수는 0입니다. 두 로그인 사용자가 거의 동시에 신청 요청을 보냅니다.

| 관찰할 값 | 기대 결과 |
| --- | --- |
| A·B 중 성공한 요청 수 | 1 |
| 성공하지 않은 요청 수 | 1 |
| 최종 신청 수 | 1 |
| 최종 신청의 소유자 | 성공한 사용자와 일치 |

먼저 요청한 것처럼 보이는 사용자가 반드시 이긴다고 기대하지 않습니다. 네트워크와 DB 처리 순서가 결과에 영향을 줍니다. 이번 판정의 핵심은 승자 이름이 아니라 **정원을 넘지 않으면서 한 신청은 성공하는 것**입니다.

## 시나리오 B — 작업 중간에 실패

트랜잭션(transaction)은 여러 DB 변경을 하나의 작업으로 묶는 단위입니다. 작업이 성공하면 함께 확정하고, 실패하면 그 작업의 변경을 되돌릴 수 있습니다. `[원리]` [PostgreSQL 트랜잭션 설명](https://www.postgresql.org/docs/current/tutorial-transactions.html)

검증 코드는 일부러 실패하는 작업을 수행한 뒤, 중간에 만들려던 변경이 남았는지 확인합니다. 실패 자체가 성공 판정은 아닙니다. **처음 상태와 실패 후 상태를 비교해 부분 변경이 남지 않았는지** 확인해야 합니다.

## 실행 결과에서 확인하기

[공통 실행](README.md)의 동시 신청과 원자성 항목을 읽습니다. 결과를 보기 전에 예상치를 적어 보세요.

| 항목 | 실행 전 예상 | 실제 결과 |
| --- | --- | --- |
| 정원 1명에 성공할 요청 수 | 1 | |
| 최종 신청 수 | 1 | |
| 강제로 실패한 트랜잭션의 잔존 변경 | 0 | |

두 요청을 차례대로 호출해 두 번째가 실패한 결과는 동시 요청 확인이 아닙니다. 검증 코드는 요청을 겹쳐 보내는 경로와 마지막 DB 상태를 모두 확인합니다. 이 작은 실행이 대규모 운영 부하 시험을 대신하지는 않습니다.

## 신청 함수가 하는 일

이 앱의 DB 함수는 로그인 사용자를 확인하고, 대상 모임의 동시 변경을 조정한 뒤, 정원과 신청 여부를 검사해 행을 만듭니다. 여러 화면이 따로 “현재 몇 명인가”를 계산하고 각자 저장하는 경로를 두지 않습니다.

트랜잭션이라는 이름만 붙이면 모든 경쟁이 해결되는 것은 아닙니다. 어느 데이터를 잠그거나 어떤 방식으로 갱신할지에 따라 결과가 달라집니다. 또한 DB 밖의 이메일 전송이나 결제는 DB 트랜잭션으로 자동 취소되지 않습니다. 이번 예제는 DB 안의 모임·신청 상태에 한정합니다.

## AI에게 요청할 수정

> “정원 1명인 모임에 A와 B가 거의 동시에 신청해도 한 명만 성공해야 해. 화면에서 버튼을 잠그는 것 외에 DB 안에서 요청을 어떻게 조정하는지 설명하고, 두 요청을 겹쳐 보내 최종 신청이 한 건인지 확인해 줘. 실패한 작업의 일부 변경도 남지 않아야 해.”

## 초기화와 다음 확인

공통 검증은 자신의 fixture 신청을 정리하고 같은 경쟁 조건을 다시 만듭니다. 반복마다 같은 사용자가 이길 필요는 없습니다. 직접 사용하던 신청 내역이 중요하다면 검증 전 다른 환경에 보존해야 합니다. 이 연습 DB에는 실제 신청을 넣지 않습니다.

다음은 정원 안에 들어온 사용자가 **다른 사람의 신청까지 바꿀 수 있는지** 확인하는 단계입니다.
