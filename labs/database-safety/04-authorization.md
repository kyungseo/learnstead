# 04. 접근 — 다른 사람의 데이터도 바꿀 수 있는가

[← 03 동시 변경](03-atomicity.md) · [전체 목차](README.md) · [05 구조 변경 →](05-migration.md)

다른 사용자의 신청을 읽고 바꾸려 합니다. 로그인한 A·B와 비로그인 요청을 구분합니다. **화면에서 감춰진 정보가 API에서도 보호되는지, 거절된 요청 뒤 DB가 그대로인지** 확인합니다.

## 고정된 시나리오

A와 B가 같은 모임에 각각 신청했습니다. A·B의 인증 토큰은 서로 다릅니다. 비로그인 요청은 사용자 토큰이 없습니다. 검증은 실제 로그인으로 얻은 사용자 상태로 API를 호출합니다.

| 요청 | 기대 결과 |
| --- | --- |
| A가 자기 신청 읽기 | 자기 행이 보임 |
| A가 B의 신청 읽기 | B의 행이 반환되지 않음 |
| 비로그인으로 테이블 읽기 | 데이터 접근 불가 |
| B가 자기 신청 생성 | B의 행 생성 |
| A가 B의 사용자 ID로 생성 시도 | B 소유의 행 생성 안 됨 |
| A가 B의 신청 메모 수정 | B의 메모가 바뀌지 않음 |
| A가 B의 신청 삭제 | B의 신청이 남음 |
| A가 자기 메모 수정·신청 취소 | 허용한 동작이 정상 반영 |

공개 모임을 비로그인 사용자에게도 보여 줄지는 제품 정책입니다. **이번 예제는 모임 목록도 로그인 사용자에게만 제공합니다.** 다른 앱에 이 표를 그대로 복사하기보다 먼저 공개 범위를 정하세요.

## 거절을 세 가지로 읽기

접근 제한은 서로 다른 형태로 관찰될 수 있습니다.

1. 요청이 권한 오류로 거절됩니다.
2. 조회는 성공하지만 `[]`라는 빈 배열이 반환됩니다.
3. 수정·삭제는 응답을 돌려주지만 적용된 행이 0개입니다.

두 번째나 세 번째에서 응답 상태만 보고 “우회 성공”이라고 판단하지 않습니다. **원래 소유자로 다시 읽어 행과 값이 유지되는지** 확인해야 합니다. 반대로 오류 응답만 보고 안심하지도 않습니다. 변경이 이미 남아 있다면 보호에 실패한 것입니다.

## 소유자 위조 확인

브라우저가 `user_id`라는 값을 보낼 수 있다고 합시다. A가 그 값을 B의 ID로 바꿔 전송하면 어떻게 될까요? 서버나 DB가 로그인 사용자의 ID와 비교하지 않는다면 데이터의 소유자를 조작할 수 있습니다.

이번 앱은 정상 신청 경로에서 인증된 사용자를 기준으로 처리하고, 직접 테이블에 잘못된 소유자를 쓰려는 요청도 거절하는지 확인합니다. 입력값을 믿는 것과 인증 결과를 사용하는 것의 차이입니다.

## 실행과 기록

[공통 실행](README.md) 결과에서 사용자별 접근 항목을 찾습니다. 아래 네 가지를 한 줄씩 기록하세요.

| 요청자 | 작업·대상 | 응답 | 소유자가 다시 본 상태 |
| --- | --- | --- | --- |
| A | B의 신청 조회 | | |
| A | B 소유로 신청 생성 | | |
| A | B의 메모 수정 | | |
| A | B의 신청 삭제 | | |

정상적인 A의 작업까지 모두 막힌다면 안전하게 완성된 것이 아닙니다. 필요한 기능이 허용되고 다른 사람의 데이터는 보호되어야 합니다. 그래서 성공과 거절을 한 묶음으로 검사합니다.

## 관리자 권한으로 대신 검사하지 않기

관리자 도구는 데이터를 모두 볼 수 있어도 이상하지 않을 수 있습니다. 일반 사용자의 접근을 검증할 때 관리자 키나 DB 소유자 연결을 쓰면 검사하려던 규칙을 건너뛸 수 있습니다. `[문서 확인 · 2026-09-13]` [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [API 키의 권한](https://supabase.com/docs/guides/getting-started/api-keys)

> “각 요청이 A·B·비로그인 중 누구의 권한으로 실행됐는지 표시해 줘. 응답 상태뿐 아니라 반환된 행 수와 실제 변경 결과를 비교해. 관리자 권한으로 통과한 결과는 일반 사용자 검사로 세지 마.”

## 초기화

공통 검증을 반복하면 fixture의 신청을 다시 준비합니다. 임의로 RLS를 끄거나 테이블 권한을 넓혀 실패를 해결하지 마세요. 다시 원본 상태가 필요하면 [튜토리얼 초기화](../../tutorials/study-signup-db/01-prepare.md)에서 이 연습 프로젝트만 초기화합니다.
