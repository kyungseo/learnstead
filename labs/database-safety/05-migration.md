# 05. 구조 변경 — 예전 데이터도 살아남는가

[← 04 접근](04-authorization.md) · [전체 목차](README.md) · [06 복원 →](06-restore.md)

앱을 쓰던 중 “신청할 때 메모도 남기고 싶다”는 요청이 생겼습니다. 새 DB에서는 잘 동작하지만 **이미 신청한 사람들의 데이터에도 변경을 적용할 수 있는지** 확인합니다.

## 고정된 시나리오

초기 구조에는 신청 메모가 없습니다. 예전 구조에 신청 데이터를 먼저 넣고, 다음 migration으로 `note` 열을 추가합니다. 이번 예제는 기존 행에 빈 문자열을 기본값으로 제공하며 메모를 빈칸으로 둘 수 있게 합니다.

| 시점 | 기대 결과 |
| --- | --- |
| 예전 구조에 신청을 넣음 | 모임·사용자와 연결된 신청 존재 |
| 메모 열 추가 | 기존 신청의 ID·소유자·모임 연결 유지 |
| 기존 신청 조회 | `note`를 읽을 수 있고 기본값 적용 |
| 새 DB에 처음부터 두 migration 적용 | 최신 구조와 같은 규칙으로 시작 가능 |

마지막 행과 두 번째 행은 다른 검사입니다. 빈 DB에 최신 구조를 만드는 데 성공해도, 예전 데이터에 이어서 변경할 때 실패할 수 있습니다.

## migration 읽기

튜토리얼의 `supabase/migrations/20260913000100_initial.sql`은 처음 구조를 만들고, `20260913000200_registration_note.sql`은 그다음 변경을 기록합니다. migration은 **DB가 어떤 순서로 달라졌는지 재현할 수 있게 남긴 SQL**입니다. `[문서 확인 · 2026-09-13]` [Supabase migration 안내](https://supabase.com/docs/guides/deployment/database-migrations)

이번에는 열을 추가하는 작은 변경입니다. 열 삭제·타입 변경·이름 변경·대량 데이터 변환은 보존할 값과 앱 호환성을 따로 검토해야 합니다. 기본값만 넣으면 모든 변경이 안전하다는 뜻은 아닙니다.

## 실행 결과에서 볼 것

[공통 실행](README.md)은 기존 데이터가 있는 변경 검사를 격리된 DB에서 수행합니다. 원래 DB의 SQL 파일을 손으로 고치거나 운영 DB를 초기화하지 않습니다.

| 비교 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 신청 행 수 | | |
| 신청 ID | | |
| 모임·사용자 연결 | | |
| 메모 열의 값 | 없음 | |

**행 수가 같다는 사실만으로 보존됐다고 결론 내리지 않습니다.** 누가 어떤 모임에 신청했는지도 그대로여야 합니다. 관계와 주요 값을 함께 비교합니다.

## 코드 되돌리기만으로 충분하지 않은 이유

앱 코드를 예전 버전으로 되돌려도 이미 추가한 DB 열은 자동으로 사라지지 않습니다. 반대로 열을 지우면 거기에 새로 저장한 메모도 잃을 수 있습니다. 소스 코드의 저장 지점과 DB 데이터의 복구 지점은 따로 생각해야 합니다.

실패 대응을 계획할 때는 “앱만 먼저 되돌릴 수 있는가”, “DB를 다시 바꾸어도 새 데이터가 보존되는가”, “백업 복원이 필요한가”를 구분합니다. 실제 운영에서의 선택은 변경 내용과 중단 허용 시간에 따라 달라집니다.

## AI에게 요청할 변경 계획

> “기존 신청이 있는 상태에서 메모 열을 추가하려고 해. 기존 행이 어떻게 채워지는지, 예전 앱과 새 앱이 각각 읽을 수 있는지, 사용자별 수정 권한이 유지되는지 설명해 줘. 빈 DB와 기존 데이터가 있는 DB를 각각 검증해. 실패하면 어떤 변경을 되돌리고 어떤 데이터는 보존해야 하는지도 적어 줘.”

## 초기화

격리된 검증 DB는 검증 도구가 만든 범위에서 정리합니다. 튜토리얼 DB를 처음부터 다시 만들려면 별도의 [초기화 명령](../../tutorials/study-signup-db/01-prepare.md)을 사용합니다. 그것은 기존 데이터를 보존하는 migration이 아니라 **연습 데이터를 버리는 재시작**이라는 점을 구분하세요.
