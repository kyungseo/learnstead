# 06. 복원 — 백업에서 정말 되살릴 수 있는가

[← 05 구조 변경](05-migration.md) · [전체 목차](README.md) · [가이드로 →](../../guides/database-for-vibe-coders/README.md)

백업 파일이 만들어졌다는 보고를 받았습니다. 이제 **다른 DB에 복원한 뒤 행·관계·접근 규칙을 확인해** 실제로 되살릴 수 있는지 판정합니다.

## 먼저 범위를 정하기

이 실습은 가상 모임과 신청 데이터를 이용한 DB 복원 연습입니다. 실제 서비스의 장애를 일으키거나 운영 DB를 덮어쓰지 않습니다. 검증 도구가 만든 별도 대상에 복원합니다.

| 백업에 담으려는 것 | 복원 뒤 확인할 것 |
| --- | --- |
| 모임·신청 데이터 | 행 수와 중요한 값 |
| 모임과 신청의 연결 | 없는 모임을 가리키는 신청이 없는지 |
| 구조와 제약조건 | 중복·잘못된 연결이 다시 거절되는지 |
| 접근 규칙 | 본인과 다른 사용자의 접근 범위 |

파일 하나를 보관했다고 전체 앱이 복구되는 것은 아닙니다. 이번 검증의 정확한 포함 범위와 실행 결과는 [검증 기록](VALIDATION.md)에 따로 남깁니다.

## 실습 순서

[공통 실행](README.md)의 복원 검사는 다음 순서로 진행합니다.

1. 알려진 모임·신청 fixture를 준비합니다.
2. DB 백업을 만듭니다.
3. 검증용 복원 대상을 따로 만듭니다.
4. 백업을 그 대상에 복원합니다.
5. 원본과 복원본의 행·관계·접근 규칙을 비교합니다.
6. 검증 도구가 만든 별도 DB는 정리하고, 결과 JSON과 논리 백업 파일은 로컬에 보관합니다.

복원 명령이 종료 코드 0으로 끝난 것은 중간 성공입니다. 마지막 비교까지 통과해야 이번 실습의 성공입니다. 백업 전부터 잘못된 데이터였다면 복원본도 잘못된 상태일 수 있으므로, 기준 데이터를 먼저 정합니다.

## 관찰 카드

| 항목 | 기준 | 복원본 |
| --- | --- | --- |
| 모임·신청 행 수 | | |
| 신청의 소유자·모임 ID | | |
| 메모 같은 중요한 값 | | |
| 중복 신청·없는 모임 연결 | 거절 | |
| 다른 사용자의 신청 접근 | 제한 | |

복원 직후 앱이 열렸다는 사실만 보고 완료하지 마세요. 빈 DB에서도 화면은 열릴 수 있습니다. 실제 사용자의 관점에서 필요한 데이터와 권한이 함께 돌아왔는지 확인해야 합니다.

## 첨부 파일은 별도로 생각하기

앱에 문서나 사진을 붙인다면 DB에는 파일 이름·경로·소유자만 저장하고 파일 본체는 별도 저장소에 둘 수 있습니다. 이 경우 DB 백업에 경로가 남아 있어도 사진 파일이 없으면 열 수 없습니다.

Supabase의 DB 백업에는 Storage API로 저장한 파일 본체가 포함되지 않습니다. `[문서 확인 · 2026-09-13]` [공식 백업 범위](https://supabase.com/docs/guides/platform/backups). 이 실습은 첨부 파일 업로드나 Storage 전체 복원을 구현·검증하지 않습니다. 실제 앱에 추가한다면 파일 본체의 백업·복원·접근 권한도 별도 항목으로 넣어야 합니다.

## 백업을 맡길 때 필요한 질문

> “백업에 DB 행·구조·접근 규칙·사용자 계정·첨부 파일 중 무엇이 포함되는지 나눠 적어 줘. 원본을 덮어쓰지 않는 별도 대상에 복원하고, 행 수뿐 아니라 모임·신청의 관계와 사용자별 접근도 확인해 줘. 확인하지 않은 범위는 성공으로 표시하지 마.”

운영에서는 백업 주기와 보관 장소, 잃어도 되는 데이터의 최대 시간 범위, 복구까지 걸려도 되는 시간을 정해야 합니다. 이 실습의 작은 데이터에서 복원된 결과를 실제 서비스의 복구 시간 보장으로 사용하지 않습니다.

## 마무리와 정리

검증 도구는 자신이 만든 별도 검증 DB를 정리합니다. `app/.local/verification.json`과 `app/.local/practice-backup.sql`은 남습니다. 논리 백업에는 가상 Auth 계정 정보도 들어 있으므로 공개 저장소나 게시물에 첨부하지 않습니다. 실습을 마친 뒤 필요 없다면 Finder에서 이 두 파일만 직접 삭제할 수 있습니다. `.local/public-config.json`은 앱 재실행에 쓰므로 결과 파일과 구분합니다. 학습을 마쳤다면 [튜토리얼의 멈추기](../../tutorials/study-signup-db/05-finish.md)로 로컬 DB를 멈춥니다. Docker의 전체 볼륨 정리는 다른 프로젝트의 데이터를 지울 수 있으므로 이 실습의 정리 방법으로 사용하지 않습니다.

여섯 실습의 기록을 모으면 “저장됐다”라는 한 문장을 저장 위치·데이터 규칙·동시 변경·권한·구조 변경·복원이라는 여섯 근거로 설명할 수 있습니다. 실제 앱에서 AI에게 맡길 다음 변경에도 이 기록을 출발점으로 사용하세요.
