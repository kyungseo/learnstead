# 검증 기록

검증은 화면·API·DB 상태·복원을 구분합니다. 같은 명령이 한 환경에서 통과했다는 사실을 다른 OS나 클라우드의 동작 보장으로 확대하지 않습니다.

## SQLite — 실행 검증 · 2026-09-13

| 항목 | 실제 환경 |
| --- | --- |
| OS·아키텍처 | macOS 26.6.2 · arm64 |
| Python | 3.14.7 |
| 외부 Python 패키지 | 사용하지 않음 |
| 데이터 | `데이터 이야기` 한 행, 고정된 교육용 fixture |
| 실행 위치 | 독립된 임시 연습 폴더. 기존 DB는 사용하지 않음 |

### 실제 실행한 명령

`labs/database-safety`를 기준으로 스크립트를 실행했습니다. 수동 경로의 `practice.sqlite`는 별도 임시 폴더에 두었으며 아래에서는 공개 예시 경로로 표시합니다.

```bash
python3 code/sqlite_lab.py
python3 code/sqlite_lab.py add --db practice.sqlite --title '데이터 이야기'
python3 code/sqlite_lab.py list --db practice.sqlite
python3 code/sqlite_lab.py add --db practice.sqlite --title '데이터 이야기'
python3 code/sqlite_lab.py list --db practice.sqlite
python3 code/sqlite_lab.py reset --db practice.sqlite --confirm-local-reset
python3 code/sqlite_lab.py list --db practice.sqlite
```

| 검사 | 실제 결과 |
| --- | --- |
| 메모리 DB를 새 연결로 열기 | 0행 |
| 파일 DB를 새 연결로 열기 | 제목이 같은 1행 유지 |
| 두 INSERT 중 두 번째의 고유값 위반 | 트랜잭션 취소, 기존 1행 유지 |
| 기존 행에 메모 열 추가 | ID·제목 보존, 메모 기본값 빈 문자열 |
| 원본 행 삭제 | 원본 0행 관찰 |
| 별도 백업 파일 조회 | 기존 1행·메모 보존, `integrity_check`가 `ok` |
| 자동 비교 합계 | 6개 판정 `PASS`, 종료 코드 0 |
| 수동 추가·별도 조회 | ID 1·제목 `데이터 이야기` |
| 수동 중복 추가 | `UNIQUE constraint failed: books.title`, 종료 코드 1 |
| 중복 거절 후 재조회 | 여전히 1행 |
| 수동 reset 후 재조회 | `[]`, 0행 |
| 정리 | 테스트가 만든 임시 DB만 정리 |

메모리 저장의 소멸은 SQLite 설정의 정상 동작입니다. 지속 저장이 필요한 앱의 요구사항과 비교할 때 실패 사례로 사용하는 것입니다. `PASS`는 정해 둔 차이를 관찰했다는 의미입니다.

| 항목 | 실제 환경·조건 |

| OS·아키텍처 | macOS 26.6.2 · arm64 |
| Node.js | 24.19.0 |
| Supabase CLI | 2.117.0 — 잠금 파일의 고정 버전 |
| PostgreSQL | 17.6 |
| Docker | 29.7.2 |
| 시작 데이터 | 모임 3개·신청 0개, 연습 사용자 A·B |
| 연결 | 로컬 Docker, 컴퓨터 내부 주소로 제한 |
| 최종 검증 시각 | 2026-09-13 01:48 KST (JSON에는 UTC로 기록) |
| 전체 판정 | 14개 `PASS`, 종료 시 신청·정원 카운터 0 |

### 실제 실행한 경로

`tutorials/study-signup-db/app`에서 패키지를 설치하고 로컬 DB를 시작한 뒤 연습 계정을 준비했습니다. 다음 `verify`는 화면을 조작하지 않고 실제 Auth·REST 요청과 DB 상태를 확인합니다.

```bash
npm ci
npm run db:start
npm run setup
npm run verify
```

완료 메시지는 `검증 완료: 14개 판정 PASS.`였으며 `.local/verification.json`에 환경과 판정 이름이 기록됐습니다. 아래는 그 결과와 검증 코드가 확인한 값을 함께 정리한 표입니다.

| 번호 | 확인한 상황 | 실제 결과 |
| --- | --- | --- |
| 1 | A·B 비밀번호 로그인 | 두 사용자 모두 성공 |
| 2 | 비로그인 테이블·신청 함수 접근 | HTTP 401. 로그인 사용자는 모임 3개 조회 |
| 3 | 본인·타인 신청 조회 | A의 신청 1행, A에게 B의 신청은 0행 |
| 4 | A가 B의 ID를 넣어 직접 신청 | HTTP 403 · SQLSTATE `42501`, 위조 행 생성 거절 |
| 5 | 중복 신청 | HTTP 409 · `23505`, 실패한 신청의 정원 카운터도 원상복귀 |
| 6 | 없는 모임에 신청 | HTTP 409 · `23503`, 잘못된 신청 거절 |
| 7 | 메모 수정·타인 변경 | 본인 메모 수정 성공. 타인 수정·삭제는 HTTP 200·`[]`, 타인 행 유지 |
| 8 | 소유자·모임·정원 직접 변경 | HTTP 403 |
| 9 | 정원 1명에 동시에 두 신청 | 한 명 HTTP 200, 한 명 HTTP 400·`23514`, 최종 신청·카운터 각각 1 |
| 10 | 신청 직후 강제 오류 | `22012`, 신청과 정원 변경 모두 rollback |
| 11 | 기존 데이터에 메모 migration | 행 수와 메모 이외의 모든 값 동일, 새 메모 기본값 빈 문자열 |
| 12 | 복원 전 실패 fixture | 별도 DB에서 신청 1행을 삭제한 차이를 확인 |
| 13 | 별도 DB로 논리 백업 복원 | 모든 신청 값·정원 동일, 정책 5개와 메모 권한 복원, 아래 역할 검사 통과 |
| 14 | 취소·정리 | 본인 취소 허용, 신청 0개·정원 카운터 합계 0, 도구가 만든 검증 DB 정리 |

`SQLSTATE`는 PostgreSQL이 오류 종류를 구분하는 코드입니다. 위 코드들은 의도한 실패를 확인한 결과이지, 예제를 통과시키려고 없애야 할 오류가 아닙니다.

### 기존 데이터 변경을 확인한 방법

별도 검증 DB에 가상 신청 데이터를 복사하고 메모 열이 없는 상태를 만든 뒤 두 번째 migration을 적용했습니다. `note`를 제외한 신청 행의 모든 값이 기준 데이터와 같은지 비교했고, 새 `note`는 모두 빈 문자열인지 확인했습니다. 빈 DB에서 처음부터 migration을 적용하는 경로는 로컬 DB 시작 경로에서 별도로 확인했습니다.

### 복원 범위와 권한 검사

`pg_dump`로 `public`·`auth` 스키마의 논리 백업을 만들고 같은 로컬 PostgreSQL 안의 별도 DB에 복원했습니다. 원본 DB를 덮어쓰지 않았습니다. 복원본에서 삭제 전후 차이를 먼저 관찰한 뒤 백업으로 다시 구성했습니다.

- A·B의 사용자 식별자를 각각 설정한 `authenticated` 역할에서 자기 신청 ID 목록이 기준과 정확히 같았습니다.
- 각 사용자에게 본인 메모 수정은 `UPDATE 1`, 타인 메모 수정·삭제는 `UPDATE 0`·`DELETE 0`이었습니다. 이 역할 검사는 트랜잭션 안에서 수행하고 되돌렸습니다.
- `anon` 역할의 조회는 `42501`로 거절됐습니다.
- 중복 신청은 `23505`, 없는 사용자 연결은 외래 키 오류 `23503`으로 거절됐습니다.
- 모든 역할·오류 검사 후 신청 행이 백업 기준값과 같은지 다시 비교했습니다.

**원본 DB는 실제 Auth 로그인과 REST로, 복원본은 SQL 역할·사용자 식별자로 검사했습니다.** 복원본에 Auth 서비스를 새로 연결해 웹 로그인을 완주했다는 결과는 아닙니다. 또한 같은 PostgreSQL 인스턴스 안의 논리 복원이므로 장비 전체 장애·다른 서버·다른 DB 버전의 복구를 검증한 것은 아닙니다.

### 남기는 것과 정리하는 것

도구가 만든 migration·복원 검증 DB 두 개는 완료 후 정리했습니다. `app/.local/verification.json`과 `app/.local/practice-backup.sql`은 남겼습니다. 백업에는 가상 Auth 계정 정보가 포함되므로 공개하지 않습니다. 필요한 관찰을 기록한 뒤 자신이 만든 두 파일만 선택적으로 삭제할 수 있습니다. Storage 파일 본체·클라우드 설정·PITR은 이 백업에 포함하지 않습니다.

명시적 초기화로 새로 만든 DB에서도 같은 14개 판정을 다시 통과했습니다. 신청·메모를 남긴 상태의 중지·재시작 보존과 초기화 전후 비교는 [튜토리얼 검증 기록](../../tutorials/study-signup-db/VALIDATION.md)에 있습니다.

## 확인하지 않은 범위

- Node.js 24 이외의 메이저 버전, Windows·Linux 실환경, 호스팅된 Supabase, 인터넷 공개 배포
- 실제 사용자·개인정보, 운영 메일과 인증 복구, 결제
- Storage 파일 본체와 앱 배포 설정의 백업·복원
- 복원본에서 Auth 서비스를 재연결한 웹 로그인 전체 경로
- 시점 복구(PITR), 운영 규모의 부하와 복구 시간
- AI 모델별 코드 생성 성공률이나 보안 성능
