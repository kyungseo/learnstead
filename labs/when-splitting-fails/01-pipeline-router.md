# 01. 파이프라인과 라우터 — 격리로 토큰이 줄고, 분류가 틀리면 전부 틀린다

> [목차](README.md) · [다음: 02. 오케스트레이터-워커 →](02-orchestrator-workers.md)

## 목표

같은 질문을 단일 호출·파이프라인·라우터로 돌립니다. 파이프라인은 토큰을 줄였고, 라우터는 **기준 질문조차 엉뚱한 담당에게 보냈습니다.**
각 단계의 출력을 확인해 실패 지점을 찾고, 분류에 실패하면 전체 문서로 다시 답하는 경로를 시험합니다.

> **검증 상태:** 모든 명령을 Apple M4 Pro·24GB Mac, Ollama 0.33.0, `gemma3:4b`(temperature 0)에서 실행했습니다. `[실행 검증 · 2026-08-30]`
> 초판(Ollama 0.32.7, 2026-08-23)과 라우터 결과가 달라진 곳이 있습니다 — §3에 그대로 적었습니다.


## 0. 기준선 — 단일 호출

```bash
cd labs
python3 patterns.py single "관리자는 연차를 며칠까지 이월할 수 있나요?"
```

**실제 출력:**

```text
  [단일] 0.6초 · 토큰 508→19 · 이월 한도는 일반 직원 5일, 관리자 10일이다.
[single] 호출 1회 · 입력 508 + 출력 19 토큰 · 0.6초
```

**★ 성공 판정:** `[single] 호출 1회`가 찍히고 답에 "10일"이 있습니다. 첫 호출은 모델 적재 때문에 4~5초가 걸리고, 이후 0.6~1.3초입니다.
**이 세 항목(1회 · 508 · 정답)이 이 실습의 비교 기준입니다.** 아래 모든 방식을 여기에 비교합니다.

## 1. 파이프라인 — 순서를 내가 정한다

`run_pipeline()`은 세 단계입니다. 분류 단계는 관련 문서를 고르고, 답변 단계는 그 문서만 읽으며, 마지막 단계는 답변의 말투를 다듬습니다.

```python
topic = ask("질문이 어느 규정에 속하는지 …", q)            # 1. 분류 (자유 텍스트)
draft = ask(ANSWER_RULE, f"<규정>\n{docs[key]}…", q)      # 2. 그 규정만 넣고 답변
final = ask("사내 안내 말투로 다듬는다 …", draft)          # 3. 다듬기
```

```bash
python3 patterns.py pipeline "관리자는 연차를 며칠까지 이월할 수 있나요?"
```

**실제 출력:**

```text
  [1.분류]   0.3초 · 토큰 67→6   · 휴가-규정
  [2.답변]   0.4초 · 토큰 234→4  · 10일
  [3.다듬기] 0.4초 · 토큰 64→19  · 관리자님의 연차 이월 일수는 최대 10일까지 가능합니다.

답변: 관리자님의 연차 이월 일수는 최대 10일까지 가능합니다.
[pipeline] 호출 3회 · 입력 365 + 출력 29 토큰 · 1.1초
```

**★ 성공 판정:** 세 단계가 순서대로 찍히고, 답이 맞고, **입력 토큰 합계(365)가 기준선(508)보다 작습니다.** 판정 규칙의 첫 칸
(토큰 ↓ · 정답 ○) — 격리 성공입니다.

### 왜 호출이 3배인데 토큰은 줄었나

분류 단계가 문서 3편 중 1편을 골라 줬기 때문입니다. 2단계가 본 것은 234토큰(휴가 규정만)이고, 단일 호출은 508토큰(3편 전부)을
봤습니다. **호출 수와 비용은 따로 움직입니다.** `[해석]`

| | 단일 | 파이프라인 |
| --- | --- | --- |
| 호출 | 1 | 3 |
| 입력 토큰 | 508 | **365** |
| 단계별 관찰 | 불가 | **가능** (어디서 틀렸는지 보임) |

## 2. 라우터 — 분류해서 담당에게 넘긴다

`run_router()`는 두 호출입니다. 분류를 **구조화 출력으로** 강제해 `enum` 밖의 값이 나오지 않게 합니다.

```python
schema = {"topic": {"enum": ["휴가-규정", "장비-규정", "회의실-예약"]}, "reason": …}
topic = json.loads(ask("질문을 담당 분야로 분류한다.", q, schema=schema))["topic"]
return ask(SPECIALISTS[topic], f"<규정>\n{docs[topic]}…", q)     # 담당은 자기 문서만
```

**정상 동작:**

```bash
$ python3 patterns.py router "회의실은 몇 시간까지 쓸 수 있나요?"
  [라우터] 1.2초 · 토큰 35→24 · { "topic": "회의실-예약","reason": "회의실 사용 시간 문의"}
  → '회의실-예약' 담당에게 위임
  [담당:회의실-예약] 0.6초 · 토큰 224→13 · 한 번에 최대 2시간까지 사용할 수 있습니다.
[router] 호출 2회 · 입력 259 + 출력 37 토큰 · 1.8초
```

**★ 성공 판정:** 분류가 맞는 담당을 고르고, 담당의 입력 토큰이 문서 1편 크기(약 220~250)이며, 답이 맞습니다. 입력 합계 259는
기준선의 절반입니다 — 다만 이 예시는 회의실 질문이고 기준선은 연차 질문입니다. 입력량이 적다는 관측만으로 같은 질문에서 어느 구성이 가장 저렴한지 판단하지는 않습니다.

## 3. ① 오분류 전파 — 실제로 일어난 일 ★

```bash
python3 patterns.py router "관리자는 연차를 며칠까지 이월할 수 있나요?"
```

**실제 출력:**

```text
  [라우터] 0.7초 · 토큰 40→24 · { "topic": "회의실-예약","reason": "연차 관련 문의" }
  → '회의실-예약' 담당에게 위임
  [담당:회의실-예약] 0.5초 · 토큰 228→9 · 규정에서 찾지 못했습니다.

답변: 규정에서 찾지 못했습니다.
[router] 호출 2회 · 입력 268 + 출력 33 토큰 · 1.2초
```

**기준 질문조차 틀렸습니다.** 라우터는 `reason`에 "연차 관련 문의"라고 적어 놓고 `topic`은 회의실-예약을 골랐습니다 — 근거와 결론이
어긋난 채로. 담당은 정직하게 "찾지 못했습니다"라고 답했고, 사용자는 답을 못 받았습니다. 같은 질문을 단일·파이프라인·루프로 돌리면
전부 맞힙니다. **이 실행에서는 라우터가 담당 분야를 잘못 선택해, 답변에 필요한 문서가 전달되지 않았습니다.** `[실행 검증 · 2026-08-30]`

> **초판과 다른 점:** 2026-08-23(Ollama 0.32.7)에는 같은 질문을 라우터가 맞게 분류했고(268 토큰, 정답), "노트북 반납"·"장비 분실"
> 두 문항만 틀렸습니다. 2026-08-30(Ollama 0.33.0)에는 같은 모델 태그·temperature 0인데 이 질문까지 틀립니다. **각 환경의 반복 실행에서는 결과가 같았지만(3회 동일),
> 두 버전에서 기록한 결과는 달랐습니다.** "지난번엔 됐다"는 라우터의 안전 근거가 아닙니다. `[실행 검증 · 2026-08-30]`

### 얼마나 자주 틀리나 — 8문항 측정

`questions.json`에 질문과 정답 분야가 있습니다. `--batch`는 분류만 8번 하고 정확도를 냅니다(담당 호출 없음).

```bash
python3 patterns.py router --batch questions.json
```

**실제 출력:** (3회 반복, 전부 동일)

```text
  [O] 연차 이월 한도는?  → 휴가-규정  (정답 휴가-규정)
  [O] 경조 휴가 며칠?  → 휴가-규정  (정답 휴가-규정)
  [X] 관리자는 연차를 며칠까지 이월할 수 있나요?  → 회의실-예약  (정답 휴가-규정)
  [X] 노트북 반납 기한은?  → 휴가-규정  (정답 장비-규정)
  [X] 노트북은 언제까지 반납하나요?  → 회의실-예약  (정답 장비-규정)
  [X] 장비 분실하면?  → 회의실-예약  (정답 장비-규정)
  [O] 회의실 예약은 며칠 전부터?  → 회의실-예약  (정답 회의실-예약)
  [O] 회의실은 몇 시간까지 쓸 수 있나요?  → 회의실-예약  (정답 회의실-예약)

라우터 정확도: 4/8 = 0.50
```

**★ 판정:** 정확도가 찍히고, 틀린 문항이 어느 분야로 갔는지 보입니다. 작성 환경에서는 **장비-규정이 한 번도 선택되지 않았고**,
"노트북 반납"은 문구에 따라 휴가·회의실로 갈렸습니다. 내 환경에서 8/8이 나왔다면 그것도 기록하세요 — 그리고 문항을 늘리세요.
`[실행 검증 · 2026-08-30]`

### 같은 모델인데 파이프라인의 분류는 맞았다

```bash
python3 patterns.py pipeline "노트북은 언제까지 반납하나요?"
```

```text
  [1.분류]   0.4초 · 토큰 62→6   · 장비-규정
  [2.답변]   0.6초 · 토큰 194→19 · 퇴직 또는 장기 휴직 시 마지막 근무일 3영업일 전까지
[pipeline] 호출 3회 · 입력 327 + 출력 55 토큰 · 1.7초
```

라우터가 회의실로 보낸 질문을 파이프라인의 분류는 장비-규정으로 맞혔습니다. 차이는 **프롬프트와 출력 형식뿐입니다** — 파이프라인은
"다음 중 하나로만 답한다"는 자유 텍스트, 라우터는 `enum` 구조화 출력. 프롬프트와 출력 형식을 함께 바꾼 비교이므로, 차이의 원인이 구조화 출력인지 이 실습만으로 분리해 판단할 수는 없습니다. `[해석]` 확실한 것은 하나 — **분류 프롬프트를 바꾸면 결과가 바뀌므로 바꿀 때마다
`--batch`로 다시 재야 한다는** 것입니다.

### 이 실패가 특히 나쁜 이유 `[해석]`

1. **담당자는 정직하게 답합니다** — "규정에서 찾지 못했습니다". 시스템은 정상 동작한 것처럼 보입니다.
2. **틀렸다는 신호가 약합니다.** 오류도, 예외도, 낮은 점수도 없습니다. `reason`을 로그로 찍지 않았다면 "연차 관련 문의 → 회의실"이라는
   모순도 못 봤을 것입니다.
3. **잘못 선택한 분야의 담당에게는 답할 자료가 없습니다.** 이 실습처럼 담당이 자기 문서만 읽고 재시도 경로도 없다면 분류 오류가 최종 답변 실패로 이어집니다. 기록된 분류 정확도는 0.50입니다.

## 4. 고치기 — 폴백으로 되돌아갈 길

폴백(fallback)은 기존 경로로 처리하지 못할 때 사용하는 대체 경로입니다. 이 실습의 `--fallback`은 담당이 "찾지 못했습니다"라고 하면 **전체 문맥(단일 호출)으로 한 번 더** 시도합니다.

```bash
python3 patterns.py router "노트북은 언제까지 반납하나요?" --fallback
```

**실제 출력:**

```text
  [라우터] 0.8초 · 토큰 35→24 · { "topic": "회의실-예약","reason": "반납일정 문의"}
  → '회의실-예약' 담당에게 위임
  [담당:회의실-예약] 0.2초 · 토큰 221→9 · 규정에서 찾지 못했습니다.
  → 담당이 찾지 못함 → 폴백: 전체 문맥으로 한 번 더
  [단일] 0.5초 · 토큰 501→27 · 퇴직 또는 장기 휴직 시 마지막 근무일 3영업일 전까지 총무팀에 반납한다.

답변: 퇴직 또는 장기 휴직 시 마지막 근무일 3영업일 전까지 총무팀에 반납한다.
[router] 호출 3회 · 입력 757 + 출력 60 토큰 · 1.5초
```

**★ 판정:** 답이 맞아졌습니다. 대가는 **호출 3회·입력 757토큰** — 처음부터 단일로 했을 때(1회·501)의 1.5배입니다. 맞게 분류한 회의실 질문의 예시는 259토큰, 폴백이 발동한 이 노트북 질문은 757토큰이었습니다. 분류 정확도 0.50과 이 두 예시만으로 질문 목록 전체의 평균 비용을 계산할 수는 없습니다. **이번 기록만으로는 라우터를 도입할 이득이 확인되지 않았습니다.** 필요한 분류 정확도는 오분류의 영향과 폴백 비용에 따라 정해야 합니다. 이 8문항 실험은 0.9 같은 보편적 채택 기준을 뒷받침하지 않습니다. `[실행 검증 · 2026-08-30]`

| 대책 | 방법 | 실습에서 |
| --- | --- | --- |
| **분류 근거를 남긴다** | `reason`을 스키마에 넣고 로그에 찍기 | 이미 함 — 모순("연차 관련 문의" → 회의실)을 잡아 줌 |
| **분류를 측정한다** | 정답 분야를 적은 질문 목록으로 정확도 | `--batch questions.json` |
| **폴백을 둔다** | 담당이 못 찾으면 전체 문맥으로 | `--fallback` |
| 모호하면 넘기지 않는다 | `confidence`가 낮으면 라우팅 대신 전체 문맥 | 🔧 스키마에 `confidence` 추가 |
| 분야를 줄인다 | 경계가 흐릴수록 틀림. 3개도 틀렸음 | — |
| 더 큰 모델을 분류에만 | 분류는 짧아서 큰 모델도 싸다 | `--model`로 분류·담당 모두 바뀜 — 분리는 🔧 |

| 실패가 발생한 단계 | 라우터의 분류 (모델의 판단이 제어 흐름을 쥠) |
| --- | --- |
| 판정 | 토큰 ↓인데 정답 ✗, `reason`이 결론과 모순 |
| 실무에서의 신호 | "찾지 못했습니다"가 특정 분야에 몰림. 한 분야가 선택되지 않음 |

## 5. 두 패턴 언제 쓰나

| | 파이프라인 | 라우터 |
| --- | --- | --- |
| 쓸 때 | 처리 **순서가 정해져** 있을 때 | 요청이 **분야로 갈리고** 분류 정확도를 쟀을 때 |
| 주의할 점 | 단계가 고정돼도 분류·답변 오류는 생길 수 있음 | 분류 오류가 담당의 답변 실패로 이어질 수 있음 |
| 먼저 확인 | 단계를 합칠 수 없나? | 오분류 영향에 맞는 정확도 기준과 폴백이 있나? |

## 6. 점검표

- [ ] 기준선(단일)의 호출·토큰·정답을 적었다
- [ ] 파이프라인과 단일의 **입력 토큰을** 비교했다
- [ ] 라우터의 오분류를 재현했거나, 재현되지 않았음을 8문항 정확도와 함께 기록했다
- [ ] 분류 근거(`reason`)를 로그에 남기고 있다
- [ ] 폴백 경로가 있고, 폴백의 비용을 알고 있다
