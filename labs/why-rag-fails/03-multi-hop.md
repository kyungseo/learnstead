# 03 — multi-hop: 벡터가 막히고 그래프가 답할 때

"검색 고도화 프로젝트 담당자가 속한 팀의 팀장은?" — 답은 **세 파일에** 흩어져 있습니다. 담당자는 프로젝트 문서에, 소속은 팀 문서에,
팀장도 팀 문서의 **다른 단락에.** 벡터 검색은 세 조각을 동시에 집어야 하고, 그래프는 선을 따라갑니다. 이 문서는 가장 작은
GraphRAG를 만들어 그 차이를 실측하고, 그래프가 만드는 **새로운 실패**(오추출·틀린 인용)까지 봅니다.

← [02 생성 실패와 진단표](02-generation-failure.md) · 다음 → [04 골든셋으로 숫자 만들기](04-golden-set.md)

> **검증 상태:** 색인(약 16초)·질의·벡터 비교를 Apple M4 Pro·24GB Mac, Ollama 0.33.0, `gemma3:4b`, `networkx` 3.6.1에서 실행했습니다.
> `[실행 검증 · 2026-08-30]` 소형 모델의 추출 결과는 실행마다 다를 수 있으므로 `--build` 출력을 반드시 눈으로 확인합니다.

---

## 0. 무엇을 만드나

`graph_minimal.py`는 `graph_docs/`의 문서에서 LLM으로 `(주어, 관계, 목적어)` 트리플을 뽑아 NetworkX 그래프를 만들고, 질문에
이름이 그대로 나오는 개체에서 **n홉** 이내의 사실을 모아 답합니다. 커뮤니티 요약(global search)은 만들지 않습니다.
트리플 형식은 구조화 출력(JSON schema)으로 강제합니다 — 방법 자체는 [별도 가이드](../../guides/local-llm-app-integration/05-structured-output.md)에
있습니다. 개념은 [가이드 07](../../guides/local-rag/07-graph-basics.md)·[08](../../guides/local-rag/08-graphrag.md).

```text
graph_docs/
├── 팀-구성.md          # 플랫폼팀(팀장 김서연, 박지호·이도윤 소속) · 데이터팀
├── 프로젝트-담당.md    # 검색 고도화(박지호) · 고객 대시보드 · 로그 파이프라인
├── 예산과-일정.md      # 팀 예산 · 프로젝트 종료 월
└── 주간-공지.md        # "프로젝트 담당자", "팀장 회의" 같은 단어를 쓰지만 답과 무관한 공지 (distractor)
```

네 번째 파일이 장치입니다. 질문과 **단어는** 많이 겹치지만 답은 없습니다 — 01 ③′의 그래프판입니다. `[해석]`

## 1. 색인 — 트리플 뽑기

```bash
pip install openai networkx
cd labs
python3 graph_minimal.py --build
```

**★ 성공 판정 (색인):** 트리플이 `주어 --관계--> 목적어` 형태로 출력되고, 마지막에 `그래프 저장: 노드 n개, 엣지 m개`가 나옵니다.
출력된 트리플을 `graph_docs/` 원문과 대조해 **문장에 없는 관계가 있는지** 확인합니다.

작성 환경의 실제 출력(노드 25·엣지 22, 일부):

```text
  플랫폼팀 --팀장--> 김서연              ← 원문 "플랫폼팀의 팀장은 김서연" — 방향이 팀→사람
  플랫폼팀 --소속--> 박지호
  정하은 --소속--> 데이터팀              ← 같은 관계인데 이번엔 사람→팀. 방향이 문장마다 다름
  검색 고도화 프로젝트 --담당자--> 박지호
  검색 고도화 프로젝트 --담당자--> 발표 자료   ← 원문은 "담당자는 발표 자료를 공유한다". 오추출
  각 팀 --팀장--> 팀장 회의              ← 원문은 "각 팀의 팀장은 팀장 회의에 참석". 오추출
  프로젝트 담당자 --승인--> 소속 팀 팀장     ← 공지 문서에서 나온 '일반 명사' 노드
```

세 가지를 눈여겨보세요. `[실행 검증 · 2026-08-30]`

1. **방향이 일정하지 않습니다.** 같은 "소속"이 팀→사람으로도, 사람→팀으로도 나옵니다. 그래서 이 스크립트는 **무방향으로** 탐색합니다.
2. **오추출이 사실처럼 남습니다.** "검색 고도화 프로젝트 —담당자→ 발표 자료"는 원문에 없는 관계입니다. [가이드 08 §4](../../guides/local-rag/08-graphrag.md)의
   "환각 트리플"이며, 트리플에 출처를 저장하고 검수하지 않으면 그래프가 이것을 진실로 답합니다. 질의 결과에도 출처 파일명이
   표시되므로, 사용한 사실과 원문을 함께 대조합니다.
3. **distractor 문서가 일반 명사 노드를 만듭니다.** "프로젝트 담당자", "소속 팀 팀장" 같은 노드는 실제 개체가 아닌데 그래프에
   들어와서, 다음 단계에서 질문의 출발점을 흐립니다.

## 2. 질의 — 홉 수에 따라 무엇이 달라지나

```bash
python3 graph_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?"
```

**★ 성공 판정 (질의):** `출발 개체`에 `검색 고도화 프로젝트`가 잡히고, 근거 사실에 담당자·소속·팀장 세 관계가 포함되며, 답이
"김서연"이면 성공입니다.

작성 환경의 실제 결과: 출발 개체가 **둘** 잡혔습니다 — `['검색 고도화 프로젝트', '프로젝트 담당자']`. 두 번째는 공지 문서가 만든
일반 명사 노드입니다. 3홉 이내 사실 12개가 모였고 답은 맞았습니다.

```text
답변: [8], [11]을 통해 답변합니다. 검색 고도화 프로젝트 담당자는 박지호이고, 프로젝트 담당자는 소속 팀 팀장의 승인을 받습니다.
따라서 검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 김서연입니다.
```

**그런데 인용이 틀렸습니다.** [8]은 "검색 고도화 프로젝트 —담당자→ 박지호"로 맞지만, [11]은 공지에서 나온 "프로젝트 담당자
—승인→ 소속 팀 팀장"입니다. 김서연에 닿는 사실은 [2] "플랫폼팀 —팀장→ 김서연"과 [3] "플랫폼팀 —소속→ 박지호"인데 인용되지
않았습니다. 답은 맞고 근거도 목록에 있는데 **인용이 엉뚱한 사실을 가리키는** 경우 — 02의 ④와 같은 부류이며, 사람이 인용만
믿고 검수하면 놓칩니다. `[실행 검증 · 2026-08-30]`

홉 수를 줄여 봅니다.

```bash
python3 graph_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?" --hops 2
python3 graph_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?" --hops 1
```

| 홉 | 모인 사실 | 작성 환경의 답 | 판정 |
| --- | --- | --- | --- |
| 3 | 12개 (팀장 관계 포함) | 김서연 — 정답, 인용 틀림 | 정상 (인용 검수 필요) |
| 2 | 9개 (`플랫폼팀 —소속→ 박지호`까지, 팀장 관계 없음) | **"팀장은 박지호입니다"** | **환각** — 사실에 없는 결론 |
| 1 | 7개 | "찾지 못했습니다" | 정직한 실패 |

2홉이 가장 나쁩니다. 답에 닿을 듯 말 듯한 사실만 모이자 모델이 **빈칸을 채웠습니다.** 1홉은 아예 못 찾아서 정직했습니다. 정보가
"거의" 있을 때가 "전혀" 없을 때보다 위험하다는 것 — 01 ③′과 같은 교훈입니다. `[실행 검증 · 2026-08-30]` 홉 수가 곧 "몇 단계를
건너뛸 수 있는가"이고, 추출 방향이 일정하지 않으므로 필요한 홉 수는 예측보다 큽니다.

## 3. 같은 질문을 벡터 RAG로

01·02에서 쓴 `rag_minimal.py`에 `--docs graph_docs`를 주면 같은 문서 묶음(조각 10개)을 벡터로 검색합니다.

```bash
python3 rag_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?" --docs graph_docs --top-k 3
python3 rag_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?" --docs graph_docs --top-k 5
python3 rag_minimal.py "검색 고도화 프로젝트 담당자가 속한 팀의 팀장은 누구인가요?" --docs graph_docs --top-k 8
```

| top-k | 근거 상위 | 작성 환경의 답 | 판정 |
| --- | --- | --- | --- |
| 3 | 담당(0.70) · 공지 보고회(0.53) · 일정(0.52) | "문서에서 찾지 못했습니다" | 정직한 실패 — 소속·팀장 조각이 없음 |
| 5 | + 대시보드(0.48) · **데이터팀**(0.46) | **"데이터팀의 팀장은 최민준입니다 [5]"** | **오답** — 엉뚱한 팀의 팀장 |
| 8 | + 로그(0.46) · **플랫폼팀**(0.45) · 팀장 회의(0.38) | "박지호 [1] … 플랫폼팀 팀장은 김서연입니다 [7]" | 정답 |

`[실행 검증 · 2026-08-30]` 세 줄이 multi-hop의 실체입니다. 질문 문장과 **가장 비슷한** 조각(담당 0.70)은 하나뿐이고, 답에 필요한
나머지 두 조각(플랫폼팀 0.45)은 공지 문서의 무관한 조각(0.53)보다 **아래에** 있습니다. top-k를 늘리면 결국 들어오지만(8 = 전체의
80%), 그 사이 5에서는 엉뚱한 팀을 답했습니다. hybrid(`--search hybrid --top-k 3`)도 같은 결과였습니다 — 단어가 겹치는 공지가
BM25에서도 앞서기 때문입니다.

그래프는 유사도가 아니라 **연결을** 따라가므로 담당자 → 소속 → 팀장 경로가 점수와 무관하게 모입니다. 이것이 [가이드 08 §6](../../guides/local-rag/08-graphrag.md)의
"multi-hop 질문이 반복되면 그래프를 비교한다"는 선택 규칙을 보여 주는 실측입니다.

## 4. 판정과 처방

| 원인 부품 | 검색의 형태 (유사도 top-k는 경로를 모으지 못함) |
| --- | --- |
| 처방 | 벡터 + 그래프 local search — 단, 트리플 출처 저장·검수, 관계 이름 고정(프롬프트에 목록 제시), 일반 명사 노드 제거(entity linking 개선) |
| 그래프가 새로 만드는 실패 | 오추출(환각 트리플), 방향 불일치, 틀린 인용, 부족한 홉에서의 환각 |
| 실무에서의 신호 | "A의 B의 C" 꼴 질문에서만 틀림. top-k를 키우면 맞지만 다른 질문의 잡음이 늘어남 |

## 5. 초기화

```bash
python3 graph_minimal.py --reset     # graph.json 삭제
```
