# RAG는 왜 틀리는가

![RAG 파이프라인에서 빠진 조각, 잘못 검색한 조각, 답과 분리된 근거를 찾아 체크리스트와 도구로 고치는 손그림](assets/why-rag-fails-hero.webp)

튜토리얼에서 만든 RAG로 다섯 가지 실패 — **검색 누락, 잘못된 조각, 관련 없는 문서, 근거 없는 답변, multi-hop** — 를 일부러 만들어
보고, 각각을 **어떤 출력을 보고 판정하는지, 어느 부품을 고쳐야 하는지** 익힙니다. 마지막에는 눈으로 하던 판정을 골든셋 20문항으로
숫자로 바꿉니다. 시리즈에서 가장 많이 배우는 자료입니다.

이 자료는 세 편으로 이어지는 시리즈의 세 번째입니다. 원리는 [가이드](../../guides/local-rag/README.md), 첫 성공 경로는 [튜토리얼](../../tutorials/local-rag-build/README.md)에
있습니다. 튜토리얼을 끝냈다는 전제로 시작하지만, `labs/`에 필요한 문서와 스크립트가 전부 들어 있어 이 자료만으로도 실행됩니다.

> **왜 하나:** 이 실습에서 예상한 실패 둘은 재현되지 않았고, 예상 못 한 실패가 셋 나왔습니다. 그 차이를 읽는 것이 RAG를 운영하는
> 기술입니다.

> **검증 상태:** 다섯 시나리오와 골든셋 측정을 Apple M4 Pro·24GB Mac, Ollama 0.33.0, `bge-m3`·`gemma3:4b`에서 실제로 실행했습니다.
> `[실행 검증 · 2026-08-30]` 결과는 예상과 달랐던 곳이 있습니다 — 각 시나리오에 그대로 적었습니다. 모델·버전이 다르면 또 다를 수
> 있으니 "재현됨/안 됨"을 스스로 기록하세요. 그것 자체가 이 실습의 산출물입니다. 상세는 [검증 기록](VALIDATION.md).

## 학습 목표와 완료 조건

| 목표 | 완료 조건 |
| --- | --- |
| 실패를 구분한다 | 각 실패를 **출력의 어느 줄로** 판정하는지 말할 수 있다 |
| 원인을 부품에 대응시킨다 | 실패마다 "청킹 / 검색 / 프롬프트·생성 / 데이터 / 그래프" 중 어디인지 짚는다 |
| 고쳐서 확인한다 | 각 실패에 대해 한 가지 수정으로 결과가 바뀌는 것을 본다 |
| 숫자로 잰다 | 골든셋 20문항으로 질문 성공률(`question success@3`)과 필수 구절 재현율(`phrase recall@3`)을 재고, 설정을 하나 바꿔 다시 잰다 |

![RAG 파이프라인 위에 네 가지 기본 실패 지점 — 검색 누락(검색), 잘못된 조각(청킹), 관련 없는 문서(검색·하한), 근거 없는 답변(프롬프트·생성) — 을 표시한 진단 지도](diagrams/08-failure-map.svg)

그림은 기본 실패 네 지점(①~④)입니다. ②′·③′은 각각 ②·③의 변형이고, ⑤는 파이프라인 밖(검색의 형태)에서 생깁니다.

## 판정의 기본 규칙 ★

모든 시나리오에서 보는 것은 세 줄입니다. `[원리]`

1. **근거 목록** — 정답이 들어 있는 조각이 상위에 있는가?
2. **인용 번호** — 답이 어느 조각을 가리키는가?
3. **조각 원문** — 그 조각에 답의 내용이 실제로 있는가? 그리고 **답이 그 내용을 다 썼는가?** (`--show`로 확인)

| 근거에 정답 | 답 ↔ 원문 | 답이 근거를 다 씀 | 판정 |
| --- | --- | --- | --- |
| 있음 | 일치 | 예 | 정상 |
| 없음 | — | — | **검색 또는 청킹 실패** (①·③·③′·⑤) |
| 반만 있음 | 반만 일치 | — | **잘못된 조각** (②) |
| 있음 | 일치 | 아니오 | **불완전 답변** (②′) — 근거 목록만 보면 정상처럼 보임 |
| 있음 | 불일치 | — | **생성 실패** (④) |

세 번째 축(완전성)이 없으면 "근거는 맞는데 덜 쓴 답"이 정상으로 분류됩니다. 튜토리얼 첫 질문이 바로 그 경우였습니다.

## 시나리오 지도

| # | 실패 | 어떻게 만드나 | 원인 부품 | 문서 |
| --- | --- | --- | --- | --- |
| ① | 검색 누락 | 자산 코드 "EQ-2291"로 질문 | 검색 (dense의 한계) | [01](01-retrieval-failures.md) |
| ② | 잘못된 조각 | 두 조각에 걸친 답을 top-k 1로, 또는 60자 고정 청킹으로 | 청킹 | [01](01-retrieval-failures.md) |
| ②′ | 불완전 답변 | 두 조각이 다 들어와도 모델이 하나만 씀 | 생성 (+ 청킹으로 예방) | [01](01-retrieval-failures.md) |
| ③ | 관련 없는 문서 | 문서에 없는 주제(식대)를 질문 | 검색 (하한 부재) + 데이터 | [01](01-retrieval-failures.md) |
| ③′ | 단어 겹침 환각 | 단어는 겹치는데 답은 없는 질문(연차 교육) | 검색 → 생성 연쇄 | [01](01-retrieval-failures.md) |
| ④ | 근거 없는 답변 | 규칙 제거, 또는 인용은 있는데 원문과 다른 경우 | 프롬프트·생성 | [02](02-generation-failure.md) |
| ⑤ | multi-hop | 세 문서에 흩어진 사실을 잇는 질문 → 벡터 RAG vs 그래프 | 검색의 형태 | [03](03-multi-hop.md) |
| 측정 | 골든셋 검색 지표 | 20문항으로 질문 성공률과 필수 구절 재현율을 측정하고, 청킹을 바꿔 재측정 | — | [04](04-golden-set.md) |

## 고정된 시나리오·입력·환경

`labs/`를 통째로 복사합니다. 튜토리얼과 같은 규정 4편이 들어 있습니다.

```text
labs/
├── docs/                 # 가상 규정 4편 (①~④·골든셋)
├── rag_minimal.py        # 튜토리얼 뼈대 + 실패 재현용 플래그 (--search --threshold --chunk --no-rules --docs)
├── recall.py             # 골든셋 20문항 검색 지표 (모델 호출 없음)
├── goldenset.json        # 질문 · 정답 조각 번호 · 정답에 있어야 할 구절
├── graph_docs/           # 조직·프로젝트 문서 4편 (⑤)
└── graph_minimal.py      # 트리플 추출 → NetworkX 그래프 → 이웃 탐색
```

예제 문서에 일부러 넣은 장치 `[해석]`:

| 장치 | 위치 | 어떤 실패를 위해 |
| --- | --- | --- |
| 자산 코드 `EQ-2291` | 장비-규정 §1·§4 | 식별자 검색 (①) |
| "이월 한도" 목록이 앞 문장과 **다른 단락** | 휴가-규정 §3 | 조각 분리 (②·②′) |
| "연차"와 "교육"이 함께 들어간 무관한 문장 | 보안-정책 §3 | 단어 겹침 (③′) |
| 문서에 없는 주제(식대·재택 등) | — | 관련 없는 문서 (③), 골든셋의 "없음" 문항 |
| 담당자·소속·팀장이 **세 파일에** 흩어짐 + 같은 단어를 쓰는 공지 문서 | graph_docs/ | multi-hop (⑤) |

| 환경 | 값 (작성 환경) |
| --- | --- |
| Ollama · 모델 | 0.33.0 · `bge-m3`(1,024차원) · `gemma3:4b`(Q4_K_M, 적용 context 4,096) |
| Python · 패키지 | 3.14.7 · `openai` 3.6.0 · `networkx` 3.6.1 (`pip install openai networkx`) |
| 모델 호출 시간 | 질문당 1~3초 (첫 호출 8~16초) |

## 초기화

①~④와 골든셋은 파일을 만들지 않습니다(리스트 기반). ⑤는 `python3 graph_minimal.py --reset`으로 `graph.json`을 지웁니다.
기록은 [RAG 구성 카드](../../guides/local-rag/RAG-CARD.md)의 Prove 칸에 "시나리오 ①~⑤ 재현 여부와 고친 뒤 결과"로 남깁니다.

## 검증 상태를 읽는 법

| 표기 | 뜻 |
| --- | --- |
| `원리` | 특정 제품 version보다 오래 유지되는 구조·수학·물리 설명 |
| `실행 검증 · YYYY-MM-DD` | 기록한 환경에서 명령과 성공 조건을 실제로 확인함 |
| `부분 검증 · YYYY-MM-DD` | 명시한 단계만 실제로 확인함 |
| `문서 확인 · YYYY-MM-DD` | 공식 문서나 발표를 확인했지만 직접 실행하지는 않음 |
| `자료 확인 · YYYY-MM-DD` | 공개 자료를 확인했지만 1차 출처나 직접 실행으로 확정하지 못함 |
| `미검증` | 아직 직접 확인하지 못함 |
| `해석` | 근거를 바탕으로 저자가 정리한 판단 |

## 범위

이 실습이 끝나는 지점은 **"RAG가 틀렸다"를 표의 한 칸으로 분류하고, 그 칸의 첫 처방을 말하며, 바꾼 뒤 나아졌는지를 검색 지표로
보이는 순간입니다.** 다루지 않는 것: reranker 실행, LLM 판정자로 faithfulness 자동 채점, 커뮤니티 요약(global search), 수천 개
이상 조각에서의 재현.
