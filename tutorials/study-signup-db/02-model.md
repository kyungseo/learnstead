# 02. 구조 — 모임과 신청 내역 나누기

[← 01 준비](01-prepare.md) · [전체 목차](README.md) · [03 연결 →](03-connect.md)

신청 앱에는 “누가 어느 모임에 신청했는가”가 남아야 합니다. 한 사람의 이름과 모임 제목을 매번 한 줄에 복사하기보다 **모임 자체와 신청 내역을 나누고 ID로 연결합니다.**

## 먼저 종이에 적기

다음 표는 구조를 읽는 예입니다. 실제 실행에서는 ID가 더 긴 문자열일 수 있습니다.

| 모임 ID | 제목 | 정원 |
| --- | --- | --- |
| E1 | 토요일 DB 스터디 | 2 |
| E2 | 한 자리만 남은 모임 | 1 |

| 신청 ID | 모임 ID | 사용자 ID |
| --- | --- | --- |
| R1 | E1 | A |
| R2 | E1 | B |

모임 이름을 바꾸면 위쪽 모임 한 곳만 고칩니다. 아래쪽 신청 내역은 계속 같은 모임 ID를 가리킵니다. ID는 대상을 구분하는 값이고, 이름은 사람이 읽는 표시입니다. 이름이 같은 모임을 만들 수 있다는 점만 생각해도 둘을 나누는 이유가 보입니다.

## 앱에서 실제로 사용하는 구조

`events`는 모임을, `registrations`는 신청 내역을 저장합니다. 로그인 사용자는 Supabase Auth가 관리합니다. 앱이 비밀번호를 별도 테이블에 다시 저장하는 구조는 만들지 않습니다.

`registrations`의 한 행은 한 사용자의 한 모임 신청입니다. 이 문장을 먼저 정해 두면 “같은 사용자가 같은 모임을 여러 번 신청해도 되는가?”라는 질문에 답할 수 있습니다. 이번 앱의 답은 아니며, 이를 DB의 고유값 제약조건으로 표현합니다.

| 규칙 | DB에서 표현하는 방법 | 막으려는 실수 |
| --- | --- | --- |
| 모임·신청을 각각 구분 | 기본 키(primary key) | 다른 행을 같은 대상으로 혼동 |
| 존재하는 모임과 사용자에 연결 | 외래 키(foreign key) | 없는 모임에 신청 내역만 생성 |
| 한 사용자당 한 모임 신청 | 두 열을 묶은 고유값(unique) | 더블 클릭·재요청으로 중복 신청 |
| 정원은 올바른 숫자 | 값 검사(check) | 음수 같은 불가능한 값 |

`[원리]` 제약조건은 DB가 데이터를 받을 때 검사하는 규칙입니다. 화면의 입력 안내를 통과하지 않고 API를 직접 호출해도 DB에 도달한 값은 같은 규칙을 거칩니다. 제품별 문법과 세부 동작은 [PostgreSQL 제약조건 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)에서 확인할 수 있습니다. `[문서 확인 · 2026-09-13]`

## 정원은 왜 조금 더 어려울까?

정원이 1명이고 현재 신청자가 0명이라고 합시다. A와 B가 거의 동시에 확인하면 둘 다 “자리가 있다”고 볼 수 있습니다. 화면에서 버튼을 빨리 잠그거나 숫자를 미리 확인하는 것만으로는 두 요청을 조정할 수 없습니다.

이번 앱에서는 신청 작업을 DB 함수로 묶고, 같은 모임의 마지막 자리를 동시에 바꾸는 요청을 조정합니다. 이 단계에서는 “정원 확인과 신청 저장이 연결된 하나의 작업이어야 한다”는 점만 이해하면 됩니다. 실제 경쟁 요청은 [실습 03](../../labs/database-safety/03-atomicity.md)에서 확인합니다.

## SQL을 다 읽지 못해도 확인할 수 있는 것

`supabase/migrations/`의 첫 구조 파일을 AI에게 읽히고, 위의 표와 비교해 보세요. migration은 DB 구조를 순서대로 바꾸는 SQL 기록입니다. 새 환경에서는 이 기록을 적용해 같은 구조를 만들고, 이미 데이터가 있는 환경에서는 다음 변경을 이어 붙입니다.

> “`events`와 `registrations`의 열과 연결 관계를 비개발자도 이해할 표로 정리해 줘. 중복 신청, 없는 모임, 마지막 자리 동시 신청은 각각 어디에서 막는지 파일의 근거와 함께 설명해 줘. 아직 코드는 바꾸지 마.”

AI의 설명에 “안전하게 처리됩니다”만 있다면 다시 구체적인 규칙과 경로를 요청하세요. 누가 읽고 바꿀 수 있는지는 구조 표만으로 알 수 없으므로 [04 권한](04-access.md)에서 따로 확인합니다.

## 이 단계의 성공 판정

자신의 말로 다음 세 문장을 완성할 수 있으면 다음 단계로 넘어갑니다.

1. `events`의 한 행은 ______이고, `registrations`의 한 행은 ______이다.
2. 같은 사용자의 중복 신청은 ______에서 막는다.
3. 마지막 자리의 동시 신청은 숫자를 화면에 보여 주는 것 외에 ______이 필요하다.

답은 각각 “모임 / 한 사용자의 신청”, “DB의 고유값 제약조건”, “DB 안에서 동시 요청을 조정하는 신청 처리”입니다. 이 단계는 문서를 읽기만 하므로 초기화할 데이터가 없습니다.
