# 03. 연결 — 화면에서 신청하고 다시 읽기

[← 02 구조](02-model.md) · [전체 목차](README.md) · [04 권한 →](04-access.md)

이번에는 화면에서 모임을 읽고 신청합니다. **신청 직후 보이는 화면과, DB에서 다시 읽어 온 결과가 일치하는지** 확인하는 단계입니다.

## 앱 실행과 로그인

[01 준비](01-prepare.md)를 완료한 터미널의 `app` 폴더에서 다음을 실행합니다.

```bash
npm run dev
```

이 터미널은 서버가 실행 중인 채로 둡니다. 브라우저에서 [http://127.0.0.1:5173](http://127.0.0.1:5173)을 엽니다. 앱은 로그인한 사용자에게만 모임 목록을 보여 줍니다.

| 사용자 | 이메일 | 비밀번호 |
| --- | --- | --- |
| A | `alice@example.com` | `Learnstead-local-2026!` |
| B | `bob@example.com` | `Learnstead-local-2026!` |

**위 값은 공개된 로컬 연습용 계정입니다.** 실제 서비스의 계정이나 비밀번호로 쓰지 않습니다. A로 로그인한 뒤 모임 세 개가 보이고, 처음 상태라면 내 신청은 0개인지 확인합니다.

이 예제는 학습 경로를 단순하게 유지하기 위해 로그인 상태를 메모리에만 보관합니다. 새로고침하면 다시 로그인해야 합니다. 재로그인 후 DB에서 같은 신청을 다시 읽는 것이 다음 확인입니다.

## 버튼 뒤에서 일어나는 일

```text
브라우저의 신청 버튼
    → 로그인 정보를 포함한 API 요청
    → DB의 신청 처리와 규칙 검사
    → 저장된 결과
    → 브라우저가 다시 읽어 표시
```

API는 앱이 다른 서비스에 정해진 형식으로 요청하는 통로입니다. 화면은 Supabase의 API에 요청하고, DB가 규칙을 검사합니다. 화면 코드가 성공 메시지를 표시했다는 사실만으로 저장을 증명하지 않습니다.

로그인에는 연습용 계정만 사용합니다. 이 계정의 비밀번호와 로컬 설정은 인터넷 서비스에 재사용하면 안 됩니다. 실제 서비스의 계정·메일·키를 넣을 이유가 없습니다.

## 첫 신청에서 볼 것

1. `내 연습 계정`의 이메일·비밀번호로 사용자 A에 로그인합니다.
2. `참여할 수 있는 모임`에서 `함께 읽는 데이터 이야기`의 `모임 신청`을 누릅니다.
3. `내 신청 내역`에 같은 모임이 한 건 보이는지 확인합니다.
4. 해당 모임 버튼이 `신청 완료`로 바뀌고 비활성화됐는지 봅니다.
5. `내 메모`에 `첫 DB 연습`을 입력하고 `메모 저장`을 누릅니다.
6. 브라우저를 새로고침한 뒤 A로 다시 로그인합니다.
7. 신청 한 건과 `첫 DB 연습` 메모가 그대로인지 확인합니다.

성공 판정은 **내 신청이 한 건 생겼고, 다시 읽었을 때 메모까지 남아 있는 것**입니다. 신청 후 버튼이 비활성화되므로 화면에서 같은 버튼을 계속 누르는 검사는 하지 않습니다. 버튼을 거치지 않는 중복 요청도 DB가 막는지는 [실습 02](../../labs/database-safety/02-constraints.md)에서 직접 API로 확인합니다.

원상복구하려면 해당 내역의 `신청 취소`를 누릅니다. 내 신청에서 사라지고 모임의 신청 인원이 줄어드는지 확인하세요. 다음 권한 단계에서 사용할 신청 한 건은 다시 만들어 두면 됩니다.

## 브라우저에서 확인할 수 있는 증거

개발자 도구를 쓰는 것이 처음이라면 처음에는 화면과 새로고침만 확인해도 됩니다. 한 단계 더 보고 싶다면 브라우저의 개발자 도구에서 Network 탭을 열고 신청 요청과 그 뒤의 조회를 찾습니다.

| 관찰 대상 | 의미 |
| --- | --- |
| 요청 주소 | 내 로컬 Supabase로 보내는가? |
| 요청 종류 | 읽기인지, 신청 처리인지? |
| 응답 상태와 내용 | 성공 응답인가, 규칙 위반인가, 빈 결과인가? |
| 다시 조회한 목록 | 실제 저장된 상태가 무엇인가? |

인증 토큰이 들어 있는 요청 전체를 캡처해 공개하거나 AI에게 붙여 넣지 마세요. 설명에 필요한 주소의 경로·상태 코드·비밀값을 지운 응답만 남깁니다.

## 화면에서 지웠는데 DB에는 남는다면

화면의 목록을 잠시 지운 것과 DB의 행을 삭제한 것은 다릅니다. 반대로 서버에서는 저장됐지만 네트워크 문제가 생겨 화면이 실패로 보일 수도 있습니다. 실패 안내를 보고 무조건 재시도하면 중복 요청이 생길 수 있으므로, DB 규칙과 현재 상태 확인이 함께 필요합니다.

이 예제의 신청은 같은 모임과 사용자의 중복을 막습니다. 모든 앱에서 재시도 문제가 저절로 해결된다는 뜻은 아닙니다. 결제처럼 외부 서비스까지 이어지는 작업은 별도의 설계가 필요하며 이번 튜토리얼 범위에 포함하지 않습니다.

## AI에게 작은 변경 맡기기

기준 앱이 동작한 뒤에는 문구 하나처럼 데이터 구조를 바꾸지 않는 변경부터 요청해 보세요.

> “신청 성공 안내를 처음 쓰는 사람이 이해하기 쉽게 바꿔 줘. 신청 API·DB 구조·권한은 유지해. 수정 후에는 신청 한 건, 새로고침 후 유지, 같은 모임 중복 신청이 생기지 않는지 확인해 줘.”

화면 문구 변경에도 저장·중복 확인을 함께 요청하면 기존 기능이 깨지는지 볼 수 있습니다. AI의 완료 보고와 자신의 브라우저 관찰을 나란히 두세요.

## 다음 단계로 넘어가기

신청과 다시 조회가 동작하면 그 상태를 기록합니다. 이 단계의 데이터를 다음 권한 확인에서 사용하므로 아직 초기화하지 않습니다. DB를 다시 만드는 설정 명령을 실행하면 신청 내역이 사라질 수 있습니다. 처음부터 다시 해야 한다면 [01 준비](01-prepare.md)의 연습 환경 초기화 절차로 돌아갑니다.
