# 04. 권한 — 다른 사용자로 확인하기

[← 03 연결](03-connect.md) · [전체 목차](README.md) · [05 완성 →](05-finish.md)

A로 신청에 성공했더라도 B의 데이터까지 볼 수 있다면 문제가 있습니다. **같은 화면을 다른 사용자로 열고, 허용할 일과 막을 일을 따로 확인합니다.**

## 이번 앱의 접근 규칙

| 대상·작업 | 비로그인 | 사용자 A | 사용자 B |
| --- | --- | --- | --- |
| 모임 목록 읽기 | 허용 안 함 | 허용 | 허용 |
| A의 신청 내역 읽기 | 허용 안 함 | 허용 | 허용 안 함 |
| A 이름으로 신청하기 | 허용 안 함 | 허용 | 허용 안 함 |
| A의 신청 내역 수정·삭제 | 허용 안 함 | 본인에게 허용된 범위 | 허용 안 함 |

인증(authentication)은 “이 요청을 보낸 사용자가 누구인가”를 확인합니다. 권한 검사(authorization)는 “그 사용자가 이 데이터를 이렇게 다뤄도 되는가”를 판단합니다. 로그인 화면이 있다는 사실만으로 두 번째 문제가 해결되지는 않습니다.

Supabase는 DB에서 행 단위 접근 규칙인 RLS(Row Level Security)를 적용할 수 있습니다. 테이블에서 작업 자체를 허용하는 권한과 어느 행에 적용하는지 정하는 정책을 함께 확인해야 합니다. `[문서 확인 · 2026-09-13]` [공식 RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 두 개의 로그인 상태 만들기

일반 창에서 A로 신청한 뒤 로그아웃하고 B로 로그인합니다. 또는 브라우저의 다른 프로필을 이용해 두 로그인 상태를 분리합니다. 단순히 새 탭을 하나 더 열면 같은 로그인 정보를 공유할 수 있으므로, 화면에 표시된 사용자를 매번 확인하세요.

B로 들어왔을 때 A의 신청이 “내 신청”에 보이면 안 됩니다. B가 같은 모임에 신청하면 B의 신청이 따로 생깁니다. 이번 규칙에서 모임 목록은 로그인한 사용자가 함께 읽으므로 A와 B에게 같은 모임이 보이는 것 자체는 결함이 아닙니다. 비로그인 사용자에게 모임을 공개할지는 별도의 제품 선택이며, 이번 앱에서는 허용하지 않습니다.

## 빈 목록도 정상 거절일 수 있다

권한 밖의 조회나 변경이 항상 `403` 오류로 나타나는 것은 아닙니다. RLS가 접근할 수 있는 행을 걸러 내면 조회가 성공하면서 `[]`라는 빈 목록을 돌려줄 수 있습니다. 수정·삭제 요청도 처리 대상이 0행일 수 있습니다.

따라서 판정은 다음 순서로 합니다.

1. 요청한 사용자와 대상 행을 확인합니다.
2. 응답 상태와 반환된 내용을 함께 봅니다.
3. 원래 소유자 A로 다시 조회해 행이 그대로인지 확인합니다.

**거절 문구가 보여도 데이터가 바뀌었다면 실패입니다.** 반대로 성공 상태라도 읽은 데이터가 없고 변경된 행도 없다면 의도한 제한일 수 있습니다. 정확한 API 검사와 소유자 위조는 [실습 04](../../labs/database-safety/04-authorization.md)에서 수행합니다.

## 관리자 도구와 앱은 역할이 다르다

DB 관리자 도구나 높은 권한의 키로 실행한 조회는 일반 사용자의 접근 검사가 아닙니다. 초기 데이터 준비에 쓰는 관리자 경로와 브라우저의 사용자 경로를 구분하세요. 브라우저에는 관리자 키를 넣지 않습니다.

공개 환경에서 사용할 수 있는 API 키가 있다는 이유만으로 모든 데이터가 공개돼도 된다는 뜻도 아닙니다. 키의 종류와 사용자 토큰, DB 권한·RLS가 함께 동작합니다. `[문서 확인 · 2026-09-13]` [Supabase API 키](https://supabase.com/docs/guides/getting-started/api-keys)

이 자료의 로컬 CLI는 기존 형식의 `anon`·`service_role` 키를 제공합니다. 브라우저는 `anon`과 로그인 사용자 토큰을 쓰며, `service_role`은 계정 준비 등 로컬 관리 경로에서만 사용합니다. 공식 문서의 새 `publishable`·`secret` 키와 형식이 달라도 공개용·서버 전용 권한을 구분해야 한다는 기준은 같습니다. “환경 변수에 넣었다”가 아니라 **브라우저로 전달되는 값인지와 그 권한을** 확인합니다.

## AI에게 요청할 확인

> “A가 만든 신청을 B와 비로그인 상태에서 읽기·수정·삭제해 봐. 화면에서 버튼을 숨기는 것만으로 통과 처리하지 말고 실제 API 응답과 A가 다시 읽은 DB 상태를 비교해 줘. 관리자 권한으로 대신 검사하지 마.”

튜토리얼의 완료 조건은 사용자 전환 후 목록이 의도와 맞는다는 것입니다. 자동화된 요청으로 우회까지 검사하는 일은 실습에서 이어집니다. 다음 단계에서는 이 결과를 기록하고 앱을 정리합니다.
