## 실행 검증 · 2026-09-13

**설치·로컬 DB 시작·브라우저 로그인·신청·메모·재조회·다른 계정·취소·중지·재시작·명시적 초기화까지 확인했습니다.** 브라우저에서 확인한 동작과 실제 Auth·REST·DB 검증은 아래에 구분합니다. 아래의 macOS 로컬 환경에서 실행했으며, 다른 OS에서의 실행과 클라우드 운영은 검증하지 않았습니다.

| 항목 | 실제 환경 |
| --- | --- |
| OS·아키텍처 | macOS 26.6.2 · arm64 |
| Node.js | 24.19.0 — 이 자료의 지원 경로는 Node.js 24 LTS |
| Supabase CLI | 2.117.0 — `package-lock.json` 고정 |
| PostgreSQL | 17.6 |
| Docker | 29.7.2 · 로컬 Unix 소켓 |
| Chrome | 152.0.7977.83 |
| 데이터 | 가상 사용자 A·B, 모임 3개, 최초 신청 0개 |
| 주소 | 웹 127.0.0.1:5173 · API 55321 · DB 55322 · Studio 55323 |

## 설치와 최초 시작

Learnstead 전체 파일을 받은 구조에서 `tutorials/study-signup-db/app`으로 이동해 다음을 실행했습니다. 최종 Node.js 24·잠금 파일을 사용한 `npm ci`도 다시 확인했습니다.

```bash
npm ci
npm run db:start
npm run setup
npm run dev
```

빈 DB 볼륨에서 시작해 구조·seed가 적용되고, 연습 계정 두 개와 모임 세 개·신청 0개를 확인했습니다. DB·API·Studio의 외부 공개 포트는 실제로 `127.0.0.1`에 묶였는지 검사했습니다. 프로젝트의 시작 명령은 이 조건이 맞지 않으면 중단합니다.

`npm run dev`를 실행한 터미널은 웹 서버용으로 남겨 두고, 이후 DB 명령은 다른 터미널의 같은 `app` 폴더에서 실행했습니다.

## 실제 브라우저 확인 — 11개 판정

| 번호 | 조작·조건 | 실제 결과 |
| --- | --- | --- |
| 1 | 비로그인 상태로 앱 열기 | 모임·신청 데이터가 보이지 않음 |
| 2 | A 로그인 | 모임 3개 조회 |
| 3 | A가 모임 신청 | 신청 저장 |
| 4 | A의 메모 저장 후 새로고침·재로그인 | 신청과 메모 유지 |
| 5 | B 로그인 | A의 개인 신청은 숨김, 모임의 합계 인원은 1명 |
| 6 | B가 같은 모임에 신청 | B의 신청 추가 |
| 7 | B가 자기 신청 취소 | B의 신청 삭제 |
| 8 | 다시 A로 조회 | A의 신청과 원래 메모 보존 |
| 9 | 화면 폭 390px | 가로 넘침 없음 |
| 10 | A가 자기 신청 취소 | 신청·정원 카운터 원상복귀 |
| 11 | 위 경로의 브라우저 실행 | JavaScript 런타임 오류 없음 |

모임의 전체 신청 인원을 보여 주는 것과 타인의 개인 신청 내역을 보여 주는 것은 다른 정책입니다. 이번 앱은 로그인 사용자에게 모임과 합계 인원을 보여 주고, 개인 신청과 메모는 소유자에게만 보여 줍니다.

화면에서 신청 버튼이 비활성화됐더라도 DB가 중복 요청을 막는지는 별도로 확인해야 합니다. 직접 API의 중복·소유자 위조·타인 수정·삭제·동시 요청은 [실습 검증 기록](../../labs/database-safety/VALIDATION.md)에 별도로 남겼습니다.

## 신청이 있는 상태의 중지·재시작

가상 신청 한 행과 메모를 저장한 뒤 다음을 실행했습니다.

```bash
npm run db:stop
npm run db:start
npm run setup
```

다시 로그인해 조회했을 때 **신청 ID·저장한 값·소유자의 조회 권한·정원 카운터가 그대로**였습니다. 신청 데이터가 있는 상태에서 중지·재시작해 보존 여부를 확인한 결과입니다. 검증 후에는 만든 신청을 삭제해 신청 0개·정원 카운터 합계 0으로 돌렸습니다.

## 데이터가 있는 상태의 명시적 초기화

별도로 가상 신청 한 행을 만든 뒤 다음 명령을 실행했습니다.

```bash
npm run db:reset -- --confirm-local-reset
```

실행 도구는 현재 연습 프로젝트와 DB 볼륨의 소유권을 확인하고, 서비스를 멈춘 뒤 **이 프로젝트의 DB 볼륨 한 개만 새로 만들어** 같은 시작 경로와 계정 준비를 실행했습니다. 일반적인 CLI의 `db reset` 명령을 그대로 호출한 결과는 아닙니다.

초기화 뒤 계정 2개·모임 3개·신청 0개를 확인했고, API·DB·Studio의 세 포트가 컴퓨터 내부 주소에 묶인 것도 다시 확인했습니다. SQLite의 `practice.sqlite`와 `app/.local`의 백업·기록 파일은 이 초기화 대상에 포함하지 않습니다.

새로 만든 DB에서 `npm run verify`를 다시 실행해 **통합 판정 14개가 통과했고**, 종료 후 신청과 정원 카운터가 0으로 복귀했습니다. 실제 Auth·REST·기존 데이터 migration·별도 DB 복원의 상세 범위는 [실습 검증 기록](../../labs/database-safety/VALIDATION.md)에 있습니다.

## 문서 확인 · 2026-09-13

공식 로컬 개발·RLS·API 키·migration·백업·Node.js 릴리스 문서를 읽었습니다. 확인한 주장과 주소는 [SOURCES.md](SOURCES.md)에 있습니다. 클라우드 배포 절차는 문서로만 확인했으며 직접 배포하지는 않았습니다.

## 확인하지 않은 범위

- Node.js 24 이외의 메이저 버전, Windows·Linux 실환경, 호스팅된 Supabase
- Windows 네이티브 Docker 소켓·원격 Docker를 사용하는 실행 경로
- 인터넷 공개 배포, 운영 사용자·이메일, 대규모 부하
- 실제 개인정보·결제·파일 업로드, 첨부 파일 복원
- 복원본에서 Auth 서비스를 다시 연결한 웹 로그인 전체 경로
- 특정 AI 모델의 코드 생성 성공률이나 지침 준수율

## 문서·그림 검사 · 2026-09-13

시리즈의 Markdown을 파서로 렌더해 일반 본문에 남은 강조 기호와 장별 상하 탐색을 확인했습니다. 대표 문서 6개를 Chrome으로 렌더했을 때 이미지 누락·가로 넘침이 없었습니다. 초판의 SVG 8종은 문법 검사와 PNG 렌더·시각 확인을 통과했습니다. 이후 대표 일러스트 3종은 WebP로 교체했고, 본문의 기술 도식 5종은 SVG·PNG로 유지합니다. 공개 자료 검사도 통과했습니다. 이 결과는 앱 실행이나 사용자 권한 검증과 별개의 정적 검사입니다.

## 대표 일러스트 확인 · 2026-09-13

대표 일러스트를 기존 바이브 코딩 시리즈의 손그림과 Git 가이드 표지의 옅은 아이보리 종이 배경에 맞췄습니다. 세 표지의 한국어 제목, 약 16:9 비율, 기존 표지 옆의 3열 카드 판독성, 시작 페이지 이미지 표시와 대체 텍스트를 확인했습니다. 본문 기술 도식과 앱 실행 검증 범위는 바꾸지 않았습니다.

## 관찰값 출력 추가 후 재검증 · 2026-09-13

Node.js 24.19.0·PostgreSQL 17.6의 macOS 로컬 Docker 환경에서 `npm run verify`의 14개 판정과 27개 관찰값 비교를 통과했습니다. `observations`에는 장 번호·항목·예상값·실제값·판정이 기록됩니다. 이 수는 기존 시나리오를 세분해 보여 주는 관찰 항목 수이며 새로운 운영 환경의 검증 수가 아닙니다.

- 중복 신청: A의 신청은 전후 1행, HTTP 409·`23505`였습니다.
- 동시 신청: 한 명 성공·한 명 실패, 최종 신청과 카운터는 각각 1이었습니다.
- 기존 데이터 변경: 별도 DB에서 직접 읽은 변경 전후 3행의 ID·사용자·모임 연결이 같고, 새 메모 기본값은 빈 문자열이었습니다.
- 복원: 삭제로 3행에서 2행이 된 뒤 백업으로 3행과 메모를 복원했습니다. SQL 역할별 본인 수정과 타인 수정·삭제 제한도 통과했습니다.
- 신청을 한 건 남긴 채 검증을 실행하면 데이터를 지우지 않고 시작 조건 오류로 중단했습니다. DB 중지 → 재시작 → `setup` 뒤 신청과 메모가 유지됐고, 본인 신청 취소 후 전체 검증을 다시 통과했습니다.
- 출력 모듈 검사 3건: 실제값 불일치 시 FAIL·중단, 기록 후 원본 객체 수정에 영향받지 않음, 숫자와 문자열의 차이 감지.

Auth·REST 요청과 DB 비교를 다시 실행했습니다. 브라우저 UI 전 경로는 이번 변경에서 재실행하지 않았으며, 위의 과거 UI 검증 기록과 구분합니다. Windows·클라우드·다른 PostgreSQL 버전은 이번에도 검증하지 않았습니다.
